# T-02 runbook の冒頭と0〜3節を人向けに整理する

## 目的
`docs/runbook.md` の冒頭と0〜3節を「人が打つコマンド・人が判断すること・人が見る場所」に絞り、エージェントの内部動作は1〜2行の要約とリンクにする。環境変数の説明は `docs/configuration.md` へのリンクにし、古い記述（「`/run` は1件処理して報告」）を今の動作に直す。

## 入力
- `docs/runbook.md`（冒頭・0〜3節）
- `docs/vault-spec.md`（1節・2節・7節・9節・10節と、T-01 で足した14節）
- `.claude/skills/run/SKILL.md`（手順1〜8）・`.claude/skills/plan/SKILL.md`（A）
- `docs/configuration.md`・`docs/guide.md`（runbook の節へのリンク）
- 設計文書 `vault/designs/D-20261011-user-guide.md` の「決定事項」とフェーズ3

## 成果物
- `docs/runbook.md`（1ファイル。冒頭と0〜3節だけを変える。4節以降は T-03 が変える）

## 受け入れ基準
- 冒頭と0〜3節の各節の本文が人の打つコマンド・判断・見る場所で、エージェントの内部動作は1〜2行の要約とリンクだけになっている。節ごとの方針（残したもの・削ってリンクにしたもの・その移し先）がタスク票の「進捗」に書かれ、verifier が節ごとに読んで確かめる
- `grep -rn '1件処理して報告' README.md docs .claude/skills .claude/agents .claude/ai-harness.md` の出力が空で、3節に `/run` が取れるタスクが無くなるまで処理して全タスクが done で PR を作る旨が書かれている
- `grep -nE 'SIGTERM|SIGKILL|gh api|glab mr create|draft→approved' docs/runbook.md` の出力が空
- `sed -n '/^## 3\./,/^## 4\./p' docs/runbook.md | grep -cE '^ *- 環境変数 `HARNESS_'` が `0` で、`sed -n '/^## 3\./,/^## 4\./p' docs/runbook.md | grep -c 'docs/configuration.md'` が1以上
- `sed -n '/^## 3\./,/^## 4\./p' docs/runbook.md | grep -cF '`docs/vault-spec.md` 14節'` が1以上で、`sed -n '/^## 3\./,/^## 4\./p' docs/runbook.md | grep -cF '`.claude/skills/run/SKILL.md` 手順7'` が1以上
- `grep -n '^## ' docs/runbook.md` の出力の見出しの文言が「決定済み」の12行と同じ順で一致し、`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (guide-1) '` が `1`
- `bash scripts/smoke.sh 2>&1 | tail -1` が `smoke: pass=<数> fail=0`、`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (ref-1) '` が `1`

## 決定済み
- `## ` 見出しは変えない。期待する `grep -n '^## ' docs/runbook.md` の見出しの文言（行番号は変わってよい）：`## 0. 大きなゴールは先に設計する`・`## 1. ゴールを入れる`・`## 2. 計画は自動で承認される`・`## 3. キューを回す`・`## 4. blocked に答えて戻す`・`## 5. 一括削除の手順`・`## 6. ルールを足す`・`## 7. ハーネス自体の更新を取り込む`・`## 8. creator のモデルを比べる`・`## 9. 権限モードの選び方`・`## 10. push 先が決められている環境（クラウドセッション）`・`## 困ったとき`。節の中に `###` の小見出しを足すのはよい。
- 削る基準（設計の決定済み）：同じ内容が `docs/vault-spec.md` かスキルにある時だけ削ってリンクにする。下の一覧に無い内部の記述で、vault-spec にもスキルにも同じ内容が無いものを見つけたら、消さずに runbook に残し、「進捗」に「移し先が無いため残した」と書く（blocked にしない。vault-spec はこのタスクの成果物ではない）。
- リンクの書き方は runbook の既存の形にそろえ、パスをバッククォートで書いて節・手順を続ける（例：`` `docs/vault-spec.md` 14節 ``・`` `.claude/skills/run/SKILL.md` 手順7 ``・`` `docs/configuration.md` ``）。受け入れ基準の grep はこの文字列を探すので、この形で書くこと。
- 節ごとの方針：
  - 冒頭：人の仕事を「ゴールを入れる」「blocked に答える」「PR をマージする」「マージ済みの計画を片づける」の4つにする（「月次で片づける」は古い。今は `scripts/purge_plan.sh --merged` を随時使う）。`docs/install.md` へのリンクは残す。続けて1〜2行で、仕様は `docs/vault-spec.md`、エージェントの手順は各スキル（`.claude/skills/*/SKILL.md`。`*` を含むパスは smoke の refcheck の対象外なのでこの形で書いてよい）、環境変数は `docs/configuration.md`、やりたいこと別の入口は `docs/guide.md` にある、と書く。
  - 0節：人向けの内容なので基本はそのまま（コマンド・使う場面・モデルの選び方）。
  - 1節：コマンド、質問があれば会話で答えること、モデルの選び方、粒度の基準へのリンク（`docs/vault-spec.md` 8節）を残す。ブランチを切る・planner が票を作る・承認してコミットする流れは1〜2行の要約と `.claude/skills/plan/SKILL.md` へのリンクにする。
  - 2節：人が承認のコマンドを打たないこと、計画の中身は PR で確認すること、直したい時は止めて指示する／PR の段階ならマージせず指示すること、を残す。log に追記する行の形（`draft→approved` の行）と `plan_guard.py` の検出は削り、`docs/vault-spec.md` 7節・10節へのリンクにする。
  - 3節：`###` の小見出しで「対話で回す」「無人で回す」「PR をマージする」程度に分けてよい。
    - 対話：`/run` は自分のブランチの承認済み計画の取れるタスクを無くなるまで処理し、全タスクが done になったら PR を作る（「1件処理して報告。続けて呼べば次へ」は古いので書き換える）。
    - 無人：`python3 scripts/run_unattended.py` を cron・CI から定期実行すること、素の `claude -p "/run"` を直接呼ばないこと、初回は対象フォルダで一度 `claude` を対話起動してフォルダを信頼すること、タイムアウトは cron・CI のログ（標準エラー）で分かること、止まった後は次回の `/run` が続きから再開すること、を残す。環境変数の箇条書き（`HARNESS_RUN_CMD`・`HARNESS_RUN_TIMEOUT`・`HARNESS_STRICT_STOP`・`HARNESS_MAX_ATTEMPTS`）は1行にまとめて `docs/configuration.md` へのリンクにする（変数名を挙げるのはよいが、意味・既定値の説明は書かない）。SIGTERM・SIGKILL・終了コード・`HARNESS_STRICT_STOP` の詳しい動きは削り、`docs/vault-spec.md` 14節へのリンクにする（T-01 で移し済み）。再開の詳細は `.claude/skills/run/SKILL.md` 手順2へのリンク。
    - 完了時の流れ（計画票の done・PR 本文への記録・取り出し・`scripts/purge_plan.sh` での除去・`vcs_finish.sh` が `gh api`／`glab mr create` を呼ぶこと）は1〜2行の要約と `.claude/skills/run/SKILL.md` 手順7へのリンクにする（同じ内容が手順7と `docs/vault-spec.md` 1節にある）。
    - PR のマージ：人が内容を確認して通常のマージ操作でマージすること、ホスティング無しは案内された `git merge --no-ff` を人が実行すること、コンフリクトは計画のブランチ上で人が解決すること、エージェントはマージしないこと、マージ方式（スカッシュ推奨・GitHub の squash の既定コミットメッセージの設定・通常のマージも可）、マージ後に計画を調べる時は PR を見ること、は人の判断なので残す（`docs/vault-spec.md` 1節が「マージ方式の運用は `docs/runbook.md` 3節」と参照しているので3節から動かさない）。PR 本文に何が載るか・「タスク履歴」表の生成元は1行の要約と `docs/vault-spec.md` 1節へのリンクにする。
    - 振り返りの提案ファイル `vault/harness-improvements/<計画ID>.md`：人が見るもの（起票に失敗すると残る・対応する計画の中で削除する）として1〜2行で残し、詳細は `docs/vault-spec.md` 1節と `.claude/skills/run/SKILL.md` 手順8へのリンクにする。
- 4節以降と「困ったとき」は変えない（T-03 が変える）。runbook の中の「8 節の手順」「0 節と同じ」などの節参照は、指す節の内容が残る限りそのままでよい。
- 文体は今の runbook に合わせる（である調、パスはバッククォート）。存在しないパスをバッククォートで書かない（smoke の `(ref-1)` が検査する）。
