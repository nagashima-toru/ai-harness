# T-06 /run の手順に worktree の引き継ぎ・起動通知が普通という主従・PR テンプレートを入れる

## 目的
`.claude/skills/run/SKILL.md` を3点直す。(1) unblock 後の再着手で、`transition.py ... doing --resume-worktree` で blocked の worktree を引き継ぎ、creator にその worktree で続きを作らせる経路を足す（Issue #190）。(2) creator の呼び出しは起動通知で返るのが普通で、完了通知を待つ、という主従に書き改める（Issue #191 の3）。(3) 手順7の PR 本文で、PR テンプレートの見出しを先に埋めてからハーネスの記録を付ける（Issue #191 の2）。あわせて `.claude/agents/creator.md` に、渡された worktree で続きを作る時のやり方を足す。

## 入力
- `.claude/skills/run/SKILL.md`（早見表・終了コードの表・手順2・手順3・手順7）
- `.claude/agents/creator.md`（入力・読むもの・手順・git）
- `scripts/transition.py`（T-02 で足した `--resume-worktree`。先頭の docstring：終了コード5・標準出力の `path=`・`branch=`・`plan_head=`）

## 成果物

## 決定済み
- (1) 引き継ぎ（run/SKILL.md）：
  - 早見表に「unblock 後の再着手（手順2。todo→doing。1 id ずつ）」の行として `python3 scripts/transition.py <計画ID> <id> doing --resume-worktree` を足す。終了コードの表に、行頭が `| 5 | 引き継げなかった` の行を1行足し、次の行動を「何も変えていない。その id を通常の着手（複数 id の todo→doing）に回す。記録行の worktree が残っていれば破棄せず、完了報告に `git worktree list` の出力を添えて人に知らせる」とする
  - 手順2の着手（今の 2.5）：選んだ行のうち、`vault/log/<計画ID>.md` にその id の記録行（`<id> worktree path=`）がある行は、まず1 id ずつ（1回の Bash に1回）`--resume-worktree` を呼ぶ。終了コード0ならその id を「引き継ぎ」として、標準出力の `path=`・`branch=`・`plan_head=` を控える。5なら通常の着手に回す。1なら今の終了コード1と同じく人に報告して止める。残りの id を今どおり1回の todo→doing で着手する
  - 手順3：引き継いだ id の `PLAN_HEAD` は、手順3の1で取る HEAD ではなく、`--resume-worktree` の標準出力の `plan_head` を使う（review・blocked・done の `--plan-head` に渡す）。worktree のパス・ブランチ名も標準出力の値を使う（手順3の4）。手順3の5の分岐元の確認はそのまま行う
  - 手順3の2：引き継いだ id の creator は `isolation: "worktree"` を付けずに呼び、prompt を `<計画ID>/<id> の成果物を作ってください。作業する worktree: <パス>` にする（この文字どおり。`<パス>` は控えた path）。`CREATOR_MODEL` の扱い・`run_in_background` の指定は通常の呼び出しと同じ
  - 手順2の中断からの再開（`doing`・`review` の行）と「ハング時の復旧」は変えない
- (2) 起動通知（run/SKILL.md の手順3の2）：creator の呼び出しは `run_in_background: false` を指定しても起動通知で返るのが普通である、という主従に書き改める（`起動通知で返るのが普通` をこの文字どおり含める）。起動通知で返ったらターンを終えて完了通知を待ち、完了通知が来るまで手順4に進まない。完了報告がそのまま返った時（同期で返った時）は手順4へ進む。待っている間の停止で stop_gate が「待機中なら問題ありません」の理由でブロックしても、そのままターンを終えて待ってよい、と書く。今の「完了を同期的に待つ（後続の手順4のreview化・手順6のverdict判定が呼び出し結果に依存するため）」の文は削る。起動通知の見分け方・複数タスクで一部だけ起動通知で返った時の扱い・ハングの判定（10分）は残す。手順5の verifier の呼び出しの記述は変えない
- (3) PR テンプレート（run/SKILL.md の手順7の5、本文ファイル）：本文ファイルの先頭に、導入先の PR テンプレートの見出しを先に埋め、その後に今のハーネスの記録（計画 ID の1行と `pr_body.py` の出力・`## verifier の指摘`・`plan_record.py` の出力・`## 取り出した情報`）をこの順で付ける（`テンプレートの見出しを先に埋め` をこの文字どおり含める）。テンプレートの探し方：GitHub は `.github/PULL_REQUEST_TEMPLATE/` 配下の複数のテンプレート、無ければ既定の1つ（`.github/` 直下・リポジトリ直下・docs ディレクトリのいずれかにある pull_request_template.md）。GitLab は `.gitlab/merge_request_templates/` 配下。テンプレートが無ければ今のまま（ハーネスの記録だけ）。複数ある時の選び方は汎用に書く：PR の差分に含まれるファイルの種類（コード・文書・設定など）と、各テンプレートの名前・冒頭の説明を照らして最も合う1つを選び、決められなければ既定のテンプレート、それも無ければ一覧の先頭を使う。特定のドメインや言語の判断基準（例：「アプリのコードを含むなら」）は書かない（`docs/vision.md` の原則7）。テンプレートの見出しは、計画のゴール・タスク表・verifier の指摘から埋め、埋められない見出しは「該当なし」と書く。チェックボックスは確かめたものだけに印を付ける
- (3) の補足：`docs/pull_request_template.md` のように `docs/`・`scripts/`・`vault/`・`.claude/` で始まる存在しないパスをバッククォートで書かない（smoke の `(ref-1)` が NG になる）。`.github/`・`.gitlab/` で始まるパスはバッククォートで書いてよい（`(ref-1)` の検査の対象外）
- (3) の補足：smoke の `(run-skill-4)`・`(run-skill-5)` は手順7の中の文字列の出現順（`git add vault/plans/<計画ID>.md` → … → `bash scripts/vcs_finish.sh`、`## verifier の指摘` → `## 計画の記録` → `## 取り出した情報`）を検査している。テンプレートの説明の文の中にこれらの文字列を順序を崩す位置で書かない
- creator.md：「入力」に、prompt に `作業する worktree: <パス>` があればそのパスの worktree で前回の続きを作ることを足す（`作業する worktree: ` をこの文字どおり含める）。その時は、ファイルは `<パス>/<相対パス>` の絶対パスで読み書きし、作業ディレクトリが要るコマンド（受け入れ基準の確認コマンドを含む）は同じ Bash 呼び出しの中で `cd <パス>` してから実行する。タスク票はその worktree の版を読む（unblock で直した「決定済み」「成果物」「受け入れ基準」が入っている）。「進捗」とすでにある成果物を読み、作り直さずに足りないところから続ける。ブランチを切り替えない・`git merge` などの git の操作をしない（計画ブランチの取り込みは transition.py が済ませている）。それ以外の手順・禁止は通常どおり
- 早見表・終了コードの表の列構成と既存の行は変えない（行を足すだけ）
