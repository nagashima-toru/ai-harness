# T-02 やりたいこと別の入口 docs/guide.md を書く

## 目的
利用者がやりたいことから必要な手順・設定に辿り着ける入口 `docs/guide.md` を作る。各項目は「やりたいこと（見出し）」「すること（コマンドや設定の最小例）」「詳しく（`docs/install.md`・`docs/runbook.md`・`docs/configuration.md` の節へのリンク）」の形にする。

## 入力
- `vault/designs/D-20261011-user-guide.md` の「決定事項」とフェーズ2
- `docs/install.md`・`docs/runbook.md`・`docs/configuration.md`（リンク先の節の見出しを確かめる）
- `scripts/smoke.sh` の `guidecheck()`（T-01 で足した書式の検査）
- 本票の「決定済み」

## 成果物
- `docs/guide.md`（1ファイル。新規）

## 決定済み
- ファイルの形：先頭に `# やりたいこと別ガイド`、続けて1〜3行の前書き（この文書は入口で、手順の本文はリンク先にあること。環境変数の設定のしかた（`export`・`env 変数=値 …`・`.claude/settings.json` の `env`）は ``[`docs/configuration.md`](configuration.md) の「設定のしかた」`` を見ること）。その後に11項目を下の順で `## ` の見出しで並べる。`## ` の見出しはこの11個だけにする（ほかの `## ` の節を作らない。`### ` も使わない）
- 各項目の書式（T-01 の guidecheck が検査する）：
  - `## <見出し>` の次に、1〜2文の補足（任意）
  - `すること：` で始まる行と、その直後にコードブロック1つ（```` ```bash ```` か ```` ```json ```` か ```` ```text ````、1〜3行）。1項目につきコードブロックは1つだけ
  - `詳しく：` で始まる行を1行。リンクは ``[`docs/<ファイル>.md`](<ファイル>.md) の「<節名>」`` の形で、節名はリンク先の見出し行から先頭の `#` と空白を除いた文字列そのまま。複数は `・` で区切る。アンカー（`#…`）は付けない（日本語の見出しのアンカーは表示環境で変わり、フェーズ3で節を変えるため）
  - 環境変数は本文に `` `HARNESS_…` `` のようにバッククォートで書く
- 手順の本文は重ねて書かない。最小例（1〜3行）と1〜2文の補足だけを載せ、詳細はリンク先に任せる
- 11項目の見出し・最小例・詳しく（節名は今の実ファイルの見出しで、実在を確かめ済み）：
  1. `## 初めて使う（インストールして最初の PR まで）`：例 `bash /path/to/ai-harness/scripts/install.sh /path/to/your-project`・`bash scripts/smoke.sh`・`/plan <ゴール>`。補足に、PR ができたら人が確認してマージすること。詳しく：install.md「パターン1: まっさらな環境にインストールする」・install.md「パターン2: 既存リポジトリに追加する」・install.md「インストール後の次の一歩」・runbook.md「1. ゴールを入れる」
  2. `## 大きなゴールを設計してから進める`：例 `/design <ゴール>`。補足に、できた `vault/designs/D-<YYYYMMDD>-<スラッグ>.md` のフェーズのゴール文を1つずつ `/plan` に渡すこと、強いモデルのセッションで実行すること。詳しく：runbook.md「0. 大きなゴールは先に設計する」
  3. `## main 以外のブランチをベースにする`：例 `.claude/settings.json` の `"env": { "HARNESS_BASE_BRANCH": "develop" }`（json）。補足に、未設定か空なら `main`。詳しく：install.md「main 以外のブランチをベースにする（任意）」・configuration.md「利用者が設定する変数」
  4. `## クラウドセッション（push 先が指定される環境）で使う`：例 `env HARNESS_PUSH_BRANCH=<指定ブランチ> bash scripts/vcs_finish.sh`。補足に次の3点を書く。(a) エージェントに頼むこと：`/plan <ゴール>` を打ち、実行環境が指定した push 先のブランチ名を伝える（`HARNESS_PUSH_BRANCH` が環境変数に無ければ、オーケストレーターが `env HARNESS_PUSH_BRANCH=<指定ブランチ> …` で `/plan`・`/design` の開始条件の確認と `vcs_finish.sh` に渡す）。(b) `HARNESS_PUSH_BRANCH` で指定ブランチに push する方法：ローカルでは `work/<計画ID>` で作業し、push 先と PR の head が指定ブランチになる。(c) 許可して `work/…` に push する方法：実行環境が指定ブランチ以外への push を許すなら `HARNESS_PUSH_BRANCH` を設定せず、ベースブランチに切り替えてから `/plan` を打つ（設定せず指定ブランチの上で `/plan` を打つと、開始条件を満たさず止まる。`.claude/skills/plan/SKILL.md` 手順2）。push 先と PR の head は `work/<計画ID>` になる。詳しく：runbook.md「10. push 先が決められている環境（クラウドセッション）」・configuration.md「利用者が設定する変数」
  5. `## 安いモデルで creator を回す`：例 `HARNESS_CREATOR_MODEL=haiku claude`。補足に、セッションの起動時に設定すること（起動後に変えたら起動し直す）、verifier・planner のモデルは変わらないこと。詳しく：runbook.md「8. creator のモデルを比べる」・configuration.md「利用者が設定する変数」
  6. `## 無人で回す`：例 `python3 scripts/run_unattended.py`・`env HARNESS_RUN_TIMEOUT=7200 python3 scripts/run_unattended.py`。補足に、cron・CI から定期実行すること、`HARNESS_RUN_CMD`・`HARNESS_STRICT_STOP`（ラッパー経由では未設定なら `1`）も効くこと、初回は対話で起動してフォルダを信頼しておくこと。詳しく：runbook.md「3. キューを回す」・configuration.md「利用者が設定する変数」
  7. `## blocked に答えて再開する`：例 `/plan unblock <計画ID> <id> [回答]`。補足に、計画票のタスク表の `question` を読んでから答えること、1回で1行だけ解除すること、続けて `/run` で再開すること。詳しく：runbook.md「4. blocked に答えて戻す」
  8. `## 再試行の上限・並列数を変える`：例 `export HARNESS_MAX_ATTEMPTS=5`・`export HARNESS_MAX_PARALLEL=1`。補足に、どちらも既定 `3`、変えたらセッションを起動し直すこと。詳しく：configuration.md「設定のしかた」・configuration.md「利用者が設定する変数」
  9. `## ルールを足す`：例（text）`vault/rules/common/<名前>.md` と `vault/rules/creator/<名前>.md` に置く形を2行で示す（それぞれ全員に渡す・creator だけに渡す）。補足に、受け入れ基準からルールファイルを名指しすると verifier がそれを根拠に判定すること。詳しく：runbook.md「6. ルールを足す」
  10. `## ハーネスを更新する・取り外す`：例 `bash /path/to/ai-harness/scripts/install.sh --update /path/to/your-project`・`bash scripts/uninstall.sh /path/to/your-project`。補足に、編集したファイルは上書き・削除されず `skip (edited)` と報告されること。詳しく：install.md「ハーネスを更新する（2回目以降）」・install.md「アンインストール」・runbook.md「7. ハーネス自体の更新を取り込む」
  11. `## マージ済みの計画を片づける`：例 `bash scripts/purge_plan.sh --merged --list`・`bash scripts/purge_plan.sh --merged --report`・`bash scripts/purge_plan.sh --merged --apply`。補足に、`--apply` は人だけが実行すること、`--report` を見て Issue 化してから `--apply` すること、作業用のブランチで実行してコミット・PR にすること。詳しく：runbook.md「5. 一括削除の手順」
- 上の詳しくに挙げていない節を足してもよいが、`docs/install.md`・`docs/runbook.md`・`docs/configuration.md` の実在する節に限る（`README.md` や `docs/vault-spec.md` へのリンクは「詳しく」に入れない。ゴールが3文書へのリンクと定めているため）
- 本文のバッククォート内に `vault/`・`scripts/`・`docs/`・`.claude/` で始まるパスを書く時は、実在するパスか、`<…>`・`*`・空白を含む雛形にする（`(ref-1)` が検査する。`vault/rules/` 配下は検査されない）
- 既存の `docs/install.md`・`docs/runbook.md`・`docs/configuration.md`・`README.md` は変えない（README のリンクは T-03、runbook の整理はフェーズ3）
- `scripts/install.sh` の配布対象に guide.md を足さない（設計文書の決定事項。導入先の docs を増やさない）
