# T-0007 scripts/rules.sh を新規作成し smoke.sh にケースを追加する

## 目的
役割名（`creator`/`verifier`/`planner`）を受け取り、`vault/rules/common/` とその役割ディレクトリの `*.md` を決定的順序（ファイル名順）で列挙する `scripts/rules.sh` を作る。作成エージェント・verifier・planner・テストが同じ出力を使う読み込みの一本化ポイント。

## 入力
- `docs/vault-spec.md`「12. ルール（vault/rules/）」節（正本。ディレクトリ構成・振り分け・読み込み順が定義済み）
- `docs/roadmap-rules-extension.md`「## ② ルール解決スクリプト scripts/rules.sh」節（`/plan` に渡した文そのもの・受け入れ基準の候補・決定済みの叩き台。そのまま使ってよい）
- `vault/rules/{common,creator,verifier,planner}/`（既存。現時点では `.gitkeep` のみで `*.md` は無い。P-006/T-0006 で作成済み）
- `scripts/smoke.sh`（既存。フックの動作検証スクリプト。末尾に新しい節を追記する。既存の `TMP`（`mktemp -d` で作られる一時ディレクトリ）と `PASS_N`/`FAIL_N` カウンタをそのまま使えばよい）
- `.claude/hooks/agent_write_guard.py`（`CLAUDE_PROJECT_DIR` の解決方法の実例。`os.environ.get("CLAUDE_PROJECT_DIR") or ...` と同じ考え方でよい）

## 成果物
- `scripts/rules.sh`（新規ファイル。1関数構成でよい）
- `scripts/smoke.sh` への追記（末尾に「== rules.sh ==」節を追加。既存の行は変更しない）

## 受け入れ基準
- `vault/rules/` が無い（または common/役割ディレクトリに `*.md` が無い）状態で `bash scripts/rules.sh creator` が無出力・exit 0 になる（確認コマンド：`CLAUDE_PROJECT_DIR=<空のtmpdir> bash scripts/rules.sh creator; echo "out=[$(CLAUDE_PROJECT_DIR=<空のtmpdir> bash scripts/rules.sh creator)] rc=$?"` で出力が空・rc=0）
- `common/` と `creator/` にそれぞれ2ファイルずつ置いた状態で `bash scripts/rules.sh creator` を呼ぶと `common/` のファイル（ファイル名順）→ `creator/` のファイル（ファイル名順）の順で列挙される（smoke.sh ケース (a) が ok）
- 同じ状態で `bash scripts/rules.sh verifier` を呼ぶと出力に `creator/` を含む行が無い（smoke.sh ケース (b) が ok）
- 同じ状態で `bash scripts/rules.sh planner` を呼ぶと出力に `common/` を含む行はあるが `creator/`・`verifier/` を含む行は無い（smoke.sh ケース (c) が ok）
- 引数が無い、または `creator`/`verifier`/`planner` 以外（例：`bash scripts/rules.sh foo`）だと標準エラーに usage を出し exit 2 になる（smoke.sh ケース (e) が ok）
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含み、pass 件数が既存（31。`bash scripts/smoke.sh` 実行前の現行値）より増えている

## 決定済み
- 出力は相対パス（`vault/rules/<dir>/<file>.md` の形）のみ。ファイル内容を `cat` して連結しない。読む側（run-queue・verifier・planner）が個別に Read する
- 列挙には `find` を使わず glob（`for f in "$dir"/*.md; do ... done`）を使う。サブディレクトリは辿らない
- グロブがヒットしない場合に `*.md` という文字列そのものが列挙されないよう `shopt -s nullglob` を使う
- ファイル名順は環境ロケールに依存させない。スクリプト内で `LC_ALL=C`（または `export LC_ALL=C`）を設定してから glob を展開する
- ルート解決は `CLAUDE_PROJECT_DIR` 環境変数があればそれを最優先。無ければ `cd "$(dirname "$0")/.." && pwd`（スクリプト自身の親の親、つまりリポジトリルート）で求める
- usage メッセージの文面は自由。「標準エラーに出る」「exit 2」の2点だけを満たせばよい
- `vault/rules/` ディレクトリ自体が無い場合、`[ -d "$dir" ] || return 0`（または同等の早期リターン）で無出力 exit 0 にする。エラー扱いにしない
- `scripts/smoke.sh` の既存節（`== stop_gate.py ==`／`== agent_write_guard.py ==`／`== todo_guard.py ==`）は変更しない。新しい「== rules.sh ==」節は既存の `TMP`（`trap 'rm -rf "$TMP"' EXIT` で自動削除される）配下に `vault/rules/` を作って使い、テスト後は次のケースのために `rm -rf "$TMP/vault/rules"` などでリセットしてよい
- smoke.sh 内でのテストファイル名はケース (a) の順序が一意に判定できるよう、ファイル名順で異なる結果になる2つ以上の名前（例：`a-*.md` と `b-*.md`）を使うこと
- ケース (d)「空なら無出力 exit 0」は「`vault/rules/` を作らない、または作っても `*.md` が無い」状態で確認する。ケース (a)〜(c) の後にテスト用ディレクトリをリセットしてから確認してよい
- このタスクでは `scripts/rules.sh` を呼び出す側（run-queue・verifier・planner のエージェント定義）は変更しない。呼び出し側の追加は別タスクで行う

## 進捗
- `scripts/rules.sh` を新規作成。`LC_ALL=C` 固定、`shopt -s nullglob` で glob 展開、`CLAUDE_PROJECT_DIR` 優先でルート解決、`common/` → 役割ディレクトリの順で列挙
- `scripts/smoke.sh` に `RULES_SH` 変数と「== rules.sh ==」節（(a)〜(e) 6ケース）を追加。既存節は変更していない
- 受け入れ基準6件の確認コマンドをすべて実行し通過（未配置時は無出力・rc=0、smoke.sh ケース(a)(b)(c)(e)全て ok、`bash scripts/smoke.sh | tail -1` は `smoke: pass=37 fail=0`。既存31件より6件増加）
- `chmod +x` は権限で拒否されたため、`scripts/rules.sh` に実行ビットは付けていない（`bash scripts/rules.sh ...` の呼び出し方は install.sh 複製の既存ファイル（例：smoke.sh）と同様に動作確認済み）
