# ゴール
verifier が書く `vault/verdicts/<id>.json` の各 criteria の `note` に、確認に使ったコマンド（または確認方法）と出力の要点を必ず残す。コマンドが実行できなかった場合はその旨と代替の確認方法を note に書く。

## 分割方針
「仕様とプロンプトの更新（契約）」の1タスクにする。note が実際に埋まることの確認は、このタスク自身を run-queue が処理した時に更新後の verifier が書く `vault/verdicts/T-0002.json` で行う（受け入れ基準6件すべての note が埋まっていれば目的達成）。
当初は「T-0001 を再検証する」タスク（T-0003）を置いたが取り下げた。T-0001 の受け入れ基準は「README の差分が未コミット」であることを前提にしており、README はコミット済みのため再検証は必ず FAIL になる。done のタスクに FAIL の verdict を残すのは状態を汚すだけで意味がない。
verdict のスキーマ（トップレベルキー）や stop_gate.py・todo.md の形式・verifier のツール制限には触れない。

## タスク一覧（順序・依存・各タスクの受け入れ基準の要約）
| 順 | id | after | title | 受け入れ基準の要約 |
|---|---|---|---|---|
| 1 | T-0002 | - | verdict.json の note 要件を仕様とverifierプロンプトに追記 | vault-spec.md 第7節とverifier.mdにnote要件（確認コマンド・出力要点・代替手段）が明記され、スキーマ／stop_gate.py／todo.md形式／verifierのtools行は無変更 |

確認方法：T-0002 が done になった時点で `python3 -c "import json;c=json.load(open('vault/verdicts/T-0002.json'))['criteria'];assert all(len(x['note'].strip())>=20 for x in c)"` が例外なく終了すれば、ゴールの「note が必ず入る」は満たされている。

## 計画の受け入れ基準
- 各タスクに成果物と受け入れ基準が1つずつある
- 依存に循環がない
- 1タスクが1コンテキストで終わる粒度である
