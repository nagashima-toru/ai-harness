# T-06 宣言外ファイル検査の取得方法を git diff --name-only main...HEAD に直す

## 目的
T-01 で追加した宣言外ファイル検査は変更ファイル一覧の取得に `git status --porcelain` を使っているが、
`vault/rules/creator/git-workflow.md` が「作業ステップごとにコミットする」と定めているため、verifier が
動く時点では作業ツリーがクリーンで、この検査は何も検出できない。取得方法をブランチ分岐点からの差分に
直し、コミット済みの変更も検出できるようにする。

## 入力
- `vault/rules/verifier/verifier.md`（T-01 で追加した宣言外ファイル検査のブレット。改訂対象）
- `vault/rules/creator/git-workflow.md`（「コミットのタイミング：作業ステップごと」の記述。この欠陥の原因）
- `vault/verdicts/P-20260920-verifier-scope/T-01.json`（`reasons` が空で、検査が働いていない実例）

## 成果物
- `vault/rules/verifier/verifier.md`（宣言外ファイル検査のブレット1つの改訂）

## 受け入れ基準
- 変更ファイル一覧の取得が `git diff --name-only main...HEAD` になっている。確認：
  `grep -cF 'git diff --name-only main...HEAD' vault/rules/verifier/verifier.md` が1
- `git status --porcelain` を変更ファイル一覧の取得手段として指示する記述が残っていない。確認：
  `grep -c 'git status --porcelain' vault/rules/verifier/verifier.md` が0
- 除外リスト4項目が改訂後も残っている。確認：`grep -cF '計画票（\`vault/plans/<計画ID>.md\`）' vault/rules/verifier/verifier.md`、
  `grep -cF 'タスク票の「進捗」' vault/rules/verifier/verifier.md`、`grep -cF '\`vault/log/<計画ID>.md\`' vault/rules/verifier/verifier.md`、
  `grep -cF '\`vault/verdicts/\` 配下' vault/rules/verifier/verifier.md` がそれぞれ1以上
- 既存の「やらないこと」節のブレット数が7のまま変わっていない。確認：
  `sed -n '/\*\*やらないこと\*\*/,/^## 確認方法/p' vault/rules/verifier/verifier.md | grep -c '^- '` が7
- ファイルが100行以内に収まっている。確認：`wc -l < vault/rules/verifier/verifier.md` が100以下

## 決定済み
- T-01 で追加した2つ目のブレット（宣言外ファイル検査）の先頭部分だけを差し替える。以下の文面をそのまま
  使ってよい（意味を変えない範囲で言い回しの調整は可）。
  `- \`git diff --name-only main...HEAD\` でブランチ分岐点からの変更ファイル一覧を取得し、タスク票の「成果物」に書かれていないファイルが含まれていないかを確認する。creator は作業ステップごとにコミットするため、verifier が動く時点では作業ツリーはクリーンで \`git status --porcelain\` では何も見えない。含まれていた場合は該当行（無ければ最後の基準行）の \`note\` に対象ファイルを書き、同じ文を \`reasons\` にも入れる（\`ok: false\` にはしない。FAIL にはしない）。ただし次は宣言外でも正常として扱い記録しない：計画票（\`vault/plans/<計画ID>.md\`）・タスク票の「進捗」・\`vault/log/<計画ID>.md\`・\`vault/verdicts/\` 配下。`
- 1つ目のブレット（基準の妥当性判定）は変更しない。
- 「やらないこと」節・「確認方法」節は変更しない。
- `main` がデフォルトブランチである前提で書いてよい（このリポジトリのデフォルトブランチは `main`）。
- このファイルは `vault/rules/` 配下のため、`doing`/`review` 中は `agent_write_guard.py` が書き込みを拒否する。
  このセッションではリモート実行で `HARNESS_ALLOW_RULES_WRITE` を渡せないため、人が承認済みの回避策
  「`todo` のうちに内容を編集し、その後 `doing` にする」を使う。
