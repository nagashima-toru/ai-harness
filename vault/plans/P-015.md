# ゴール
planner / creator / verifier の責務を `vault/rules/` に標準ルールとして定義し、インストール先にも配布する。目的は各サブエージェントの出力品質の向上。内容は「責務＋入出力のつながり」に加えて、このリポジトリで実際に起きた失敗を「やらないこと」として書く。

書く場所（4ファイル、いずれも `vault/templates/rule.md` の3見出し・100行以内）：
- `vault/rules/common/roles.md`：誰の出力が誰の入力になるかの差分だけ（既出は参照に留める）
- `vault/rules/planner/planner.md`
- `vault/rules/creator/creator.md`
- `vault/rules/verifier/verifier.md`

あわせて `scripts/install.sh` の複製対象に4ファイルを加え、`README.md`（拡張ポイント節）・`docs/vault-spec.md`（第12節）・`vault/rules/README.md` の「ハーネス本体はルールを同梱しない」という記述を「役割定義の標準ルールだけは同梱し、ドメイン固有のルールはインストール先で書く」に直す。

## 分割方針
最大の制約は `.claude/hooks/agent_write_guard.py` の改ざん防止判定で、`doing` / `review` 中は `vault/rules/` への書き込みが agent_type を問わず拒否されること。ルール本体を書くのは run-queue の作成エージェント（常に `doing`）なので、そのままでは1ファイルも書けない。

そこで **T-0018（契約タスク）でフック側に人だけが使える明示解除の口を作り**、以降のルール執筆タスクをすべてそれに依存させる。解除は環境変数 `HARNESS_ALLOW_RULES_WRITE=<doing のタスク ID>` を人が起動時に与えた時だけ効く（フックは Claude Code プロセスの環境を継承するため、作成エージェントが Bash 内で `export` しても届かない＝実質的に人しか解除できない）。「人がフックを一時的に外す」方式は、settings.json やフック本体を一時改変する事故が起きやすいため採らない。

ルール4本は互いに独立なので、`common/` を先に確定させ（他の3本がそこを参照する）、役割別3本は並行可能な依存にする。配布と文言修正は4本が揃ってから1タスクにまとめる（install.sh が実在パスを列挙するため）。

## 計画の受け入れ基準

- 依存に循環がない（T-0018 → T-0019 → {T-0020, T-0021, T-0022} → T-0023）

## 次フェーズの候補（このプランでは票を起こさない）
- 標準ルールを実際に効かせた通し検証（一時 install 先で `claude -p "/run-queue"` を回し、creator の進捗と verdict の note に標準ルールのパスが出ることを確認して `docs/decisions.md` に記録）
- インストール先が編集済みの標準ルールへ、ハーネス側の更新を届ける手段（`copy_if_absent` では届かない。差分提示 or バージョン付きファイル名）
- `docs/runbook.md` に「標準ルールを更新する手順」（`HARNESS_ALLOW_RULES_WRITE` の使い方を含む）を追記する

## 決定事項（人の回答。2026-09-18）
1. 改ざん防止の解除方式は環境変数 `HARNESS_ALLOW_RULES_WRITE=<doing のタスク ID>` とする。人が起動時に指定し、ID が一致する時だけ解除される。代替案（人が手で書く／作業中だけフックを外す）は採らない。恒久的な抜け道がコードに残ることは了解済み
2. その結果 T-0019〜T-0023 は起動時に環境変数が必要で、無人 cron では流れない。この5件は人が `HARNESS_ALLOW_RULES_WRITE=T-00xx` を付けて1件ずつ回す
3. ルールのファイル名はディレクトリ名と揃える：`common/roles.md`・`planner/planner.md`・`creator/creator.md`・`verifier/verifier.md`
4. 標準ルールとドメイン固有ルールは同じディレクトリに同居させる。`rules.sh` は変更しない（サブディレクトリは辿らないまま）
