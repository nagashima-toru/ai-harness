# T-02 vcs_finish.sh が引数なしの時に計画のタスク履歴を PR/MR 本文に載せる（smoke.sh にケース追加）

## 目的
`bash scripts/vcs_finish.sh` を引数なしで実行した時、現在のブランチの計画が見つかれば、T-01 の `scripts/pr_body.py` の出力を PR/MR 本文に渡す。見つからない時・引数がある時・ホスティング無しの時は今の動作のまま残す。

## 入力
- `scripts/vcs_finish.sh`（現行）
- `scripts/pr_body.py`（T-01 の成果物）
- `scripts/smoke.sh` の `== vcs_finish.sh ==` 節（`VF_BIN` の gh/glab スタブ、`expect_vf`）
- `docs/vault-spec.md` 3節（ブランチ名は計画 ID を英小文字にして `work/` を付ける）

## 成果物
- `scripts/vcs_finish.sh` の変更（あわせて、その動作を確かめる `scripts/smoke.sh` の vcs_finish 節へのケース追加。この2ファイル以外は変えない）

## 受け入れ基準
- `bash -n scripts/vcs_finish.sh` が終了コード0
- `bash scripts/smoke.sh 2>&1 | tail -1` が `fail=0` で終わる
- `bash scripts/smoke.sh 2>&1 | grep -c 'ok   (vcs_finish) '` の出力が `4`（既存の4ケース：計画の無いブランチの引数なし `--fill`/`--fill --yes` と、引数ありの素通しが変わらない）
- `bash scripts/smoke.sh 2>&1 | grep -c 'ok   (vcs_finish-body) '` の出力が `3`（決定済みの3ケース）
- `grep -c 'HARNESS_PR_BODY_FILE' scripts/vcs_finish.sh` の出力が `0`（D-013 の環境変数を先取りしない）

## 決定済み
- 本文を使うのは「引数なし」かつ host が `github` か `gitlab` の時だけ。引数がある時は今どおりそのまま渡す。`none` の案内文・未知の host のエラーは変えない
- 計画の見つけ方：`git rev-parse --abbrev-ref HEAD` が `work/` で始まる時、残り（例：`p-20261006-pr-task-history`）と、`git rev-parse --show-toplevel` 配下の `vault/plans/*.md` のファイル名（`.md` を除く）を英小文字にしたものが一致する計画票を1つ探す（`tr '[:upper:]' '[:lower:]'` でよい）。計画 ID はファイル名（大文字のまま）。frontmatter の status は見ない（run は status を done にしてから呼ぶため）
- 本文は `python3 "<vcs_finish.sh と同じディレクトリ>/pr_body.py" "<計画ID>"` の標準出力（`$(dirname "$0")` で場所を決める）。計画が見つからない・`pr_body.py` が0以外で終わる・出力が空、のいずれかなら今の既定（`gh pr create --fill` / `glab mr create --fill --yes`）に戻す
- 計画が見つかった時の呼び方：GitHub は `gh pr create --title "<計画ID>" --body "<本文>"`、GitLab は `glab mr create --title "<計画ID>" --description "<本文>" --yes`。本文は変数で渡し、一時ファイルは作らない。`--fill` は付けない
- push（upstream が無い時の `git push -u origin`）の位置と、gh/glab が無い時の終了コード127は変えない
- 冒頭の使い方コメントに、引数なしで計画が見つかった時の挙動を1〜2行で足す
- smoke のケース名は `(vcs_finish-body) ` で始める（`expect_vf` の出力が `  ok   <name>` になるので、基準4の grep に当たる）。3ケース：
  1. github・計画あり・引数なし → スタブの記録の先頭4行が `pr` `create` `--title` `P-20990101-vf`、5行目が `--body`、本文に `| T-01 | ` で始まり `PASS (attempt=1) |` で終わる行と、`| T-02 | ` で始まり `| - | - |` で終わる行がある
  2. gitlab・計画あり・引数なし → 記録が `mr` `create` `--title` `P-20990101-vf` `--description` <本文> `--yes` の順
  3. github・計画あり・引数あり（`--title T --body B`）→ そのまま（記録が `pr create --title T --body B`）
- smoke のフィクスチャは既存の `VF_REPO` とは別の一時リポジトリ（例：`$TMP/vf_repo2`）に作る。既存の4ケースの前提（ブランチ `vfmain`、計画票なし）を変えないため。中身は、ブランチ `work/p-20990101-vf`、`vault/plans/P-20990101-vf.md`（タスク表に T-01 `done`・T-02 `todo` の2行）、`vault/verdicts/P-20990101-vf/T-01.json`（`"result": "PASS"`, `"attempt": 1`）、メッセージ `P-20990101-vf/T-01: done` のコミット。push を避けるため、既存と同じく `branch.<名前>.remote=.`・`branch.<名前>.merge` を設定する
- 本文は複数行なので、既存の `expect_vf`（記録全体の完全一致）で比べにくければ、記録の行ごとに確かめる別の小さな関数を足してよい。`PASS_N`/`FAIL_N` の数え方は既存に合わせる
