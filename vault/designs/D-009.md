# ゴール

このハーネス（ai-harness）が何のために存在し、何を目指し、何を目指さないかを1つの文書に固定する。現時点では README・docs/decisions.md・各設計文書に理念が分散して暗黙的に存在するだけで、「これはハーネスに入れるべきか」を将来判断する時の内規が無い。`docs/vision.md` にそれを書き、README「目的」節からリンクする。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| 目的・目指していることは新規 `docs/vision.md` に書き、README「目的」節の既存4行はそのまま残して末尾にリンクを1行追加する | 詳細な理念・非ゴールを独立文書に集約しつつ README の簡潔さを保つ。将来の `/design`・planner・人が参照しやすい場所に置く（人の回答） |
| 主な用途は将来のスコープ判断の内規とする。外部の採用者向けの訴求文書にはしない | 読み手は主に将来の自分・contributor・planner。「これはハーネスに入れるべきか／入れないべきか」を判断する時の基準として使う（人の回答） |
| 内容は理念・原則と非ゴールに絞り、ロードマップ（次に何をやるか）は含めない | ロードマップは時間で古くなり陳腐化する。恒久的に参照できる内容にとどめる（人の回答） |
| 非ゴールに「個人の私的ツールとして閉じたままでよい（マルチユーザー化・SaaS化・GUI化はしない）」を明記する | 現状は MIT で公開し `install.sh` で他リポジトリへのコード配布はするが、ホスティングサービス化はしていない。この前提を明文化し、将来変える時は本ドキュメント自体を更新する対象にする（人の回答） |

## フェーズ1 docs/vision.md の作成とREADMEからのリンク

### ゴール文

`docs/vision.md` を新規作成し、「目的」「原則」「非ゴール」の見出しでこのハーネスの理念を書く。「目的」にはこのハーネスが解決する問題（AI エージェントの成果物を別コンテキストの検証エージェントが受け入れ基準で採点し、PASS しない限り完了扱いにしない、状態をファイルに集約してセッション断でも再開できるようにする、等）を書く。「原則」には既に README・docs/decisions.md・vault-spec.md から読み取れる恒久的な方針（作成→検証の二段構成／状態はvault/のファイルに集約／5状態固定で変更は必ずログに残す／質問は着手前にまとめて聞き着手後はblockedで止める／人が最終決定権を持つ／ドメイン知識はvault/rules/の拡張点に分離する／1セッション=1計画=1ブランチ）を1件1行で列挙する。「非ゴール」にはマルチユーザー化・SaaS化・GUI化をしないこと、汎用のプロジェクト管理・タスク管理ツールになることを目指さないこと、Claude Code以外のランタイムへの対応を現時点では目指さないことを書く。README.md の「目的」節（既存4行のbulleted list）はそのまま残し、末尾に `docs/vision.md` へのリンクを1行追加する。

### 受け入れ基準の候補
- `docs/vision.md` が存在し、`^## 目的`・`^## 原則`・`^## 非ゴール` の3見出しをこの順で含む（`grep -n '^## ' docs/vision.md` で確認）
- 「原則」に列挙された各項目が、既存の README・docs/decisions.md・docs/vault-spec.md のいずれかの記述と矛盾しない（1件ずつ元の記述箇所を目視確認する）
- 「非ゴール」に、マルチユーザー化・SaaS化・GUI化を目指さない旨が明記されている（`grep -n -e 'マルチユーザー' -e 'SaaS' -e 'GUI' docs/vision.md` でいずれかがヒットする）
- README.md の「目的」節に `docs/vision.md` へのリンクが追加されている（`grep -n 'docs/vision.md' README.md` で確認）
- README.md の「目的」節にある既存4行の bullet の文言が変更・削除されていない（`git diff main -- README.md` で追加行のみであることを確認する）

### 決定済み
- `docs/vision.md` に frontmatter は付けない（`vault/designs/` の設計文書とは別系統の通常の docs ファイル）
- 「原則」「非ゴール」の各項目は簡潔な1行見出し＋必要なら1行の補足程度にする。理由の長い説明や具体的な実装への言及（特定のフック名・スクリプト名等）は書かない。原則は実装詳細ではなく方針を書く場所
- ロードマップ・次にやることのリストは書かない。書きたくなった場合は別の設計文書か `docs/decisions.md` を使う
- README「目的」節の既存4行は文言も順序も変更しない。リンクは既存4行の後に追加する独立した1行とする

## 今回やらないこと

- 将来的な多人数利用・OSS展開の是非そのものの検討：今回は「今は個人の私的ツールとして閉じたままでよい」という前提を非ゴールとして明文化するだけであり、方針転換の検討自体は必要になった時に別の設計文書で扱う
- `docs/decisions.md` や既存の設計文書（D-001〜D-008）の書き直し・整理：`docs/vision.md` は新規に理念を集約する場所であり、既存ログの遡及的な整理は範囲外
- ハーネスのロードマップ（次に実装する機能の一覧）の策定：原則・非ゴールのみを扱い、時間で古くなる情報は含めない
