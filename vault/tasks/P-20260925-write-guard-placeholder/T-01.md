# T-01 agent_write_guard: 山括弧プレースホルダー内の `>` をリダイレクト誤検知から除外する（issue #54）

## 目的
`.claude/hooks/agent_write_guard.py` の `PreToolUse:Bash` 判定が、`<n>`・`<計画ID>` 等の山括弧プレースホルダー（plan/task 票で慣習的に使われる表記）を含むだけの読み取り専用コマンドを、プレースホルダー内の `>` をシェルのリダイレクトと誤認して拒否する不具合（GitHub issue #54）を直す。実際のリダイレクト（`> file`・`>> file`）や `rm`/`git commit` 等の既存の破壊的操作検出能力は弱めない。

## 入力

- `.claude/skills/run/SKILL.md`（39行目に誤検知の実例 `` `- <日時> <id> doing→review attempt=<n>` `` がある。再現用の実コマンド例：`grep -n -A 5 "doing→review attempt=<n>" .claude/skills/run/SKILL.md`）
- `scripts/smoke.sh` の `== agent_write_guard.py ==` セクション（124〜227行目付近。`run_guard`/`expect_guard` ヘルパーと既存ケースの書き方の前例）

## 決定済み
- 根本原因（本タスク票作成時に planner 自身のセッションで再現・特定済み）：`BASH_WRITE_PATTERNS` のリダイレクト検出正規表現 `r"(^|[^<>])>{1,2}\s*(?!&)\S"` は、`<n>` のように「`<` で始まり `>` で終わる、`>` 直前が `<`/`>` 以外・直後が非空白かつ非 `&`」という形の山括弧プレースホルダーの閉じ `>` にもマッチする。さらに、これで `any(re.search(p, cmd) for p in BASH_WRITE_PATTERNS)` が真になった後、`extract_bash_write_targets()`（および `main()` 末尾の許可ディレクトリ判定で使う `re.findall(r">{1,2}\s*([^\s;&|]+)", cmd)`）が `<n>` の直後の1文字（例えば閉じクォート `"`）をダミーの書き込み対象として抽出してしまい、「全対象がリポジトリ外」「全対象が許可ディレクトリ配下」のどちらの許可条件も満たせず fail-closed で deny される。実際のリダイレクト（例：`> /tmp/foo.txt`）が同じコマンド文字列に別途あっても、ダミー対象が混入するとその許可判定ごと壊れる（`echo 'doing→review attempt=<n>' > /tmp/foo.txt` で実際に再現した）
- 対応方針は issue #54 の対応案2（`<...>` のペアで囲まれた区間内の `>` をリダイレクト候補から除外する）を採用する。対応案1（grep/rg 等のクォート引数内部を除外する方式）は、このリポジトリでの誤検知の実例がいずれも「プレースホルダー表記」由来であり、汎用的なシェルのクォート解析はスコープが大きくなりすぎるため採らない
- 実装は、コマンド文字列から `<[^<>\s]+>`（`<` と `>` の間に空白も `<`/`>` も含まない区間）にマッチする箇所を同じ文字数の空白に置換して返すヘルパー関数 `mask_angle_placeholders(cmd)` を1つ追加し、次の呼び出し箇所で素の `cmd` の代わりにこの関数の戻り値を使う：(1) `main()` の Bash 分岐で `any(re.search(p, cmd) for p in BASH_WRITE_PATTERNS)` を判定する箇所、(2) `extract_bash_write_targets(cmd)` の内部（または呼び出し前にマスク済み文字列を渡す）、(3) `main()` 末尾の許可ディレクトリ判定で使う `re.findall(r">{1,2}\s*([^\s;&|]+)", cmd)`。`targets_vault_rules()`・`targets_creator_denied_paths()` は同じ `BASH_WRITE_PATTERNS` ゲートを使うが、対象パスの一致条件が `vault/rules/`・`vault/plans/`・`vault/log/` という具体的な接頭辞であるため今回のダミー対象（1文字程度の断片）では誤って一致せず、この issue の false-deny は起きない（マスクしなくても正しく動く）。ただし一貫性のためこの2関数にもマスク済み文字列を使ってよい（必須ではない）
- deny() のエラーメッセージに表示するコマンド文字列（`cmd[:120]` 等）はマスク前の元の `cmd` を使う（人が読むエラーメッセージを不自然に空白だらけにしないため）。マスクは判定用の内部処理にのみ使う
- `mask_angle_placeholders()` はテキスト全体（`vault/rules/` パス判定用の `path_like` 抽出等）に無条件適用してよい。ただしこのタスクの受け入れ基準が要求するのはリダイレクト誤検知の解消と回帰の無さであり、`vault/rules/`・creator 拒否パスの判定ロジック自体を変更する必要はない
- `scripts/smoke.sh` の新規ケースは既存の `run_guard`/`expect_guard` ヘルパー（124〜130行目）をそのまま使い、`== agent_write_guard.py ==` セクション内（224〜227行目の `2>&1` ケースの近く）に追加する。ケース名に issue 番号や `placeholder` 等、誤検知修正のケースだと分かる語を含めること
- テストに使うプレースホルダーは issue #54 の実例（`attempt=<n>`）と、汎用性を示すため `<計画ID>` の2種類を含めるとよい（必須ではないが望ましい）
- 確認コマンドはパイプ・`&&`・コマンド置換を含む複合コマンドにしないこと（`vault/rules/planner/planner.md` の既存指針、issue #46・#48 由来）。本タスク票の確認コマンドはこの方針に沿って、リダイレクト（`>`/`<`）のみを使う単純なコマンドに分解済み。一時出力先は固定パス `/tmp/P-20260925-write-guard-placeholder-T-01-*` を使い、後片付けの `rm -rf` は前提にしない（同ファイル名を毎回上書きする運用でよい）
- `docs/vault-spec.md` 等の仕様書更新はこのタスクのスコープ外（挙動の修正であり仕様変更ではない）
