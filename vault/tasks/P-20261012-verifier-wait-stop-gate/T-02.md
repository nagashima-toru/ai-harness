## 決定済み
- run 手順5の1：「この呼び出しも `run_in_background: false` を指定し、完了を同期的に待つ（後続の手順6のverdict判定が呼び出し結果に依存するため）」を、「この呼び出しも `run_in_background: false` を指定する。指定しても、verifier の呼び出しも起動通知で返るのが普通である。」に置き換える（後半の文はこの文字どおり書く）。手順6の verdict 判定が verifier の完了に依存することは、下の箇条の「完了通知が来るまで手順6に進まない」で表す
- 手順5の1の下の箇条：先頭の「それでも Agent ツールの結果が起動通知（バックグラウンド起動）だった時は」を「Agent ツールの結果が起動通知（バックグラウンド起動）だった時は」にする（「それでも」を外す）。手順3の2の箇条と同じく「完了報告がそのまま返った時（同期で返った時）は手順6へ進む。」と「待っている間の停止で stop_gate が「待機中なら問題ありません」の理由でブロックしても、そのままターンを終えて待ってよい。」を足す。起動通知の見分け方・一部だけ起動通知で返った時の扱いの文は残す
- `docs/vault-spec.md` 9節の表の「verdict が無い、または task / attempt が不一致」の行の判定欄の末尾（「（判定は同じでブロックは変わらない。文面だけが変わる）」の前）に、「status が review の時は、理由に `待機中なら問題ありません` を含め、verifier の完了通知を待っているならそのままターンを終えて待つよう案内する文面になる」旨を足す。「status が review の時は」はこの文字どおり書く。表の列構成・他の行は変えない
- `docs/decisions.md`：表の末尾に1行足す。日付は `2026-10-12`、「何を」は「`stop_gate.py` の判定は変えず、review で verdict が無い・古い時の理由文にも「待機中なら問題ありません」と verifier の完了通知を待つ案内を入れる。run 手順5の verifier も「起動通知で返るのが普通」を主に書く（Issue #193）（P-20261012-verifier-wait-stop-gate）」、「なぜ」は「verifier も `run_in_background: false` で起動通知で返ることがあり（PR #192 の T-06）、「verifier を実行せよ」と読むと二重起動しうる。review・verdict なしは「verifier 実行中」と「verifier が中断して終わった」を区別できないのでゲートは緩めない（2026-10-10・2026-10-12 の人の選択と同じ）」の趣旨で書く。`Issue #193` はこの文字どおり書く
- 範囲の除外：`.claude/skills/plan/SKILL.md` の planner の呼び出しにも「それでも Agent ツールの結果が起動通知」の書き方があるが、このタスクでは変えない。Issue #193 は verifier の待ち（review・verdict なし）が対象で、planner の待ちは draft の計画で stop_gate がブロックしない（approved が0件なら許可）ため、二重起動の問題が起きないから。そのため受け入れ基準の「残っていない」の確認は `.claude/skills/run/SKILL.md` に限る
- `docs/runbook.md`・`docs/guide.md` には stop_gate の理由文や起動通知の扱いの記述が無いので触らない
- `.claude/hooks/stop_gate.py`・`scripts/smoke.sh` は T-01 で直し済みなので触らない。vault-spec に書く文面は T-01 で入った `stop_gate.py` の実際の理由文と食い違わないようにする
- smoke は1回およそ1分かかる。確認コマンドの5つ目と6つ目はそれぞれ smoke を実行する
