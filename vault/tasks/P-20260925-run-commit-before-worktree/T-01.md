# T-01 runスキル: worktree生成前に計画票・ログのコミットを明記

## 目的
`.claude/skills/run/SKILL.md` の手順2・手順4・手順6.3.2で、計画票・ログを更新した直後、次に creator/verifier を呼ぶ（worktree を新規作成する、または既存 worktree に `EnterWorktree` で入る）前に、その更新をコミットする旨を明記する。`isolation: "worktree"` の Agent 呼び出しは計画ブランチの**コミット済み** HEAD から分岐するため、未コミットのまま呼ぶと新しい worktree に反映されない（issue #50）。

## 入力
- `.claude/skills/run/SKILL.md`（修正対象）
- `vault/rules/common/git.md`（コミット運用の既存方針：作業ステップごとに小さくコミットする）
- `vault/plans/P-20260925-run-merge-uncommitted.md` / `vault/tasks/P-20260925-run-merge-uncommitted/T-01.md`（同一ファイル・同種の運用バグ修正を1タスクで完結させた前例。文体・粒度の参考にする）
- `vault/plans/P-20260925-sandbox-hang-timeout.md`（本タスクの発端になった事故の経緯）

## 決定済み
- 新しい手順番号（`## n.`）は切らない。既存の該当箇所（手順2の番号付きリストの末尾、手順4の段落末尾、手順6.3.2の該当項目）に一文・一項目を書き足す形にする。ゴール文の「対応方針」に記載の3箇所がそのまま挿入位置
- 手順2への追記位置：現在の番号付きリストの項目5（`本手順の中で連続してまとめて行う` で終わる文）の後に新しい項目6として追加する。内容の骨子：直前の一括反映（doing への状態更新＋ログ追記）をこの時点でコミットする。理由として「手順3で `isolation: "worktree"` を指定して creator を呼ぶと、その時点の計画ブランチのコミット済み HEAD から新しい worktree が分岐するため、コミットしておかないと今回の doing 反映が新しい worktree に含まれない」という趣旨を書く
- 手順4への追記位置：既存の段落（`doing→review attempt=<n>` の形で追記する、で終わる文）の直後に一文を足す。内容の骨子：この反映もこの時点でコミットする。理由として「手順5で verifier が対象タスクの worktree に `EnterWorktree` で入るため、コミットされていない変更はその worktree には反映されず verifier から見えない」という趣旨を書く
- 手順6.3.2への追記位置：`review→doing attempt=<n+1> 理由要約` を追記する旨の文の直後、かつ `discard_worktree.sh` で worktree を破棄する旨の文の直前（またはその文に続ける形）。内容の骨子：直前の状態変更（doing・attempt+1・ログ追記）がコミット済みであることを確認してから worktree を破棄する、という順序を明示する
- コミットのコマンド例を書く場合は `vault/rules/common/git.md` の運用（作業ステップごとに小さくコミットする）に沿った単発の `git add -A && git commit -m "..."` 程度でよい。厳密なコミットメッセージ書式は規定しない（受け入れ基準はコミットする旨の一文の有無だけを見る）
- 手順6.2（PASS 時の未コミット差分回収、`git status --porcelain` 〜 `creator 成果物の未コミット分をオーケストレーターが収集` の一文を含む段落）は一切変更しない。これは既存の別対応（`P-20260925-run-merge-uncommitted`）の範囲であり、本タスクの対象外
- `discard_worktree.sh` の実装、`vault/rules/creator/`・`vault/rules/verifier/`、`docs/vault-spec.md` は変更しない
- 「ハング時の復旧」節（手順3・5がハングした場合の別経路）は対象外。今回のゴールが指す `discard_worktree.sh` 呼び出しは手順6.3.2（FAIL 再試行）のものだけ
