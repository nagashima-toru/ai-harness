# ゴール

「done にできるのは attempt が一致する PASS の verdict がある時だけ」という中心の不変条件を、フックで機械的に守る。あわせて、run のオーケストレーターがプロンプトの手順として行っている状態遷移・log 追記・コミット・マージ・worktree の後始末を `scripts/transition.py` にまとめ、creator の差分が「成果物」に宣言した範囲に収まっているかを `scripts/diff_gate.py` で機械的に確かめてからマージする。今は、done の行を検査するフックが無く、creator が受け入れ基準やフックを書き換えた差分もそのままマージされうるうえ、log の日時がモデルの書いた値になっている。これらの穴をふさぐ。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| 「done の行には attempt が一致する PASS の verdict がある」ことを `plan_guard.py`（PostToolUse）と `stop_gate.py`（Stop）で検査する。状態遷移スクリプトは推奨の経路とし、Edit による計画票の直接の書き換えは拒否しない | 書き方を問わず「PASS の無い done」が残らないことが目的。書き方を縛ると `/plan approve`・`/plan unblock` の Edit との切り分けと Bash 経由の書き換えの検出が要り、ガードがまた複雑になる（人の回答） |
| 差分ゲートの違反は差し戻して再試行にする（doing のまま attempt+1、違反ファイルをタスク票の「進捗」と log に書き、worktree を破棄して creator を呼び直す）。上限に達したら blocked | うっかり触ったファイルなら creator が自分で戻せる。既存の FAIL の再試行と同じ形にそろえる（人の回答） |
| 差分ゲートは creator の完了直後、verifier の前に行う。そのため、worktree の未コミット分をオーケストレーターがコミットする時機も、今の「PASS の後」から「creator の完了直後」に移す | verifier が見る内容とマージされる内容を一致させる。違反時に verifier を呼ばずに済む。verifier がコマンドを実行して生じたファイルがマージに紛れ込まない（人の回答） |
| `.claude/hooks/`・`.claude/settings.json` などの変更は、タスク票の「成果物」に宣言があれば差分ゲートを通す | このリポジトリではフックが普通の成果物。宣言は planner が書き、計画の承認は人が行うので、人の承認を経た宣言の範囲だけが入る（人の回答） |
| 状態遷移は新設の `scripts/transition.py` で行い、log の日時はスクリプトが実時刻で書く | log の日時がコミット時刻より後になっている実例がある（ブランチ `work/p-20261004-hooklib-extract` のコミット `596470e`（18:35:06）に `18:39 T-02 todo→doing`、`1d3800b`（18:41:04）に `18:51 T-04 review→done`）。手順をプロンプトに書いてモデルに実行させる方式では守られない（調査に基づく設計判断） |
| 差分の判定は `scripts/diff_gate.py` が行い、タスク票は base（計画ブランチ側の `PLAN_HEAD`）の版で読む | creator はタスク票に書き込める（「進捗」を書くため）。branch 側の版で読むと、creator が「成果物」の宣言を自分で書き足せてしまう（調査に基づく設計判断） |
| `vault/plans/`・`vault/log/`・`vault/verdicts/`・`vault/rules/` 配下の変更は、「成果物」に宣言があっても違反にする | creator の差分から、状態・判定結果・ルールが計画ブランチへ入る経路を、宣言の書き方に関係なく塞ぐ（調査に基づく設計判断） |
| 自分のタスク票の変更は「## 進捗」節だけを許し、受け入れ基準などほかの節の変更は違反にする | 受け入れ基準は採点の基準そのもので、`vault/rules/` 以上に守る必要がある。今はどのフックも creator による書き換えを止めていない（調査に基づく設計判断） |
| `scripts/transition.py` は `.claude/hooks/_hooklib.py` を import して計画票・タスク表を読む（D-011 の「`scripts/` から `_hooklib.py` を使わない」を改める） | タスク表の解析規則の4つ目の複製を作らない。D-011 で共通化した理由と同じ（調査に基づく設計判断） |
| 承認（draft→approved）と blocked の解除は `transition.py` の対象にせず、今の `/plan` の Edit のままにする | スクリプトがコミットまで行うと、`plan_guard.py` が承認・解除の裏付けを検査する「HEAD と作業ツリーの比較」に当たらず、会話記録の検査を素通りする（調査に基づく設計判断） |
| `transition.py` は、現在のブランチが `work/<計画IDの英小文字>` の時だけ状態を変える | creator の worktree（ブランチ `worktree-agent-*`）や `main` から実行されても状態を変えないようにする（調査に基づく設計判断） |

## フェーズ1 done の行の verdict をフックで検査する

### ゴール文

`.claude/hooks/plan_guard.py`（PostToolUse）と `.claude/hooks/stop_gate.py`（Stop）に検査を1つ足す。自分のブランチの承認済み計画票のタスク表で status が `done` の行それぞれについて、`vault/verdicts/<計画ID>/<id>.json` が次の条件をすべて満たすかを確かめる。
- ファイルがある
- `task` が `<計画ID>/<id>`
- `attempt` がタスク表の値と一致する
- `result` が `PASS`
- 形式が正しい（`stop_gate.py` の既存の形式検査と同じ）

満たさない done の行があればブロックし、その行を review に戻して verifier を実行するよう指示する。`stop_gate.py` の `validate_verdict` は `.claude/hooks/_hooklib.py` に移して両方のフックで使う。`stop_gate.py` の到達しない done の分岐は消す。`docs/vault-spec.md` の9節・10節をこの検査に合わせて更新する。

### 受け入れ基準の候補
- 承認済み計画票に done の行があり verdict が無い時、`stop_gate.py` と `plan_guard.py` がそれぞれブロックし、reason に `<計画ID>/<id>` を含む（smoke にケースとして追加する）
- done の行の verdict が FAIL の時・attempt がタスク表と一致しない時・形式が不正な時（criteria の行数がタスク票の受け入れ基準と不一致）に、両フックがブロックする（smoke にケースとして追加する）
- done の行に attempt が一致する正しい PASS の verdict がある時、両フックが許可する（smoke にケースとして追加する）
- `validate_verdict` が `_hooklib.py` にだけ定義されている。確認：`grep -l "^def validate_verdict(" .claude/hooks/*.py` が `.claude/hooks/_hooklib.py` だけを出す
- 既存の smoke が全件 PASS し、既存ケースの期待値（block/allow と reason の部分文字列）は変わっていない。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含み、pass が516より多い
- `docs/vault-spec.md` の9節の判定表と10節に、done の行の verdict の検査が書かれている

### 決定済み
- 検査の対象は、自分のブランチの approved な計画票（`approved_plans` が1件の時）だけ。draft・done の計画票と `vault/archive/` は見ない
- 「正しい PASS の verdict」の条件は次のとおり。
  - JSON として読める
  - `task` が `<計画ID>/<id>`
  - `attempt` がタスク表の attempt と文字列として一致する
  - `result` が `PASS`（大文字小文字は既存の扱いのとおり区別しない）
  - `validate_verdict` が問題を返さない
- `_hooklib.py` に次の2つを置く。
  - `validate_verdict`：今の `stop_gate.py` のものを引数の形を変えずに移す（問題のリストを返す）
  - `done_rows_without_pass(root, plan_id, tasks)`：done の行を検査し、`[(id, 理由), ...]` を返す
- 検査の位置：
  - `plan_guard.py`：既存の検査（列数・status・依存・blocked の question・id の重複）の後。既存ケースのブロック理由が先に出るようにする
  - `stop_gate.py`：approved な計画票を1件に特定した直後、doing/review の検査より前
- ブロック理由の文面：`[<フック名>] <計画ID>/<id> は done ですが、attempt=<n> の PASS の verdict がありません（<理由>）。計画票の <id> の status を review に戻し、verifier を実行してください。`
  - done のタスクの verdict への書き込みは `agent_write_guard.py` が拒否する。そのため、直す手順は「review に戻す → verifier」の順で書く
- `stop_gate.py` の `stop_hook_active` の扱いは変えない
- `agent_write_guard.py` は変更しない
- 既存の smoke で done の行を含む計画票を使うケース（`plan_guard.py` の (a-5) など）は、PASS の verdict を置くように前提を直してよい。期待値は変えない。直したケースは PR 本文に列挙する

## フェーズ2 状態遷移スクリプト transition.py の基本

### ゴール文

計画票のタスク表の状態遷移を1コマンドで行う `scripts/transition.py` を新設する。呼び出しの形は次のとおり。

`python3 scripts/transition.py <計画ID> <id>[,<id>...] <遷移先> [--question <文> | --question-file <パス>] [--note <補足>] [--no-model]`

このスクリプトは次のことを行う。
- 現在の status から許される遷移だけを行う：todo→doing、doing→doing、doing→review、doing→blocked、review→done、review→doing、review→blocked
- タスク表の status・attempt・question を書き換える
- `vault/log/<計画ID>.md` に、実際の JST の時刻で遷移行を追記する
- 計画票と log（done の時は verdict も）だけをコミットする
- review→done は、フェーズ1と同じ条件の PASS の verdict が無ければ拒否する
- 遷移行のモデルの記録（`creator=`・`verifier=`）は、`.claude/agents/<name>.md` の frontmatter から自動で付ける

このフェーズでは run の手順は変えない。

### 受け入れ基準の候補
- 一時 git リポジトリ（ブランチ `work/p-test`、承認済み計画票 `P-TEST`）で `transition.py P-TEST T-01,T-02 doing` を実行すると、両行が doing・attempt=1 になり、log に2行が追記され、計画票と log だけを含むコミットが1つ増える（smoke にケースとして追加する）
- log に追記される行の日時が、実行時の `TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M'` と1分以内で一致する。doing→review の行には `creator=<.claude/agents/creator.md の model>` が、review→done の行には `verifier=<.claude/agents/verifier.md の model>` が付く（smoke）
- review→done は、PASS の verdict が無い・FAIL・attempt が不一致の時に終了コード1で拒否し、計画票・log・コミットは変わらない。正しい PASS の verdict がある時は done にし、verdict もコミットに含める（smoke）
- 次の場合は終了コード1で拒否し、何も変えない（smoke）
  - 遷移先が todo・approved
  - blocked の行からの遷移
  - 計画票が approved でない
  - 現在のブランチが `work/<計画IDの英小文字>` でない
  - after の依存が done でない行を doing にする
  - 再試行で attempt が `HARNESS_MAX_ATTEMPTS` を超える
  - blocked にするのに question が無い
- question に `|` と改行を含めても、書き換えた後の計画票で `plan_guard.py` がブロックしない（smoke）
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む
- `docs/vault-spec.md` の2節と7節に、`scripts/transition.py` の使い方と、これが遷移を行う推奨の経路であることが書かれている

### 決定済み
- スクリプト名は `scripts/transition.py`。`install.sh` は `scripts/` 直下の `*.py` を自動で配るので変更しない
- 計画票の frontmatter とタスク表の読み方は `.claude/hooks/_hooklib.py` を使う。import の手順は `sys.dont_write_bytecode = True` → `os.path.dirname(os.path.abspath(__file__))` から見た `../.claude/hooks` を `sys.path` の先頭に入れる → `import _hooklib`
- PASS の verdict の条件は、フェーズ1の `done_rows_without_pass` と同じ関数を使って判定する
- 対象のリポジトリは、実行時のカレントディレクトリの `git rev-parse --show-toplevel`
- 遷移ごとの attempt は次のとおり。
  - todo→doing：1にする
  - doing→doing・review→doing：+1 する
  - それ以外：変えない
- モデルの記録：
  - doing→review・doing→blocked の行に `creator=` を付ける
  - review→done・review→doing・review→blocked の行に `verifier=` を付ける
  - 値は対象リポジトリの `.claude/agents/creator.md`・`verifier.md` の frontmatter の `model`。読めない時は付けない
  - `--no-model` を指定した時は付けない（中断からの再開・ハング・worktree が無い時の行のため。`docs/vault-spec.md` 7節）
- log の行は `- <日時> <id> <旧>→<新> attempt=<n>[ creator=<m> | verifier=<m>][ <補足>]` の形。
  - 日時は UTC+9 固定（`datetime.timezone(datetime.timedelta(hours=9))`）で取る
  - log が無ければ作る
- question の書き方：
  - `|` は `／` に、改行は空白に置き換えて表に書く
  - `--question-file` はファイルの中身を question にする。Bash の引用符の問題とガードの誤検知を避けるためで、run からはこちらを使う
- 複数の id は、全部の行で同じ遷移が許される時だけ行う（1つでも拒否があれば何も変えない）。コミットは1回だけ
- コミットの仕方：
  - 計画票・log（done の時は verdict も）をファイル名で指定し、`git commit -m "<計画ID>/<id,...>: <旧>→<新>" -- <パス...>` の形でそれらだけをコミットする
  - ほかに staged な変更があってもコミットに混ぜない
- 終了コード：0 遷移した／1 前提を満たさず何も変えていない（理由を標準エラーに出す）／2 引数の誤り
- 承認（draft→approved）と blocked の解除はこのスクリプトでは行わない（決定事項を参照）
- このスクリプト自身が subprocess で `git commit` を実行する。そのため、`main` で実行させないことはブランチの検査で担保する
- run/SKILL.md は変えない（フェーズ5で変える）

## フェーズ3 差分ゲート diff_gate.py と「成果物」の記法

### ゴール文

creator の作業ブランチの差分が、タスク票の「成果物」に宣言されたファイルの範囲に収まっているかを確かめる `scripts/diff_gate.py` を新設する。

`python3 scripts/diff_gate.py <計画ID> <id> <base> <branch>` で、`<base>..<branch>` で変わったファイルを、`<base>` の版のタスク票の「成果物」節にあるバッククォートのパス（末尾が `/` ならディレクトリ）と照らし合わせる。次のものを違反として1行ずつ出す。
- 宣言されていないファイルの変更
- 自分のタスク票の「進捗」以外の節の変更
- `vault/plans/`・`vault/log/`・`vault/verdicts/`・`vault/rules/` 配下の変更

あわせて、タスク票の雛形と planner の定義に、「creator が変えるファイルはすべて『成果物』にバッククォートのパスで書く」という記法を足す。このフェーズでは run から呼ばない。

### 受け入れ基準の候補
- 宣言したファイルだけを変えたブランチでは終了コード0、宣言外のファイルを足したブランチでは終了コード1になり、そのパスが出力に含まれる（smoke にケースとして追加する）
- 自分のタスク票の「進捗」節だけを変えた時は違反にならず、「受け入れ基準」節を変えた時は違反になる（smoke）
- `vault/plans/`・`vault/log/`・`vault/verdicts/`・`vault/rules/` 配下の変更は、「成果物」に書かれていても違反になる（smoke）
- branch 側でタスク票の「成果物」にパスを書き足しても、base の版で判定するので違反のままになる（smoke）
- 末尾が `/` の宣言はその配下のファイルの変更を許す。`.claude/hooks/` 配下の変更は、宣言があれば許し、無ければ違反になる（smoke）
- `vault/templates/task.md` と `.claude/agents/planner.md` に「成果物」の記法（変えるファイルをすべてバッククォートのリポジトリ相対パスで書く、ディレクトリは末尾を `/` にする）が書かれ、`docs/vault-spec.md` の5節にも同じ規則と `diff_gate.py` の判定が書かれている
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- 変わったファイルは `git diff --name-only --no-renames <base> <branch>` で取る（リネームは削除と追加の両方として扱う）。見るのはコミット済みの差分だけで、未コミット分は対象外（コミットはフェーズ4で呼び出し側が行う）
- タスク票は `git show <base>:vault/tasks/<計画ID>/<id>.md` で読む。作業ツリーや branch 側の版は使わない
- 宣言の読み方：
  - 「## 成果物」の見出しから次の `## ` 見出しまでにある、バッククォートで囲まれた文字列をすべて候補にする
  - 末尾が `/` の候補は前方一致、それ以外は完全一致で照らし合わせる
  - パスでない文字列（関数名など）が混じっても害は無いので、そのまま候補に入れる
- 自分のタスク票（`vault/tasks/<計画ID>/<id>.md`）の扱い：`## ` 見出しで節に分け、「## 進捗」以外の節（最初の見出しより前の部分を含む）が base と branch で同じなら許す
- 宣言があっても常に違反にするもの：`vault/plans/`・`vault/log/`・`vault/verdicts/`・`vault/rules/` 配下。他の計画・他のタスクのタスク票やフィクスチャは、宣言が無ければ通常の宣言外として違反になる
- `.claude/hooks/`・`.claude/settings.json`・`.claude/agents/` は、宣言があれば許す（人の回答）
- 出力：違反1件につき `<パス>: <理由>` を1行出す
- 終了コード：0 違反なし／1 違反あり／2 次のいずれか
  - 引数の誤り
  - base にタスク票が無い
  - git コマンドが失敗した
- 節の分割は `diff_gate.py` の中に書く（使うのはこのスクリプトだけなので `_hooklib.py` には置かない）
- フェーズ4の `transition.py` から関数として import できるようにする。形は `check(root, plan_id, task_id, base, branch)` で、違反のリストを返す
- 雛形の記法の例：`` - `scripts/foo.py`（1ファイル） ``。「成果物は1つに特定する」という既存の粒度基準は変えない
- `vault/rules/planner/planner.md` は変えない（エージェントは書き込めないため。planner への指示は `.claude/agents/planner.md` に書く）

## フェーズ4 transition.py に worktree の運用を足す

### ゴール文

`scripts/transition.py` に、run の worktree の運用を1コマンドで行う機能を足す。

(1) `review --worktree <パス> --branch <ブランチ> --plan-head <sha>`
- worktree の未コミット分をコミットする
- 新規コミットが無ければ doing→blocked にする
- 新規コミットがあれば `diff_gate.py` で検査する
  - 違反が無い：再開情報の記録行と doing→review を書いてコミットする
  - 違反がある：違反をタスク票の「進捗」と log に書き、doing のまま attempt を +1 して worktree を破棄する。上限なら blocked にして worktree を残す

(2) `done --worktree <パス> --branch <ブランチ> --plan-head <sha>`
- PASS の verdict と差分ゲートを確かめてから、計画ブランチへ `git merge --no-ff` する
- done にしてコミットし、worktree とブランチを消す
- コンフリクトしたらマージを中止して review→blocked にする

(3) `doing --worktree <パス> --branch <ブランチ>`（FAIL の再試行）
- attempt を +1 して worktree を破棄する
- 上限なら、verdict の reasons を question にして review→blocked にする

(4) `blocked --worktree <パス> --branch <ブランチ> --plan-head <sha>`（creator が blocked を報告した時）
- 記録行を書いて blocked にし、worktree は残す

このフェーズでは run の手順は変えない。

### 受け入れ基準の候補
- review：worktree に未コミットの変更がある状態で実行すると、worktree 側にコミットができる。宣言どおりの変更なら計画票が review になり、log に `worktree path=... branch=... plan_head=...` の行と `doing→review` の行が追記され、終了コード0になる（smoke にケースとして追加する）
- review：宣言外の変更があると、計画票は doing のまま attempt+1 になり、タスク票の「進捗」と log に違反ファイルが書かれ、worktree とブランチが消え、終了コード3になる。attempt が上限の時は blocked（question に違反ファイル）になって worktree が残り、終了コード4になる（smoke）
- done：計画ブランチに `--no-ff` のマージコミットができ、計画票が done になり、コミットに verdict が含まれ、worktree とブランチが消え、終了コード0になる（smoke）
- done：計画ブランチ側と衝突する変更ではマージが中止され（`git status` にマージ中の状態が残らない）、計画票が blocked・question に衝突したファイルが書かれ、worktree が残り、終了コード4になる（smoke）
- 新規コミットの無い worktree で review を実行すると blocked になる。FAIL の再試行（doing）で上限を超える時は、verdict の reasons を question にした blocked になる（smoke）
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む
- `docs/vault-spec.md` に、各サブコマンドの動きと終了コードが書かれている

### 決定済み
- worktree とブランチの検証条件は `scripts/discard_worktree.sh` と同じ。
  - ブランチ名が `worktree-agent-` で始まる
  - `git worktree list --porcelain` に登録済み
  - 登録されたブランチが指定と一致する
  - 満たさなければ終了コード1で何もしない
- 未コミット分の収集：`git -C <worktree> add -A` → `git -C <worktree> commit -m "<計画ID>/<id>: creator 成果物をオーケストレーターが収集"`（今の run の手順6.3.1と同じ文面）
- 新規コミットの判定は `git rev-list <plan-head>..<branch>` の件数で行う（今の手順6.3.2と同じ）。0件なら doing→blocked にし、question は「worktree に新規コミットが無い（マージ対象の差分が無い）」とする
- 差分ゲートの違反による差し戻し（人の回答）：
  - タスク票の「進捗」の末尾に `- 差し戻し（attempt=<n>）: 宣言外の変更 <パス>, ...` を1行追記する
  - log に `doing→doing attempt=<n+1> 宣言外の変更: <パス>, ...` を書く（モデルは付けない）
  - タスク票もコミットに含める
  - worktree は破棄する
- done の前にも差分ゲートを実行する。review の後に worktree のブランチは変わらないはずだが、マージする内容をもう一度確かめるため。違反があれば review→blocked にする
- マージ：計画ブランチ上で `git merge --no-ff <branch> -m "<計画ID>/<id>: マージ"` を実行する。失敗したら `git diff --name-only --diff-filter=U` で衝突ファイルを取ってから `git merge --abort` し、衝突ファイルを question に書く
- done の後始末：`git worktree remove --force <パス>` → `git branch -d <branch>`。`--force` は、verifier の実行で残った未追跡ファイルがあっても消せるようにするため
- 破棄の処理は `discard_worktree.sh` と同じ（`git worktree remove --force` → `git branch -D`）。シェルスクリプトを呼んでも、同じ処理を Python で書いてもよい
- 終了コード：0 review/done にした／1 前提を満たさず何もしていない／2 引数の誤り／3 差し戻した（creator を呼び直す）／4 blocked にした
- FAIL の再試行と上限時の文面：
  - 再試行の log の補足：verdict の reasons の先頭を80文字で切ったもの
  - 上限で blocked にする時の question：reasons を `／` でつないで200文字で切ったもの
- `--worktree` などを渡さない review・done・doing は、フェーズ2の動き（タスク表と log だけを変える）のまま残す
- 終了コードが3・4の時は、何をしたかを標準出力に1行で出す（run が完了報告に写せるように）
