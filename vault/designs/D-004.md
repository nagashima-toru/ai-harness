# ゴール
`run` スキルが計画のタスクを全部 `done` にして PR を作った後、その計画実行を通して気づいたハーネス自体（`.claude/` のスキル・エージェント定義・フック、`vault/rules/`）への構造的な改善点があれば、オーケストレーターが1回だけ振り返り、`gh issue create` で起票する仕組みを追加する（issue #16）。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| 改善点がある時だけ書く。無ければ何もしない・issue も作らない | 人の判断（推奨案採用）。毎回 must にすると絞り出しになりノイズが増える懸念（issue の検討事項）を避ける |
| 拾うのは構造的な問題（スキル手順の分かりにくさ、フックの誤検知・見落とし、ルール文書の過不足など、繰り返し発生しうる問題）だけに絞る。軽微な言い回し修正は対象外 | 人の判断（推奨案採用）。粒度を広げすぎるとノイズが増え、issue 起票の価値が下がる |
| 出力先は常に別 issue（`gh issue create`）。PR 本文には改善提案セクションを設けない | 人の判断。PR 本文は成果物の説明に専念させ、ハーネス改善の議論は issue 側で独立してトリアージできるようにする（issue のたたき台から変更） |
| `gh issue create` が使えない（権限・ネットワークポリシー等）場合のフォールバックとして、提案内容を `vault/harness-improvements/<計画ID>.md` に書き残す。issue 化に成功した場合はこのファイルを作らない | 人の判断（「Issue機能が使えないケースも想定する事」という指摘への対応）。ここで拾った気づきを、起票できなかったからといって消さずに残す |
| 振り返りは `run` のオーケストレーター（メインセッション）が、全タスク `done` → PR 作成の直後に1回だけ行う。`creator`・`verifier` の役割・書き込み制約は変更しない | 人の判断（推奨案採用）。実装コストが低く、対象範囲（直近の計画実行1本分）が把握しやすい。各タスク実行中に creator/verifier へ気づきのメモ書きを課すと、役割定義（vault/rules/ への書き込み制約等）に波及する変更が必要になり範囲が広がる |
| 起票された issue は人がレビューする前提とし、自動アサイン・自動ラベル付けなどのトリアージ機構は作らない | 人の判断。トリアージの仕組み自体は issue 検討事項の範囲外とし、今回は「気づきを残す」ことに絞る |

## 依存関係
単一フェーズ。`/plan` に1回で渡せる規模（`run/SKILL.md` への手順追加が中心）。

## フェーズ1 計画完了時のハーネス振り返り・issue 起票

### ゴール文
`.claude/skills/run/SKILL.md` の手順7（全タスクが `done` になり PR を作成する箇所）の後に、「ハーネス振り返り」の手順を追加する。オーケストレーターは直近の計画実行（今回処理したタスク群）を振り返り、`.claude/`（スキル・エージェント定義・フック）や `vault/rules/` に対する**構造的な**改善点（スキル手順の分かりにくさ、フックの誤検知・見落とし、ルール文書の過不足など）に気づいた場合に限り、`gh issue create` で改善提案 issue を起票する。気づきが無ければ何もしない（issue も作らず、ログにも残さない）。`gh issue create` の実行が失敗した場合（権限不足・ネットワークポリシー等）は、提案内容をそのまま `vault/harness-improvements/<計画ID>.md` に書き残し、最終報告でその旨を人に伝える。issue 化に成功した場合はこのファイルを作らない。PR 本文には改善提案セクションを追加しない（PR 本文の内容・構成は変更しない）。

### 受け入れ基準の候補
- `run/SKILL.md` の手順7の後に「ハーネス振り返り」の手順が追加されており、「構造的な改善点があれば `gh issue create` で起票し、無ければ何もしない」という条件と、対象とする改善点の具体例（スキル手順の分かりにくさ・フックの誤検知や見落とし・ルール文書の過不足）が明記されている。確認：`grep -n "ハーネス振り返り" .claude/skills/run/SKILL.md` がヒットする
- `gh issue create` が失敗した場合に `vault/harness-improvements/<計画ID>.md` へ提案内容を書き残す手順が明記されており、成功時にはこのファイルを作らないことも明記されている
- この手順を実施する主体がオーケストレーター（run のメインセッション）であることが明記されており、`.claude/agents/creator.md`・`vault/rules/creator/`・`vault/rules/verifier/` には変更が入っていない（確認：`git diff main -- .claude/agents/creator.md vault/rules/` が空）
- 改善点が無い場合は issue を作らず PR 本文にも何も書かないという方針が明記されている（PR 本文のテンプレート・構成が変わっていないことも確認：既存の `gh pr create` 呼び出し手順自体は変更しない）
- 追加された手順以外の既存手順1〜7の記述に差分が無い（確認：`git diff main -- .claude/skills/run/SKILL.md` の差分が手順7の後への追記のみである）

### 決定済み
- 改善点の粒度は「構造的な問題」に限定する。軽微な言い回し修正・タイポ程度のものは拾わない
- 頻度は「あれば書く」。毎回 must にしない。今回の計画実行で気づきが無ければ、その旨をログや報告に書く必要も無い（完全にスキップしてよい）
- issue 起票時のタイトル・本文フォーマットは自由（「気づいたこと」「該当箇所」「提案」が分かる程度の内容であればよい）。テンプレートを新設する必要は無い
- `vault/harness-improvements/<計画ID>.md` は `gh issue create` 失敗時のみ作成する。ファイル自体はタスクの5状態遷移の対象ではなく、人が後で内容を見て手動で issue 化する運用とする
- 起票された issue のトリアージ（誰が見る・ラベル付け等）はこの設計の範囲外。人がレビューする前提のまま何もしない
