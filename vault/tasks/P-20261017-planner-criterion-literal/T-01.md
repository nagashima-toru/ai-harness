# T-01 plan_guard に受け入れ基準の grep の文字列と決定済みのバッククォートの食い違いの検査を足す

## 目的
draft の計画のタスク票で、受け入れ基準の grep の文字列が「決定済み」「成果物」の文言とバッククォートの有無だけで食い違っている時に、`.claude/hooks/plan_guard.py` が Write・Edit の後に止めるようにする（Issue #204）。

## 成果物
- `.claude/hooks/plan_guard.py`（主な成果物）

## 受け入れ基準
- 純関数 `literal_mismatches` が、バッククォートの有無だけで食い違う `-F` の文字列を返す：`printf '## 受け入れ基準\n- \x60grep -c -F \x27{Xxx}JobConfig。命名は方式設計 §11\x27 docs/a.md\x60 が 1\n## 決定済み\n- 「\x60{Xxx}JobConfig\x60。命名は方式設計 §11」と書く\n' | python3 -B -c 'import sys; sys.path.insert(0, ".claude/hooks"); import plan_guard; print(plan_guard.literal_mismatches(sys.stdin.read()))'` の出力が `['{Xxx}JobConfig。命名は方式設計 §11']`
- バッククォートを `.` に置き換えた（`-F` の無い）パターンは食い違いにしない：`printf '## 受け入れ基準\n- \x60grep -c \x27.{Xxx}JobConfig.。命名は方式設計 §11\x27 docs/a.md\x60 が 1\n## 決定済み\n- 「\x60{Xxx}JobConfig\x60。命名は方式設計 §11」と書く\n' | python3 -B -c 'import sys; sys.path.insert(0, ".claude/hooks"); import plan_guard; print(plan_guard.literal_mismatches(sys.stdin.read()))'` の出力が `[]`
- smoke に `(literal-task)` のテストが6件あり、すべて ok：`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (literal-task) '` の出力が `6`
- smoke 全体が通る：`bash scripts/smoke.sh 2>&1 | tail -1` の出力が `fail=0` で終わる
- `docs/vault-spec.md` の10節に検査の説明がある：`grep -c 'そのまま当たらず、バッククォートを除くと当たる' docs/vault-spec.md` の出力が `1`
- smoke の参照切れの検査が通る：`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (ref-1) '` の出力が `1`

## 決定済み
- 実装は `.claude/hooks/plan_guard.py` の中に置く（`_hooklib.py` は変えない）。純関数 `literal_mismatches(text)` と、フック用の `literal_violation(payload, root)` の2つを足す。モジュールの docstring にも検査の説明を1〜2行足す
- `literal_mismatches(text)`：引数はタスク票の本文（文字列）。食い違った grep の文字列（パターン）を、受け入れ基準の中の出現順にリストで返す（重複は除かない）。食い違いが無ければ空のリスト。ファイル・git・外部コマンドには触れない
- 節の分け方：行頭が `## ` の行を見出しとし、次の `## ` の行までをその節とする（`count_criteria` と同じ。見出しは `rstrip()` して `## 受け入れ基準`・`## 決定済み`・`## 成果物` と比べる）
- grep の取り出し方：「## 受け入れ基準」節の各行から、正規表現 `` `([^`\n]+)` `` でコードスパンの中身を取り、`shlex.split` で分ける（`ValueError` ならそのコードスパンは飛ばす）。トークンが `grep` の所から、`|`・`&&`・`;` のトークンの手前までをその grep の引数とする。1つのコードスパンに grep が複数あればすべて見る
- オプションの読み方：`--` の後の最初のトークンはパターン。`--fixed-strings` は固定文字列、`--extended-regexp`・`--perl-regexp` は対象外、その他の `--` で始まるトークンは読み飛ばす。`-` で始まる短いオプションは1文字ずつ読み、`F` は固定文字列、`E`・`P` は対象外。`e`・`f`・`m`・`A`・`B`・`C`・`d`・`D` は値を取る（残りの文字があればそれが値、無ければ次のトークンが値）。`-e` の値はすべてパターン。`-e` が無ければ、オプションでない最初のトークンがパターン
- 対象にするパターン：(1) 固定文字列（`-F`・`--fixed-strings`）はそのままの文字列として照合する。(2) `-E`・`-P` の無い基本正規表現は、`[`・`]`・`*`・`^`・`$`・`\` のどれかを含めば対象外。含まなければ `.` を任意の1文字、その他の文字をそのままの文字として照合する（`re.escape` した断片を `.` でつなぐ）。(3) `-E`・`-P` は対象外。空のパターンと、バッククォートを含むパターンも対象外
- 照合：「## 決定済み」と「## 成果物」の節の各行を照合先にする。どれかの行にそのまま当たれば食い違いではない。どの行にもそのままは当たらず、行からバッククォートをすべて除いたもののどれかに当たる時だけ食い違いとする。どちらにも当たらないパターンは対象外（「決定済み」に無い文字列は、残っていないことの確認・既存ファイルの文言・コマンドの出力を見る基準など正しい基準が多く、過去のタスク票158件では `-F` の112件中20件がこれに当たった。誤検知を避けるため止めない）
- `literal_violation(payload, root)` の契機と fail-open は `granularity_violation` と同じ（tool_name が Write か Edit、`file_path` が `vault/tasks/<計画ID>/T-NN.md`、計画票の status が draft、タスク票が読めない時は None）。`main()` では `granularity_violation` の後、`plan_size_violation` の前に呼ぶ
- ブロックの理由文：`[plan_guard] <計画ID>/<id> の受け入れ基準の grep の文字列が、「決定済み」「成果物」の文言とバッククォートの有無だけで食い違っています（'<パターン>'、複数なら `、` でつなぐ）。creator が決定済みどおりに書くと当たりません。バッククォートをまたがない部分文字列を選ぶか、バッククォートを . に置き換えたパターン（-F を付けない）にしてください。` の形にする（語句「バッククォートの有無だけで食い違っています」と、パターンそのものを必ず含める）
- smoke のテスト：`scripts/smoke.sh` の `(headings-task)` のテストの後（`# 計画票のタスク表行数検査` より前）に、名前が `(literal-task) ` で始まる `expect` を6件ちょうど足す。タスク票は6見出しと基準3行をそろえた本文を printf などで書く関数を smoke の中に足してよい（`make_task` は変えなくてよい）。6件の中身：(1) draft・`-F` の文字列が決定済みとバッククォートの有無だけで食い違う → block（理由に `バッククォートの有無だけで食い違っています` を含む）、(2) draft・バッククォートを `.` に置き換えたパターン → allow、(3) draft・決定済みにそのまま書かれた文字列 → allow、(4) draft・決定済みにも成果物にも無い文字列（例：残っていないことを見る基準）→ allow、(5) approved・(1) と同じ票 → allow（検査しない）、(6) draft・(1) と同じ票・tool_name が Bash → allow（対象外）。テストの後で `$TMP/vault/plans/P-TEST.md` と `$TMP/vault/tasks` を既存のテストと同じやり方で片付ける
- smoke の中のテスト用のタスク票の本文にバッククォートを書く時は、smoke の既存の書き方（単一引用符の中の printf の引数など）に合わせる。確認コマンドではないので、シェルの特殊文字の制限は smoke の中身には掛からない
- `docs/vault-spec.md` の10節の、6見出しの検査の箇条（「タスク票（契機は粒度の検査と同じ…」）の後に、箇条を1つ足す。その箇条に「受け入れ基準の grep の文字列が、「決定済み」「成果物」の行にはそのまま当たらず、バッククォートを除くと当たる」という文言をそのまま書き、対象にするパターン（`-F` の固定文字列と、`[ ] * ^ $ \` を含まない基本正規表現。`-E`・`-P` は対象外）と、「決定済み」に無い文字列は止めないこと、Issue #204 を書く。この文言は10節のこの箇条の1か所だけに書く
- `docs/vault-spec.md` に新しいファイルのパスをバッククォートで書かない（`(ref-1)` の対象。既存のパスだけを書く）
- 受け入れ基準の1・2行目の `printf` は、`\x60` でバッククォート、`\x27` で単一引用符を出す（確認コマンドにバッククォートと入れ子の引用符を直接書かないため）。`python3 -B` は `__pycache__` を作らないため
- 8節（粒度の基準）・`.claude/skills/plan/SKILL.md`・`.claude/agents/planner.md` はこのタスクでは変えない（planner.md は T-02）
