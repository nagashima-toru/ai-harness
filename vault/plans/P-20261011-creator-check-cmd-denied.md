# ゴール
GitHub Issue #184 に対応する。creator が受け入れ基準の確認コマンドを Claude Code 側のガード（権限判定・サンドボックスなど）に拒否された時のふるまいを `.claude/agents/creator.md` に定める。verifier 側の同種のルール（`.claude/agents/verifier.md` の「手順」8：実行できなかった旨と代替の確認方法・結果をセットで書き、黙って置き換えない）と整合させる。

## 分割方針
- 成果物は `.claude/agents/creator.md` の1ファイルで、1タスクに収まる。
- 方針の決定（Issue の候補 (a)・(b) のどちらにするか）：(b) を基本とし、(a) を緩める時の歯止めにする折衷にした。理由は次のとおり。
  - 拒否は判断の迷いではなく実行環境の事情で、原因が未確定かつ別セッションでは再現しない。拒否のたびに blocked にすると、人が答えようのない質問で止まり続け、vision の「途中で止まらない」を損なう。
  - 一方で、Issue の事例ではパターンの一部を削って確かめており、元の基準より緩い確認に置き換えていた。これは「受け入れ基準を読み替えない」に反する。そこで代替は「同じ対象を同じ条件で（緩めずに）確かめられる時」だけに限り、緩める以外に手が無い時は blocked にする（vision の「迷ったら推測で進めずに止める」）。
  - 完了の判定は verifier が元の確認コマンドで行い、verifier も実行できなければ自分の「手順」8で代替と結果を note に書く。creator の代替確認は完了を決めるものではないので、vision の「完了は作った本人に決めさせない」とも両立する。creator は「進捗」に、元のコマンド・拒否された旨・代替の方法・結果の4点をセットで残す（verifier の「手順」8と同じ構成）。
- `creator.md` は導入先に配布されるため、計画 ID・Issue 番号などこのリポジトリ固有の経緯は書かない（planner の経緯を `vault/rules/planner/ai-harness-lessons.md` に分けたのと同じ扱い）。
