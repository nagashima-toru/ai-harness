# T-01 agent_write_guard.py に done タスクへの書き込み拒否判定を追加し smoke.sh にテストを足す

## 目的
`.claude/hooks/agent_write_guard.py` に、`agent_type` を問わず（メインセッション含む）適用する判定を追加する。書き込み先が `vault/tasks/<計画ID>/<id>.md` または `vault/verdicts/<計画ID>/<id>.json` で、かつ `vault/plans/<計画ID>.md` のタスク表でその id の status が `done` の場合は拒否する。計画票が見つからない・その id の行が無い・読めない場合は許可する（fail-open）。`scripts/smoke.sh` に回帰テストを足す（issue #76）。

## 決定済み
- 対象は2種類だけ：`vault/tasks/<計画ID>/<id>.md` と `vault/verdicts/<計画ID>/<id>.json`。正規表現の目安は `^vault/tasks/([^/]+)/([^/]+)\.md$` と `^vault/verdicts/([^/]+)/([^/]+)\.json$`（`normalize()` で root 相対化した後のパスに対して適用する）。`<id>-proposal.md` のような派生ファイルや `vault/archive/` 配下は、この正規表現に一致しないため自然に対象外になる（特別な除外処理は不要）
- 判定順序：`main()` 内の既存の `vault/rules/` 改ざん防止判定（`targets_vault_rules` のブロック）の直後、`agent = payload.get("agent_type")` の行より前に、この新しい判定を追加する。`agent_type` を問わず必ず評価する
- タスク表の解析は `.claude/hooks/plan_guard.py` の `COLUMNS = ("id", "status", "attempt", "after", "title", "question")`・`raw_rows(plan_text)`（「## タスク表」以降のデータ行を生セルで返す）と同じ規則を、このファイル内にコピーして実装する（他ファイルへの `import` はしない、既存方針どおり）。計画票 `vault/plans/<計画ID>.md` を読み、`raw_rows` で該当 id の行を探し、無ければ（ファイルが無い・読めない・行が無い）status を求めず許可（fail-open）とする
- Write/Edit/MultiEdit/NotebookEdit：対象 `file_path`（`tool_input.get("file_path") or tool_input.get("notebook_path")`）を `normalize(path, root)` した結果に対し、上記2つの正規表現でマッチを試みる。マッチしたら plan_id・id を取り出し、対応する計画票の該当行の status を調べ、`done` ならブロック
- Bash：まず既存の `BASH_WRITE_PATTERNS` のいずれかにマッチしない場合は何もしない（読み取り専用コマンドは対象外）。マッチする場合、対象パス候補は既存の `extract_bash_write_targets(cmd)` の戻り値と、`targets_vault_rules` が使っているのと同じ path-like 抽出（`re.findall(r"[^\s'\"]*vault/(?:tasks|verdicts)/[^\s'\"]*", cmd)`、マスク前の生の `cmd` に対して適用）の両方を合わせたものにする。`sed -i` はファイル名を直接引数に取るため `extract_bash_write_targets` では拾えず、後者の path-like 抽出で拾う
- 拒否時のメッセージ（reason）には、対象の `<計画ID>/<id>` と、文字列 `done` を含める。例：`[agent_write_guard] P-FIX/T-01 は status が done のため、vault/tasks/P-FIX/T-01.md へは書き込めません。`
- 解除口は作らない（`vault/rules/` の改ざん防止と同じ考え方）。環境変数等でこの判定をスキップする経路は用意しない
- worktree 委譲（`delegate_to_worktree`）は変更しない。新しい判定は委譲判定より後（委譲しない場合のローカル判定の中）に置く
- フィクスチャ手順（受け入れ基準で使う。固定パスを `mkdir -p` で作り直す運用とし `rm -rf` は使わない）：
  1. `mkdir -p /tmp/P-20260927-done-write-guard-T-01-fixture/vault/plans`
  2. 次の内容で `/tmp/P-20260927-done-write-guard-T-01-fixture/vault/plans/P-FIX.md` を作る（Write ツールでも `cat > /tmp/P-20260927-done-write-guard-T-01-fixture/vault/plans/P-FIX.md <<'EOF' ... EOF` の1コマンドでもよい）：
     ```
     ---
     id: P-FIX
     status: approved
     ---
     # ゴール
     テスト用

     ## タスク表（状態の正本）
     | id | status | attempt | after | title | question |
     |---|---|---|---|---|---|
     | T-01 | done | 1 | - | done task | |
     | T-02 | doing | 1 | - | doing task | |
     | T-03 | review | 1 | - | review task | |
     ```
  3. このフィクスチャ root は git リポジトリにしない（既存の `scripts/smoke.sh` の `TMP` フィクスチャと同じ前提。`resolve_root` の git 探索は失敗し `CLAUDE_PROJECT_DIR` へフォールバックする）
- `scripts/smoke.sh` に追加するテストケース名には接頭辞 `(done-write)` を付ける（`(delegate)`・`(worktree)` 等、既存の接頭辞付きケースの命名規則を踏襲）。ケース数・文言は上記の受け入れ基準5件の内容をそのままカバーできればよく、既存の `make_plan`／`expect_guard` ヘルパーをそのまま使ってよい（新規ヘルパーを追加してもよい）
- reason に `done` を含むことを smoke.sh 側でも機械的に確認したい場合、`expect_guard` を拡張する（4番目の引数で reason に含むべき部分文字列を追加できるようにする等）か、新規ヘルパーを足すか、実装方法は creator が選んでよい
- コミットは、実装（`.claude/hooks/agent_write_guard.py`）とテスト（`scripts/smoke.sh`）をそれぞれ分けて行ってよい（`vault/rules/common/git.md` の「作業ステップごとに小さく分ける」方針に従う）
