# T-02 vault-spec.md を提案ファイル方式に書き直す

## 目的
`docs/vault-spec.md` 第12節（agent_write_guard フックの改ざん防止判定）を、新しい「提案ファイル方
式」（ルール変更を成果物とするタスクは `vault/tasks/<計画ID>/<id>-proposal.md` に下書きし、verifier
がそこを検証し、実体への反映は人が手作業で行う）を正本として書き直す。第11節の要約文も、`doing`/
`review` の有無を条件にした説明のままだと第12節と矛盾するため、常時拒否である旨に揃える。

## 入力
- `docs/vault-spec.md` 第11節（166〜174行付近、「改ざん防止」小節）・第12節（176〜201行付近）
- `vault/designs/D-002.md`「## 決定事項」「## フェーズ1」
- T-01 の成果物（`.claude/hooks/agent_write_guard.py`。書き直す文面が実装と矛盾しないか照らし合わせ
  る参照用。T-01 が先に終わっていなくても、D-002 の決定事項だけで文面は書ける）

## 成果物
- `docs/vault-spec.md` 第11節・第12節

## 受け入れ基準
- 第12節が提案ファイル方式（成果物パスを `vault/tasks/<計画ID>/<id>-proposal.md` にする、verifier
  はそこを検証する、実体への反映は人が手作業で行う）を記述している。確認：
  `grep -c -- '-proposal.md' docs/vault-spec.md` が1以上
- `vault/rules/` への書き込み拒否が、`doing`/`review` の有無や承認済み計画の有無を問わず常に発火す
  る旨が明記されている。確認：`awk '/^## 11\\./,/^## 13\\./' docs/vault-spec.md | grep -c 'review 中'`
  が0（状態条件付きの説明が残っていない）
- `HARNESS_ALLOW_RULES_WRITE` への言及が消えている。確認：
  `grep -c HARNESS_ALLOW_RULES_WRITE docs/vault-spec.md` が0
- 見出し番号の連番が保たれている（第12節の見出しが存在し、第13節がそのまま続く）。確認：
  `grep -c '^## 13\\.' docs/vault-spec.md` が1
- `bash scripts/smoke.sh | tail -1` に `fail=0` が含まれる（このタスクの編集がドキュメントのみでも、
  smoke.sh はドキュメントを読まないため通ることの確認）

## 決定済み
- 提案ファイルのパス形式は `vault/tasks/<計画ID>/<id>-proposal.md` に固定する（例：
  `vault/tasks/P-20260924-rules-guard/T-03-proposal.md`）。複数のルールファイルにまたがる変更は、成
  果物を1つに保つ既存原則に従ってタスクを分割する、という運用ルールも一文添える
- 「実体への反映は人が手作業で行う」ことと、反映を自動化するスクリプト・スキルは作らないことを明記
  する（`vault/designs/D-002.md` の決定事項どおり）
- 第11節の要約文（現行「`doing` / `review` 中のタスクがある間は、`vault/rules/` への書き込みをフッ
  クで拒否する」）は「常に（`doing`/`review` の有無や承認済み計画の有無を問わず）拒否する」に書き換
  える。理由の説明（作成エージェントが判定基準を自分で緩めることを防ぐ）はそのまま残してよい
- 第12節の表形式（状況／判定の2列）は維持してよいが、行数・内容は新ロジックに合わせて作り直してよ
  い。列見出しやこの節のタイトルを変えても、フックが解析する対象ではないので問題ない
- `plan_guard.py`・`stop_gate.py` に関する既存の記述（第9節・第10節）は変更しない
- 見出し番号（1〜13）はこのタスクでは増減させない。節タイトルの文言変更（例：「12. agent_write_
  guard フックの改ざん防止判定」→内容に合わせた文言）は可
