## 決定済み
- vault-spec の新しい段落は、1節の「環境変数 `HARNESS_BASE_BRANCH` はベースブランチ…」で始まる段落の直後に置き、行頭を `` 環境変数 `HARNESS_PUSH_BRANCH` `` で始める1段落（1行）にする。文中で「前後の空白を除いて空」・`git push -u origin HEAD:<値>`・`head=<値>`・`--source-branch <値>` をこの順に出す
- 段落に書く内容：push 先と PR/MR の head（source branch）を上書きする値であること／前後の空白を除いて空（未設定を含む）なら未設定で、今の動作（上流が無ければ現在のブランチ名で push、head は現在のブランチ）のまま／設定時は GitHub・GitLab の経路で上流の有無に関係なく毎回 `git push -u origin HEAD:<値>` で push し、GitHub の REST は `head=<値>`、GitLab の引数なしの経路は `glab mr create` に `--source-branch <値>` を足す／引数ありの経路でも push は `HEAD:<値>` で行い、PR/MR 作成の引数は足さない／push が失敗したら（non-fast-forward を含む）その終了コードで終わり、force はしない／`none` の経路は値を見ない／`/plan` 手順A-2・`/design` 手順1 の開始条件に「`HARNESS_PUSH_BRANCH` が設定され、現在のブランチがその値で、`git rev-parse HEAD` がローカルの `<ベースブランチ>` と同じコミットなら、ベース上とみなして現在の HEAD から切る」が加わる（ローカルにベースブランチが無ければ止まる。`origin/<ベース>` の fetch はしない）／run 手順7・design 手順8 の MCP 代替時の head もこの値／ローカルのブランチ名（`work/…`・`design/…`）と transition.py のブランチ検査は変えない／この値のブランチ上の直接コミットはフックで拒否しない
- runbook は `## 9.` の節の後、`## 困ったとき` の前に `## 10. push 先が決められている環境（クラウドセッション）` の節を足す。内容：クラウドセッションのように、実行環境の指示で push 先のブランチが決められていて、セッションはベースブランチと同じコミットのその指定ブランチ上で始まること／環境変数に無い時は、オーケストレーターがその値を `env HARNESS_PUSH_BRANCH=<指定ブランチ> …` でコマンドに渡す（`/plan`・`/design` の開始条件の確認と `vcs_finish.sh` の両方。`env` で始めると許可リストの `Bash(env *)` で通る）／値が毎回同じ環境なら、恒久的に `.claude/settings.json` の `env` に書いてもよい／ローカルでは `work/…` を切って作業し、push 先と PR の head だけがその値になること／指定ブランチのリモートが先に進んでいて push が失敗した時（non-fast-forward）は、スクリプトは force せずに止まるので人が判断すること
- runbook の例では、`env HARNESS_PUSH_BRANCH=<指定ブランチ>` をバッククォートかコードブロックで書く（`<指定ブランチ>` を含むパスは ref-1 の検査対象外）
- `docs/install.md`・`README.md` は変えない（`HARNESS_PUSH_BRANCH` はセッションごとに値が変わる前提で、導入時の設定手順には入れない）
- vault-spec の13節は変えない
