# T-0031 `vault/rules/creator/git-workflow.md` を新設し `creator.md` の記述を改訂する

## 目的
`vault/rules/common/git.md`（T-0030）で決めた方針を、作成エージェント（run-queue のメイン）が「いつブランチを切るか・いつコミットするか・いつ PR を作るか」という具体的な手順に落とす。あわせて `vault/rules/creator/creator.md` の「やらないこと」から、この計画で読み替えた git commit の記述を外し、新ルールへの参照に改める。

## 決定済み
- このタスクは `vault/rules/` へ書き込む。人が `HARNESS_ALLOW_RULES_WRITE=T-0031 claude`（または同形の `claude -p`）で起動している前提で進める。deny されたら status を `blocked` にし question に「`HARNESS_ALLOW_RULES_WRITE=T-0031` を設定して再実行してください」と書く
- `git-workflow.md` の「ルール」に書く内容（各1〜4行、`**見出し**` 付き）：
  1. **いつブランチを切るか**：todo.md から取ったタスクがどの計画に属するか（`vault/plans/*.md` の「タスク一覧」に自分の ID がある票を探す）を特定し、その計画の作業ブランチがまだ無ければ `main` から `work/p-xxx-<slug>` を作成してチェックアウトする。`slug` は計画タイトルを短い英小文字ハイフン区切りにしたもので、厳密な自動生成アルゴリズムは要求しない（人が読んで計画を識別できれば良い）。既にそのブランチがあれば作り直さずチェックアウトするだけにする
  2. **いつコミットするか**：「成果物」を作る・受け入れ基準を1つ満たす・タスク票の「進捗」に追記する、などの作業ステップを終えるたびにコミットする。まとめて1コミットにしない。動作しない中間状態でも構わないが、何をしたか説明できる単位にする。メッセージ1行目に「何をしたか」を書く（日本語可）
  3. **いつ PR を作るか**：あるタスクを `done` にした直後、そのタスクが属する計画の全タスクが `vault/todo.md` 上で `done` になっているか確認する。全部 `done` なら `git push` してから `gh pr create` する。`gh pr merge` は実行しない（マージは人が行う）。PR 作成後は「マージ可能です」と報告して次のタスクに進む（ブランチ・PR は計画単位で使い回すので、次の計画に移るまでは同じブランチで作業を続けない＝次のタスクが別の計画に属するなら手順1に戻って新しいブランチを切る）
  4. **例外**：コンフリクト・想定外の差分・判断がつかない git の状況に遭遇したら、自己判断で処理せず、対象タスクを `blocked` にし question に git の状況を書いて止まる
- 「確認方法」には、コミットログが作業ステップ単位に分かれているか（`git log --oneline` で1コミット1変更になっているか）、`main` に直接コミットしていないか、PR が計画の全タスク完了後にだけ作られているか、を2〜4行で書く
- `creator.md` の改訂は最小限にする：該当行から「指示されていない git commit、」を削除し、「やらないこと」の末尾に新しい1行「git のコミット・ブランチ・PR は自己判断せず `vault/rules/common/git.md`・`vault/rules/creator/git-workflow.md` に従う」を追加する。他の行は変更しない
- `.claude/skills/run-queue/SKILL.md`・フック・`install.sh`・ドキュメント類は変更しない（それぞれ T-0032〜T-0035 の範囲）
- git commit はしない（人が確認してからコミットする）
