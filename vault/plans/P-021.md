# ゴール
フック3つ（`stop_gate.py`／`todo_guard.py`→`plan_guard.py`／`agent_write_guard.py`）とスキル2つ
（`/plan`／`run-queue`→`/run`）を、`vault/todo.md` ではなく自分のブランチの計画票（`vault/plans/`
の `status: approved` な1件）を読む形に作り替える。`stop_gate.py` は verdict の形式検査・鮮度・
attempt 照合のロジックを保ったまま読む先だけを変える。付随して `.claude/agents/planner.md`・
`.claude/agents/verifier.md`、標準ルール4本（`vault/rules/common/roles.md`・`creator/creator.md`・
`verifier/verifier.md`・`planner/planner.md`）の `vault/todo.md` 言及を新方式に直す。
`vault/designs/D-001.md` フェーズ3に対応する（設計文書の再検討は行わない）。

## 分割方針
`vault/designs/D-001.md` フェーズ3の決定事項どおり、フック改修中はすべて fail-open（計画票が見つか
らない＝許可）で通し、`vault/todo.md` へのフォールバックは書かない。既存資産（旧 `vault/todo.md`・
`vault/plans/P-001〜P-020`・`vault/tasks/T-0001〜T-0045` など）の凍結・削除は次フェーズ（フェーズ4）
で行うため、このプランでは旧ファイルに一切手を触れない。

`scripts/smoke.sh` の `make_todo`（`vault/todo.md` を作る共通ヘルパー）は `== stop_gate.py ==` と
`== agent_write_guard.py ==` の両セクションから呼ばれている共有関数なので、どちらか一方だけを新形
式に書き換えると他方のケースが壊れる。これを避けるため、まず新しいヘルパー `make_plan` /
`make_plan_task`（計画票を作る）を追加で導入し、`make_todo` は当面残したまま各タスクが自分の担当
セクションだけを新ヘルパーに移行する。全セクションの移行が終わった時点（T-0048）で `make_todo` を
削除する。

契約（計画票のタスク表を探す・検査する規則）を最初に固定するため、`plan_guard.py`（新規、
`todo_guard.py` の作り替え）を最初のタスクにする。`stop_gate.py`・`agent_write_guard.py` は
`import` はしないが、`plan_guard.py` と同じ「approved な計画票を1つ探す」「`## タスク表` 以降の行
を読む」規則を自分のファイル内にコピーして使うため、`plan_guard.py` の実装が先にあった方が文言・
挙動を合わせやすい。`scripts/smoke.sh` を同じファイルとして順に書き換えるため、この3タスクは一本
鎖の `after` にする。

`/plan`（+ `planner.md`）と `/run`（+ `verifier.md`）はそれぞれ別ファイル（スキル・エージェント定
義）で `scripts/smoke.sh` にも触れないため、フックの3タスクとは独立して進められる。標準ルール4本の
更新は、上記5タスクすべての最終的な用語・パス（`plan_guard.py`・`vault/log/<計画ID>.md` 等）が確定
してから行う方が書き直しの手戻りが無いため、最後に置く。

## 人への質問
決定済みの範囲で判断できたため、着手を止めるほどの不明点は無い。念のため以下2点は「決定済み」に
先回りの回答として書いたので、意図と異なれば承認前に指摘してほしい。
- `/plan` はブランチ作成前に現在のブランチが `main` であることを確認し、`main` でなければブランチ
  を切らずに止まる、とした（T-0049 決定済み）。既存の作業ブランチに計画を重ねる運用は今回入れない。
- ~~`stop_gate.py`・`agent_write_guard.py` は、approved な計画票が2件以上見つかった異常時、判定を進
  めず許可（fail-open）する~~ → **承認時に人が変更。** 安全機構が「壊れている時だけ無効になる」のは
  向きが逆なので、`stop_gate.py` は2件以上でブロックし、`agent_write_guard.py` は全部の計画票から
  doing/review を集めて保守的に判定する。0件のときの fail-open は D-001 の決定どおり維持。
  `plan_guard.py` は PostToolUse のため、編集以外の経路（マージ・チェックアウト）で入った異常を
  次の編集まで検知できないことが理由（T-0047・T-0048 の決定済みに反映済み）。
