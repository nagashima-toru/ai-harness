# ゴール
複数のエージェントセッションが同時に別々の計画を進められるようにする。そのために、計画をまたぐキュー（`vault/todo.md`）を廃止し、計画の作成から実行・PR までを1本のブランチに閉じる。状態ファイルをセッション間で共有しないことで、マージコンフリクトと ID 衝突を運用ルールではなく構造で消す。

前提として、現行の `scripts/install.sh` はインストール先の既存ファイルを上書きしないため、ハーネスを更新しても配布先に届かない。この欠陥を先に直してから移行する。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| フェーズ3実施中、旧計画（P-001〜P-017, P-019, P-020）の `status` を `approved` から `done` に一括移行した（P-021 のみ `approved` のまま残す） | `plan_guard.py` を `.claude/settings.json` に配線した瞬間、旧方式に `done` 相当の終端状態が無く全計画が `approved` のままだったため「1ブランチ1計画の不変条件違反（20件）」を検出し、以後の全 Write/Edit/Bash がブロック理由付きで警告される実害が出た。このセッションが git worktree を使わず main 直コミットで運用してきたため、過去の計画ファイルが同じ `vault/plans/` に積み上がり続けたことが根本原因。人の指示によりその場で旧計画を `done` へ移行して解消した |
| 今後も worktree 化はせず、main 直コミットで作業を続ける | D-001 は git worktree による物理隔離を前提に設計されているが、実際の運用はこのセッション開始からずっと main 直コミット。今回変えず、計画完了ごとに `status: done` へ更新する運用で不変条件を保つ |
| セッションの並行性を最優先し、複数計画を1ブランチで一気に流す効率は捨てる | ハーネスとしての価値は並行性の側にある。実運用でも計画単位でしか実行していない |
| キューに必要な機能は「1計画内の複数タスクを順に実行する」だけ。計画をまたぐキューは持たない | `vault/todo.md` のタスク表は計画票のタスク表に status 列を足したコピーで、二重管理だった |
| 1セッション = 1計画 = 1ブランチ。計画の作成から実行・PR まで同じブランチに閉じる | main に触るのがマージの瞬間だけになり、セッション同士が同じファイルを書く場面が無くなる |
| `vault/todo.md` を廃止し、状態（status / attempt / question）は `vault/plans/<id>.md` のタスク表が持つ | 計画票がキューそのものになる。共有される可変ファイルを1つも残さないため |
| 計画 ID は `P-YYYYMMDD-<slug>` 形式にする（例：`P-20260919-git-ops`） | 採番が不要なので並行セッションで衝突しない。ブランチ名 `work/p-20260919-git-ops` を機械的に導ける |
| タスク ID は計画スコープの `T-01`〜 にする | 計画内で閉じるため、並行セッション間で衝突しない |
| 既存資産（17計画・29タスク票・29 verdict・`queue.md`・`todo.md`）は `vault/archive/2026-09/` に凍結する | 全部 `done` で運用上の価値が無く、履歴は git に残る。変換コストが純粋な無駄になる |
| `todo_guard.py` は `plan_guard.py` に作り替える | PostToolUse の即時フィードバックに価値がある。既存5検査をほぼそのまま移植でき、`doing は1件` が計画スコープになる |
| 移行は一気に切り替える。旧方式へのフォールバックは作らない | 恒久的な複雑さを残さない。フック改修中は「計画票が見つからなければ許可」の fail-open で通す |
| 移行の前に、インストール先への更新経路を直す | 現行は `copy_if_absent` なので2回目以降の install でフック・スキル・仕様が一切更新されない。この状態で移行しても配布先に届かない |
| 更新は install 時のハッシュをマニフェストに残し、未編集なら上書き・編集済みならスキップして差分を報告する | 利用者が標準ルールに足した記述を消さずに、触っていないファイルは確実に最新化できる |
| `.claude/settings.json` は専用マージャで、hooks の欠落エントリと `permissions.deny` の不足分だけを足す | 利用者が必ず編集するファイル。ハッシュ照合では実質常にスキップされ、フックの入れ替えが届かない |
| マージは人が行う。エージェントは `gh pr create` まで。`gh pr merge` は実行しない | 既に決定済み。計画の完了判断を人に残す |
| 証跡は3層（計画ごとの状態遷移ログ / verdict の判定根拠 / git のステップごとコミットと PR）で残す | どれもブランチ内に閉じるので競合しない。マージ後に main へ積み上がる |
| git worktree は推奨するが強制しない | セッションごとに `CLAUDE_PROJECT_DIR` が別になれば成立する。別クローンでも同じ |
| `/run-queue` は `/run` に改名する | 横断キューが無くなり、名前が実態と合わなくなるため |
| 検証ゲートは変えない（作成→検証の二段、`done` は verdict PASS のみ、Stop フックの強制、6見出し、受け入れ基準3〜7行、役割分離と `vault/rules/`） | ハーネスの価値はキューではなく検証ゲートの側にある。キューを外しても弱くならない |

### 新しいディレクトリ構造

```
vault/
  plans/P-20260919-git-ops.md            計画票（frontmatter status + タスク表）= キュー
  tasks/P-20260919-git-ops/T-01.md       タスク票（6見出しは不変）
  verdicts/P-20260919-git-ops/T-01.json  verdict（形式は不変）
  log/P-20260919-git-ops.md              その計画の状態遷移ログ
  designs/D-001.md                       設計文書（変更なし）
  archive/2026-09/                       旧資産の凍結先
  rules/                                 変更なし
  templates/                             plan.md にタスク表を追加
```

計画票の frontmatter は `id` と `status`（`draft` / `approved` / `done`）。タスク表が5状態（`todo` / `doing` / `review` / `blocked` / `done`）と `attempt` / `question` を持つ。

## フェーズ1 インストール先への更新経路を作る

### ゴール文
`scripts/install.sh` を、2回目以降の実行でもハーネス本体（フック・エージェント定義・スキル・`scripts/`・`docs/vault-spec.md`・テンプレート・標準ルール）をインストール先に届けられるようにする。配ったファイルのハッシュをマニフェストに記録し、更新時に未編集なら上書き、利用者が編集していればスキップして差分を報告する。`.claude/settings.json` は専用マージャで hooks の欠落エントリと `permissions.deny` の不足分だけを足す。

### 受け入れ基準の候補
- `scripts/install.sh` に `--update` が実装され、初回インストール時に配布ファイルのハッシュを `.claude/harness-manifest.json` に記録する。確認：一時ディレクトリに install し、`python3 -c "import json;print(len(json.load(open('<dst>/.claude/harness-manifest.json'))['files']))"` が1以上
- 更新時、インストール先のファイルのハッシュがマニフェストと一致する（未編集）なら上書きし、記録を更新する。確認：install 先のフックを書き換えずに再 install し、`diff <src>/.claude/hooks/stop_gate.py <dst>/.claude/hooks/stop_gate.py` が差分なし
- ハッシュが一致しない（利用者が編集済み）ならスキップし、対象パスを一覧で報告する。確認：install 先の `vault/rules/common/roles.md` に1行足してから再 install し、出力に `skip` と当該パスが出て、足した行が残っている
- 利用者の資産（`vault/plans/`・`vault/tasks/`・`vault/verdicts/`・`vault/log/`・`vault/archive/`・`vault/designs/`・標準4本以外の `vault/rules/`・`settings.local.json`）はマニフェストに含めず、更新の対象にしない。確認：マニフェストの `files` にこれらのパスが1つも含まれない
- `scripts/merge_settings_json.py` が新規に作られ、インストール先の `settings.json` に不足している hooks エントリと `permissions.deny` の要素だけを足す。利用者が追加した `permissions.allow` の要素を消さない。確認：allow に独自行を足した settings.json に対して実行し、その行が残り、欠けていた hooks が追加される
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含む（更新経路とマージャのケースを追加した上で）

### 決定済み
- 上書き対象（ハーネス本体）：`.claude/hooks/*.py`、`.claude/agents/*.md`、`.claude/skills/*/SKILL.md`、`.claude/ai-harness.md`、`scripts/smoke.sh`、`scripts/rules.sh`、`scripts/merge_claude_md.py`、`scripts/merge_settings_json.py`、`scripts/install.sh`、`docs/vault-spec.md`、`vault/templates/*.md`、`vault/rules/README.md`、標準ルール4本（`rules/common/roles.md`・`rules/creator/creator.md`・`rules/verifier/verifier.md`・`rules/planner/planner.md`）
- 絶対に触らない（利用者の資産）：`vault/plans/`・`vault/tasks/`・`vault/verdicts/`・`vault/log/`・`vault/archive/`・`vault/designs/` の中身、標準4本以外の `vault/rules/` 配下、`.claude/settings.local.json`
- マニフェストの置き場は `.claude/harness-manifest.json`。形式は `{"version": "<install した時刻 JST>", "files": {"<相対パス>": "<sha256>"}}`。ハッシュは `hashlib.sha256` の16進
- `--update` を付けない従来の呼び出しは、これまでどおり `copy_if_absent` で振る舞う（初回インストール用）。マニフェストの記録は初回でも行う
- マニフェストが無いインストール先に `--update` した場合は、全ファイルを「編集済み」とみなしてスキップし、差分を報告する（既存の利用者の編集を勝手に潰さないため）
- `settings.json` のマージャは `merge_claude_md.py` と同じ発想で独立した Python スクリプトにする。`hooks` は同じ `command` 文字列を持つエントリがあれば足さない。`permissions.deny` は文字列の集合として不足分だけ足す。`permissions.allow` は読み取るだけで変更しない
- `CLAUDE.md` の扱い（`merge_claude_md.py` と `--no-claude-md`）は変更しない
- このフェーズは旧方式（`vault/todo.md`）のまま実施する。新しい状態モデルには触れない

## フェーズ2 新しい状態モデルの仕様とテンプレートを固める

### ゴール文
`docs/vault-spec.md` を、計画をまたぐキューを持たない新しい状態モデルで書き直す。`vault/todo.md` を廃止し、計画票が状態を持つこと、ID 体系が `P-YYYYMMDD-<slug>` とスコープ付き `T-01` になること、タスク票・verdict・ログが計画スコープのディレクトリに入ること、ブランチ名の導出規則を正本として定義する。`vault/templates/plan.md` を新形式（frontmatter に `status`、本文にタスク表）に更新する。この時点ではコードを変更せず、旧方式が動いたままにする。

### 受け入れ基準の候補
- `docs/vault-spec.md` から `vault/todo.md` を状態の正本とする記述が消え、計画票が状態を持つ旨に置き換わっている。確認：`grep -c 'vault/todo.md' docs/vault-spec.md` が0
- ID 体系の節に、計画 ID `P-YYYYMMDD-<slug>`、タスク ID は計画スコープの `T-` + 2桁、ブランチ名は計画 ID の英小文字化に `work/` を付ける、の3点が書かれている。確認：`grep -c 'P-YYYYMMDD' docs/vault-spec.md` と `grep -c 'work/p-' docs/vault-spec.md` がそれぞれ1以上
- ディレクトリの節が新構造（`vault/tasks/<計画ID>/T-01.md`・`vault/verdicts/<計画ID>/T-01.json`・`vault/log/<計画ID>.md`）を示している。確認：`grep -c 'vault/log/<' docs/vault-spec.md` が1以上
- 計画票の節に frontmatter の `status`（`draft` / `approved` / `done`）とタスク表の列（`id` / `status` / `attempt` / `after` / `title` / `question`）が定義されている
- 検証ゲートの定義（5状態・`done` は verdict PASS のみ・Stop フックの判定表・verdict の形式・受け入れ基準3〜7行・`vault/rules/` の節）が意味を変えずに残っている。確認：`grep -c '## 12. ルール' docs/vault-spec.md` が1以上
- `vault/templates/plan.md` に frontmatter の `status` とタスク表の雛形がある。確認：`grep -c 'attempt' vault/templates/plan.md` が1以上

### 決定済み
- このフェーズは文書とテンプレートだけを変える。フック・スキル・`install.sh` は次フェーズで追従するので触らない。したがって作業中は旧方式（`vault/todo.md`）で run-queue が回り続ける
- 計画票の frontmatter は `id` と `status` の2つ。`status` は `draft`（planner が作った直後）/ `approved`（人が承認）/ `done`（全タスクが done で PR 作成済み）の3値。タスクの5状態とは別系列
- タスク票の6見出し（目的 / 入力 / 成果物 / 受け入れ基準 / 決定済み / 進捗）と verdict の形式（`task` / `attempt` / `result` / `checked_at` / `criteria` / `reasons`）は変更しない。`verdict.task` の値は計画スコープの `T-01` ではなく `<計画ID>/T-01` にする（verdict 単体で計画を特定できるようにするため）
- `vault/log/<計画ID>.md` の1行形式は従来どおり `- YYYY-MM-DD HH:MM T-01 doing→review attempt=1 補足`。計画が特定できるのでタスク ID は短い形でよい
- スラッグは英小文字・ハイフン区切り。人が計画を識別できればよく、厳密な自動生成アルゴリズムは要求しない
- `docs/vault-spec.md` の節番号は振り直してよい。「11. todo_guard フックの判定」は「plan_guard フックの判定」に改める
- 旧方式の記述は残さない（一気に切り替える決定のため、移行期の併記をしない）

## フェーズ3 フックとスキルを新方式に作り替える

### ゴール文
フック3つとスキル2つを、`vault/todo.md` ではなく自分のブランチの計画票を読む形に作り替える。`stop_gate.py` は verdict の形式検査・鮮度・attempt 照合のロジックを保ったまま読む先だけを計画票に変える。`todo_guard.py` を `plan_guard.py` に作り替え、`doing は1件` を計画票スコープで検査する。`agent_write_guard.py` の doing/review 判定も計画票を見る。`/plan` はブランチ作成と計画票生成まで行い、`/run-queue` を `/run` に改名して自分のブランチの計画を進める形にする。

### 受け入れ基準の候補
- `stop_gate.py` が `vault/plans/` から `status: approved` の計画票を1つ見つけ、そのタスク表の `doing`/`review` のタスクと `vault/verdicts/<計画ID>/<タスクID>.json` を照合する。計画票が無い場合は許可（fail-open）。確認：新規 smoke ケースが block と allow の両方で通る
- `stop_gate.py` の判定表（verdict 無し・鮮度不一致・形式不正・FAIL と attempt 上限・PASS だが done でない・PASS かつ done）が意味を変えずに動く。確認：既存の `== stop_gate.py ==` のケースを新形式に書き換えた上で全件通る
- `plan_guard.py` が計画票のタスク表を検査し、`doing` が2件以上・`blocked` で question が空・status が5値以外・id の重複・列数が6でない、をブロックする。確認：新規 smoke ケース5件が block
- `agent_write_guard.py` の doing/review 判定が計画票を読み、`vault/rules/` の改ざん防止と `HARNESS_ALLOW_RULES_WRITE` の解除口が従来どおり効く。確認：既存の `== agent_write_guard.py ==` のケースが新形式で全件通る
- `/plan` がブランチ作成（`work/<計画IDの英小文字>`）と計画票生成まで行い、承認は計画票の frontmatter を `approved` にするだけになる。`vault/todo.md` への登録手順が消えている。確認：`grep -c 'todo.md' .claude/skills/plan/SKILL.md` が0
- `/run`（旧 `/run-queue`）が自分のブランチの計画票からタスクを取り、`vault/log/<計画ID>.md` に追記する手順になっている。確認：`.claude/skills/run/SKILL.md` が存在し、`grep -c 'todo.md' .claude/skills/run/SKILL.md` が0
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- フック改修中は、計画票が見つからない場合をすべて fail-open（許可）にする。旧 `vault/todo.md` へのフォールバックは書かない。これにより、このフェーズの作業中は Stop フックの強制が効かなくなるが、一気に切り替える決定の帰結として許容する
- 「自分のブランチの計画票」の特定方法：`vault/plans/*.md` を走査し、frontmatter の `status` が `approved` のものを取る。複数見つかった場合は計画票が2つ approved になっている異常なので、`plan_guard.py` がブロックする（1ブランチ1計画の不変条件）
- `agent_write_guard.py` の `ALLOWED`（verifier は `vault/verdicts/`、planner は `vault/plans/` と `vault/tasks/`）は変更しない。計画スコープのサブディレクトリも同じ接頭辞の下にあるため、そのまま通る
- セッション同士の踏み込み防止（自分の計画のディレクトリ外への書き込み拒否）は入れない。worktree が別なので物理的に届かず、同一ディレクトリで2セッションを走らせる運用は想定しない
- `/run-queue` は削除して `/run` を新規に作る（リネーム）。旧名のエイリアスは残さない
- `/plan` の承認は引き続き人が行う。`/plan approve` の引数は計画 ID
- `vault/rules/common/roles.md`・`creator/creator.md`・`verifier/verifier.md`・`planner/planner.md` のうち、`vault/todo.md` に言及している箇所を新方式に直す。役割の責務そのものは変えない
- `.claude/agents/planner.md`・`.claude/agents/verifier.md` の ID 採番・出力先の記述を新方式に直す
- 旧資産のアーカイブと `vault/todo.md` の削除は次フェーズで行う。このフェーズでは旧ファイルを残したままにする

## フェーズ4 旧資産を凍結して切り替えを完了する

### ゴール文
既存資産（17計画・29タスク票・29 verdict・`vault/log/queue.md`・`vault/todo.md`）を `vault/archive/2026-09/` に移し、`vault/todo.md` を削除して新方式への切り替えを完了する。`scripts/install.sh` の複製対象とマニフェストを新構造に合わせ、`README.md`・`docs/runbook.md`・`docs/install.md`・`CLAUDE.md`（`.claude/ai-harness.md`）・`docs/decisions.md` を新方式で書き直す。

## 今回やらないこと

- **成果物の衝突を機械で検出する仕組み**。状態ファイルの衝突は設計で消えるが、2つの計画が同じソースファイルを触る衝突は消せない。計画票に「触る主なファイル」を書き、人が承認時に同時実行の可否を判断する運用に留める。警告する仕組みは必要になった時に別の設計文書で扱う
- **既存資産の新形式への変換**。全部 `done` なので凍結する（決定事項のとおり）
- **`git worktree` の自動化**。worktree の作成・削除をスキルが行うことはせず、人が用意する前提にする
- **`gh pr merge` の自動化**。マージは人が行う決定を維持する
- **旧方式との恒久的な互換**。移行中も fail-open で通すだけで、`vault/todo.md` を読むフォールバックは書かない
- **`vault/rules/` のドメイン固有ルール**（コーディングルール・テスト観点など）。拡張ポイントは維持するが、中身はインストール先で書く
- **`HARNESS_ALLOW_RULES_WRITE` がリモートセッションで機能しない件の解決**。この解除口は「フックは Claude Code プロセスの環境を継承するので、エージェントが Bash 内で `export` しても届かない＝実質的に人だけが解除できる」という前提で作られている。リモート実行では人が起動コマンドに環境変数を渡せず、人の操作手段がエージェント経由しかないため、**「人だけが解除できる」を環境変数で表現する方法が存在しない**。ファイルによる解除フラグに変えてもエージェントがそのファイルを作れるので同じ問題が残る。P-021 の T-0051 では「タスクが `todo` のうちに編集し、その後 `doing` にする」という順序で迂回した（人が承認時に明示的に選んだ回避策）。恒久的な解決（署名・別チャネルでの承認・そもそも人の操作を前提にしない設計など）は別の設計文書で扱う
