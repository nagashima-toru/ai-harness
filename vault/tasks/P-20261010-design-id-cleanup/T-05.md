## 受け入れ基準

## 決定済み
- 追記する5行（列は `| 日付 | 何を | なぜ |`。日付はすべて `2026-10-10`）。「何を」の書き出しは次の語句に固定し、続けて内容を書く。各行の「何を」の末尾に `（D-016）` を付ける：
  1. `PR の直前に計画一式を除去する`：run の手順7で PR を作る直前に計画一式4種（`vault/plans/<計画ID>.md`・`vault/tasks/<計画ID>/`・`vault/verdicts/<計画ID>/`・`vault/log/<計画ID>.md`）を `scripts/purge_plan.sh` で除去し、`main` には入れない。計画ブランチの中では従来どおり git で管理する。取り出しと除去はオーケストレーターが行う。`vault/harness-improvements/` は対象外。なぜ：ブランチ内では worktree・`transition.py` のコミット・フックが vault/ の git 管理を前提にしており、`.gitignore` で管理外にすると大改修になる。PR の前に除去すれば古い情報が `main` に溜まらない（人の選択）。creator は `vault/plans/`・`vault/log/`・`vault/verdicts/` を変更できず、計画票と log に書くのは元からオーケストレーターだけ
  2. `証跡は PR に残す`：PR 本文に計画のゴール・タスク表・log の全行・verifier の指摘を写し、タスク票と verdict の中身は PR のコミット履歴から辿る。なぜ：整合性と承認の履歴が要るのはマージまでで、マージ後に参照するのは PR だけで足りる（人の情報）
  3. `取り出しの置き場は`：恒久的な仕様・判断は `docs/`（判断は `docs/decisions.md`）に追記し、未解決のこと・改善提案は Issue にする。なぜ：人の選択。run 手順8（振り返りの Issue 化）と同じ扱いにそろえる
  4. `設計文書は最終フェーズで削除する`：`/design` は最終フェーズの受け入れ基準に「決定事項のうち docs に無いものを `docs/decisions.md` に追記し、設計文書を削除する」を必ず入れる。既存の設計文書（旧方式の D-001〜D-016）も削除した。なぜ：設計文書は全フェーズを `/plan` に渡すまで `main` に要るが、最後のフェーズが終われば読まれない。既存の分の削除は人の選択
  5. `設計文書の ID は `D-<YYYYMMDD>-<スラッグ>``：ブランチは `design/d-<YYYYMMDD>-<スラッグ>`。D-016 が旧方式（`D-` と3桁の番号）の最後。なぜ：設計文書を削除すると既存の最大値に1を足す採番が崩れ、過去の番号と衝突する。計画 ID と同じ日付＋スラッグなら状態ファイル無しで重複しない
- archive の廃止と一括削除を人が実行することは、既存の 2026-10-10 の `scripts/archive_plans.sh` の廃止の行に記録済みなので、新しい行を足さない。既存の行は書き換えない
- 5行は表の末尾（現在の最後の行 `P-20261010-purge-prereq` の後ろ）に、上の番号の順で足す
- 表の中で `|` を値に使わない（列が崩れるため）。改行も入れない（1件1行）
- 受け入れ基準2の文は、5番目でなく4番目の行にだけ書く（`grep -cF` が `1` になるように、ほかの行に同じ文を重ねない）
- `docs/decisions.md` は参照切れ検査（smoke の refcheck）の対象外だが、パスは実在するものか `<...>` の形で書く
- 過去の行にある `D-0xx` への言及は書き換えない
