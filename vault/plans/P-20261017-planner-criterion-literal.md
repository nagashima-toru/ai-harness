# ゴール
GitHub Issue #204「planner が受け入れ基準の grep 文字列と「決定済み」の置換文言を食い違わせる」を解決する。

導入先の計画で、T-03 の受け入れ基準が `grep -c -F '{Xxx}JobConfig。命名は方式設計 §11' docs/coding-standards.md` が `1`、「決定済み」の置換文言が「`{Xxx}JobConfig`。命名は方式設計 §11」（バッククォートあり）だったため、creator が決定済みどおりに書くと基準が通らず blocked になった。planner が「決定済み」の文言から grep の文字列を抜き出す時に、Markdown のバッククォートを落とす食い違いを、仕組み（plan_guard フック）で止め、planner の指針と経緯集にも書き方を残す。

## 分割方針
- 原則2（仕組みで強制）を優先し、`.claude/hooks/plan_guard.py` に検査を足す（T-01）。draft の計画のタスク票への Write・Edit の後に、受け入れ基準の grep の文字列が「決定済み」「成果物」の行にはそのまま当たらず、バッククォートを除くと当たる時だけ止める。
- 「決定済み」に無い文字列を一律に止める案は採らない。過去の計画のタスク票158件（git の履歴から取り出したもの）で試したところ、`-F` の固定文字列112件のうち20件は「決定済み」「成果物」に無かった（残っていないことの確認・既存ファイルの文言・コマンドの出力を見る基準など、正しい基準）。一律に止めると誤検知が約2割になる。バッククォートの有無だけで食い違う形に絞った試作では、158件で誤検知0件、Issue の例は検出した。
- Issue の提案の「`-F` とシングルクォートの中にバッククォートをそのまま書く」は採らない。planner.md の「grep パターンにシェルの特殊文字（バッククォートを含む）を入れない」と矛盾するため。代わりに、バッククォートをまたがない部分文字列を選ぶか、バッククォートを `.` に置き換えた（`-F` を付けない）パターンにする書き方を、既存の `.` 置換の箇条と整合させて書く（T-02）。
- Issue の提案の「決定済みの文言を一時ファイルに書いて試走する」は、planner が `vault/plans/`・`vault/tasks/` 以外に書けないため手順にしない。plan_guard の検査がその試走を機械で行う。
- 検査は grep という汎用の道具だけを見て、ドメイン知識を持たない（原則7）。`.claude/skills/plan/SKILL.md` の手順5は変えない（planner と orchestrator のタスク票の Write・Edit で plan_guard が動くため）。
- T-02 は T-01 の検査を前提に書くので `after` で T-01 に依存させる。
