# T-02 run/SKILL.md の手順3（blocked・記録行）と手順4（review）を transition.py に置き換える

## 目的
`.claude/skills/run/SKILL.md` の手順3の 6〜8（分岐元の不一致の blocked・再開情報の記録行の追記・creator の blocked 報告）と手順4（review にする）を、T-01 の早見表の2・3の呼び出しに置き換える。これで、creator の完了直後に worktree の未コミット分の収集コミットと差分ゲートが行われ、verifier はコミット済みの worktree を検証するようになる。

## 入力
- `.claude/skills/run/SKILL.md`（T-01 で足した早見表と、手順3・手順4）
- `scripts/transition.py`（docstring の `--worktree` の review・blocked）
- `docs/vault-spec.md` 2節（worktree 運用の review・blocked）・7節（再開情報の記録行は transition.py が書く）
- `vault/designs/D-012.md` の「フェーズ5」の決定済み
- 呼び出しの形の確認に使ってよいフィクスチャ：`vault/tasks/P-20261007-transition-worktree/fixtures/try.sh`（preset `rev`・`revx`・`rev0`・`blk`。成果物ではない）

## 成果物
- `.claude/skills/run/SKILL.md`（このファイルだけ）

## 決定済み
- 呼び出しの文字列は T-01 の早見表と同じものを使う（プレースホルダ `<計画ID>`・`<id>`・`<worktree>`・`<branch>`・`<PLAN_HEAD>`・`<質問ファイル>`）。早見表そのものは変えない
- 手順3の1〜5（PLAN_HEAD を控える・creator を `isolation: "worktree"` で呼ぶ・並行呼び出し・worktree のパスとブランチ名を保持・分岐元の確認）は変えない。ただし3.4の「手順3.7で `vault/log/<計画ID>.md` に記録して再開に使う」は「review・blocked の呼び出しで transition.py が再開情報の記録行を log に書く」に直す
- 3.6（分岐元が計画ブランチと一致しない）：自分で起点を上書きしない方針は残し、状態の変更は「質問文（確認コマンドの出力の要点を含む）を一時ファイルに書いて、3.8 と同じ呼び出しで blocked にする」と書く。呼び出しの文字列は3.8 に1回だけ書き、3.6 からは参照する（基準2が手順3の中で `1` と数えるため）
- 3.7（再開情報の記録行の手動の追記）は消す。記録行は transition.py の review・blocked が遷移の行の直前に同じ日時で書く（`docs/vault-spec.md` 7節）。記録行の書式（`plan_head=<sha>` など）を手順3・4に書かない（再開で記録行を読む説明は手順2の2にあり、T-04 で直す）
- 3.8（creator の報告が「blocked: <質問文>」の時）：質問文を言い換えずに Write ツールで一時ファイル（例：`/tmp/<計画ID>-<id>-question.txt`）に書き、`python3 scripts/transition.py <計画ID> <id> blocked --question-file <質問ファイル> --worktree <worktree> --branch <branch> --plan-head <PLAN_HEAD>` を id ごとに1回呼ぶ。worktree は transition.py が残す。終了コードは4（blocked にした）が正常。選んだタスクの中に blocked 以外が無ければここで終わる
- 手順4：blocked ではない完了報告を受けたタスクについて、id ごとに1回ずつ、計画票のタスク表の上から順に `python3 scripts/transition.py <計画ID> <id> review --worktree <worktree> --branch <branch> --plan-head <PLAN_HEAD>` を呼ぶ（並行に呼ばない）。この1回で、worktree の未コミット分の収集コミット・新規コミットの判定・差分ゲート・再開情報の記録行・doing→review とそのコミットが行われる、と1〜2文で書く
- 手順4の終了コードごとの次の行動：
  - 0：review になった。手順5で verifier を呼ぶ対象にする
  - 3：差分ゲートの違反で差し戻した（doing のまま attempt+1。worktree は破棄済み）。標準出力の1行を完了報告に写し、手順3の1から PLAN_HEAD を取り直して、その id の creator を呼び直す（transition.py のコミットで計画ブランチの HEAD が進むため取り直す）
  - 4：blocked にした（新規コミット無し、または差し戻しが上限）。標準出力の1行を完了報告に写し、その id を終える。worktree は残っている
  - 1・2：早見表の終了コードの表のとおり（人に報告して止める／呼び出しを直す）
- 手順4の今の「この反映もこの時点でコミットする。手順5で verifier が…コミットされていない変更は…verifier から見えない」の説明は、「creator の成果物は review の呼び出しで worktree 側にコミット済みになり、verifier はそれを検証する」という内容に置き換える
- 表を直接書き換える言い回し（「status を `blocked` にし」「question 列に…書き写す」など）と log の行のひな形（`- <日時> <id> doing→review ...` など）を手順3・4に書かない。`creator=<モデル>` の記録は transition.py が自動で付けるので、手順3・4には書かない（0.5節にある）
- 手順5〜8・「ハング時の復旧」・「回帰確認」・「注意」・手順2はこのタスクでは変えない。途中の版では手順6.3.1（PASS の時の収集）が残るが、review の呼び出しで収集済みなので「残りが無ければ何もしない」で済み、矛盾しない
- 「終了コード」の表（`| 0 |`〜`| 4 |` の行）を手順4に新しく作らない（行頭が `| <数字> |` の行は早見表の5行だけ）。手順4の終了コードは箇条書きで書く
- `scripts/smoke.sh`・`scripts/transition.py`・`docs/vault-spec.md`・`.claude/agents/verifier.md` は変えない
