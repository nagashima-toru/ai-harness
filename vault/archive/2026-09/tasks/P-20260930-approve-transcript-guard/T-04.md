# T-04 plan_guard.py で作業ツリーの計画票を HEAD と比べて承認の裏付けを検査し smoke.sh にテストを足す

## 目的
PreToolUse（T-03）は Write/Edit/MultiEdit だけを見るので、Bash（`sed -i`・リダイレクトなど）による draft→approved の書き換えが漏れる。PostToolUse の plan_guard が、作業ツリーの計画票を `git show HEAD:<path>` と比べて同じ判定を行い、裏付けが無ければブロックして元に戻すよう指示する。会話記録が読めない時は警告に落とす（D-010 フェーズ4、決定事項の #75）。

## 入力
- `vault/designs/D-010.md` の決定事項（#75・会話記録が読めない時の警告）とフェーズ4の決定済み
- `.claude/hooks/plan_guard.py`：`main()`（粒度検査 `granularity_violation`・`plan_size_violation` の後、`approved_plans` の判定より前に置く）、`plan_id_and_status`、`project_dir`、`block`、`delegate_to_worktree`
- `.claude/hooks/agent_write_guard.py` の T-03 で足した会話記録の解析関数（規則をコピーする）
- `scripts/smoke.sh` の `== plan_guard.py ==` 節（`run_plan_guard_file`）と T-03 で足した `make_transcript`

## 成果物
- `.claude/hooks/plan_guard.py` の変更と `scripts/smoke.sh` への回帰テスト追加（1PR分の関連する2ファイル変更）

## 受け入れ基準
- git フィクスチャ（HEAD で draft の計画票をコミット済み）で、作業ツリーの計画票を Bash で approved に書き換えた後、会話記録に `/plan approve P-TEST` が無ければ plan_guard が `{"decision": "block", ...}` を返し、reason に計画 ID と `git restore` を含む。確認：`bash scripts/smoke.sh` の出力に `ok   (approve-post)` で始まる該当ケースがあり `NG` が無い
- 同じ状況で、会話記録の人の発言に `/plan approve P-TEST` があればブロックしない。tool_result・`isMeta: true` の行にしか無い場合と、別の計画 ID のコマンドだけの場合はブロックする（同上）
- 会話記録が読めない時（`transcript_path` が無い・ファイルが無い・どの行も JSON でない・人の発言が1件も無い）はブロックせず、標準出力の JSON の `hookSpecificOutput.additionalContext` に警告を出す（同上）
- HEAD で既に approved の計画票（承認直後のコミット済み）、draft のまま、HEAD が無い・未追跡の計画票（HEAD では approved でない扱い）、非 git ディレクトリの各場合が、仕様どおりに判定される（承認済みは検査しない・非 git は何もしない）（同上）
- 既存の plan_guard のケース（approved 計画のタスク表検査・粒度検査）の結果が変わらない。確認：`bash scripts/smoke.sh > /tmp/P-20260930-approve-transcript-guard-T-04-smoke.txt 2>&1` の後 `grep -c '^  NG' /tmp/P-20260930-approve-transcript-guard-T-04-smoke.txt` が `0`、`tail -1 /tmp/P-20260930-approve-transcript-guard-T-04-smoke.txt` が `smoke: pass=<N> fail=0`

## 決定済み
- 検査の対象：`vault/plans/*.md` のうち、作業ツリーの frontmatter の status が approved のもの。HEAD の版（`git show HEAD:vault/plans/<ファイル名>`）の frontmatter の status が approved でなければ「今回承認された」とみなす。HEAD の取得失敗（HEAD 無し・未追跡）は「HEAD では approved でない」として扱う。非 git ディレクトリ（`git rev-parse --is-inside-work-tree` が失敗）では何もしない。git は `cwd=root` で `subprocess` から呼び、タイムアウトを付ける（既存の `git_toplevel` の呼び方に合わせる）
- 同じ承認に何度も当たらない：承認は直後にコミットされる（T-05）ので、コミット後は HEAD も approved になり検査対象外になる
- 裏付けの判定：T-03 と同じ規則（人の発言＝`type` が `user`・`message.content` が文字列・`isMeta` が真でない行。スラッシュコマンド形式か文形式。計画 ID は完全一致）。フック間で import しない既存方針のため、解析関数を `plan_guard.py` にコピーする。`agent_type` は PostToolUse の入力には無いので見ない
- 「会話記録が読めない」の定義は T-03 と同じ。読めない時はブロックせず警告に落とす。警告は `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "additionalContext": "..."}}` を標準出力に1回だけ出す（文言に計画 ID と「会話記録が読めないため承認の裏付けを検査できませんでした」を含める）。警告は変数に保持し、既存の検査（タスク表・粒度）がブロックしなかった場合だけ、終了前に出力する（block が出る時は block を優先し、JSON を2つ出さない）。そのため `main()` の終了経路（`sys.exit(0)`）をまとめる小さな関数を作ってよい
- 裏付けが無い時のブロックの reason：`[plan_guard] <計画ID> が draft から approved に書き換えられていますが、人の /plan approve <計画ID> の指示が会話記録にありません。git restore vault/plans/<計画ID>.md で元に戻してください（承認は人が /plan approve <計画ID> で指示した時だけ行えます）。`
- 挿入位置は既存の粒度検査・行数検査の後、`approved_plans` の判定より前。既存の approved 計画の検査は変えない
- `delegate_to_worktree` は既存のまま。委譲後も同じ判定が働く
- 新規の計画票（HEAD に無く、未追跡）を最初から approved で作る書き込みも「HEAD では approved でない」に当たるので、裏付けが必要になる
- smoke.sh の git フィクスチャは、`/tmp/P-20260930-approve-transcript-guard-T-04-repo`（固定パス。`mkdir -p` で作り、既存の内容を無条件に使わないよう `git init` し直す）で作る。`git -c user.name=t -c user.email=t@example.com commit` でコミットする。後片付けに `rm -rf` は使わない。ケース接頭辞は `(approve-post)`
- 会話記録は T-03 の `make_transcript` を流用する。フックの入力には `transcript_path` を含める
