# ゴール
`/design` スキルはブランチを切らずに `vault/designs/D-xxx.md` を書くが、`agent_write_guard.py` は
現在のブランチが `main` の時に `git commit` を拒否するため、設計文書単体を正規の手順でコミットする
経路が存在しない（GitHub issue #4）。`/design` にも `/plan` と同様のブランチ運用（`main` から
`git checkout -b design/d-xxx` を切り、そのブランチ上でコミットし、`gh pr create` で PR を作って人が
レビュー・マージする）を導入し、`docs/vault-spec.md` 第13節・`.claude/skills/design/SKILL.md`・
`vault/templates/design.md` を揃える。あわせて、`/design` が生む各フェーズは独立した `/plan`→`/run`
→PR で単体マージされる実行単位であることを踏まえ、「そのフェーズだけが単体で `main` にマージされて
もシステムが動作する状態を保証する」という受け入れ基準の質を明文化する。最後に、実際にテストブラン
チで一連の操作（ブランチ作成→ファイル作成→コミット）が `agent_write_guard.py`・`stop_gate.py` に阻
害されないことを確認する。

## 分割方針
人との検討で以下が決定済み（再検討不要。各タスク票の「決定済み」に転記する）。
- ブランチ名は `design/d-xxx`（`xxx` は D-ID の3桁を小文字化。例：D-002 → `design/d-002`）。`main`
  から切る
- マージは `gh pr create` まで（`/plan` の `run` が最後に作る PR と同じ運用）。`gh pr merge` はエー
  ジェントが実行しない
- 設計文書は全フェーズ分を一括で1回の PR で `main` にマージする（フェーズ単位で分割マージしない）。
  マージのタイミングはフェーズ1の実装着手前
- `/plan` 側は変更しない（既存の「現在のブランチが `main` か確認してから `work/...` を切る」手順の
  まま）
- 各フェーズの受け入れ基準の質として「そのフェーズだけが単体で `main` にマージされてもシステムが動
  作する状態を保証する内容にする」を明記する

タスクへの割り方：
- T-01（`docs/vault-spec.md` 第13節）：上記の運用と受け入れ基準の質を仕様の正本に書く「契約」タス
  ク。他タスクが参照する文言のもと
- T-02（`.claude/skills/design/SKILL.md`）：T-01 の内容を手順として実装する。ただし決定事項は本計
  画票・タスク票にすべて転記済みで、T-02 の作業に必要な文言は独立に確定できるため、`after` は付けず
  並行実行を妨げない
- T-03（`vault/templates/design.md`）：見出し構成に変更が必要か確認し、必要なら受け入れ基準の候補
  の説明文に1文加える。単独ファイル・独立作業
- T-04（`scripts/smoke.sh`）：実装コード（`agent_write_guard.py`）の変更は不要という想定を、実際に
  一時 git リポジトリで再現して検証し、回帰防止のテストケースとして固定する。他タスクの成果物を読ま
  なくても実行できるため独立
- 4タスクとも成果物ファイルが異なり、内容は本計画票の決定事項から一意に定まるため、`after` はすべ
  て `-` とした（循環なし）。次フェーズの候補は無い（今回のゴールで完結する）
