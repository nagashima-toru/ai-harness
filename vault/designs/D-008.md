# ゴール

`EnterWorktree` で分離実行された verifier / creator が `.claude/hooks/` 配下のスクリプト自体を成果物として検証する時、`PreToolUse`（`agent_write_guard.py`）・`PostToolUse`（`plan_guard.py`）・`Stop`（`stop_gate.py`）の3フックはいずれも Claude Code が固定パス `${CLAUDE_PROJECT_DIR}/.claude/hooks/<name>.py` で実行するため、worktree 内で直しているはずのコードが反映されず、メインリポジトリ側の未修正コードがそのまま動く（issue #56）。3フックそれぞれに、呼び出し元セッションの `cwd` が worktree を指している場合はそのルート配下にある同名スクリプトへ委譲する仕組みを入れ、この構造的欠陥を解消する。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| `agent_write_guard.py`・`plan_guard.py`・`stop_gate.py` の3フックすべてに委譲ロジックを入れる（2フェーズに分割） | `${CLAUDE_PROJECT_DIR}` 固定パス実行という同じ構造的欠陥が3フックに共通するため。放置すると `.claude/hooks/` 配下のどれかを変更するタスクのたびに issue #56 と同種の不具合が個別に起き、その都度場当たり的対応が必要になる（人の回答） |
| 委譲（subprocess 実行）自体が失敗・タイムアウトした場合はフェイルオープンでメインリポジトリ側のロジックにフォールバックする | 既存コードの `git_toplevel()` 等が採るフェイルオープンの方針と一貫させるため。委譲は「worktree 側の新しい判定を反映する」ための追加経路であり、この経路自体の不調で worktree 内の全ツール呼び出しが止まる方が影響が大きい。安全側の判定（`vault/rules/` 改ざん防止・`main` 直接コミット拒否等）はメインリポジトリ側のコードでも変わらず効くため、フォールバックしても丸腰にはならない（人の回答） |
| 委譲するかどうかの判定は `payload["cwd"]` の `git rev-parse --show-toplevel` だけで行う（`agent_write_guard.py` の `resolve_root()` が Write/Edit で使う「書き込み対象ファイルのパス起点」のルート解決とは別軸） | 委譲の目的は「このフック呼び出しを発火させたセッションが今どの worktree にいるか」であり、個々の書き込み対象がどのリポジトリに属すかとは別の問い。`Stop`/`PostToolUse` ペイロードには対象ファイルパスの概念自体が無く、`cwd` が唯一共通して使える手がかりでもある（調査に基づく設計判断） |
| 委譲ロジックは共有モジュールに切り出さず、3ファイルそれぞれに複製する | `stop_gate.py` に既存の「`plan_guard.py` と同じ規則をこのファイル内にコピーして使う（import はしない）」という確立された流儀に合わせる（調査に基づく設計判断） |
| 委譲は1段まで（環境変数で二重委譲を防止） | worktree のネストは現状の運用で想定しておらず、委譲先がさらに委譲を試みる無限再帰を機械的に防ぐ（調査に基づく設計判断） |
| 委譲は「フックのコード」をどこから読むかだけを切り替える。`vault/plans`・`vault/verdicts` 等のデータをどのディレクトリから読むか（`project_dir()`/`resolve_root()` の `CLAUDE_PROJECT_DIR` 優先の解決順序）は変更しない | issue #56 の症状は「フックのコードが古い」ことであり、「読んでいるデータが古い」ことではない。今回の対象タスク（`.claude/hooks/` 配下を成果物とするタスク）では worktree 側の `vault/` データはメインリポジトリと同一であることが前提になっており、データ解決順序の見直しは別問題（調査に基づく設計判断） |

## 依存関係

フェーズ1（`agent_write_guard.py`）→ フェーズ2（`plan_guard.py`・`stop_gate.py`）。フェーズ2はフェーズ1で確立した委譲の実装パターン（関数の形・フェイルオープンの扱い・環境変数による二重委譲防止）をそれぞれのファイルに複製するだけなので、フェーズ1のマージ後に着手する。

## フェーズ1 agent_write_guard.py の worktree 委譲

### ゴール文

`.claude/hooks/agent_write_guard.py` に、PreToolUse 呼び出しの `payload["cwd"]` が git worktree を指している場合はそのルート配下の `.claude/hooks/agent_write_guard.py` へ委譲する（委譲先の stdout をそのまま自分の stdout として出し `exit 0` する）ロジックを追加する。委譲先が存在しない・委譲の実行自体が失敗/タイムアウトした場合は、フェイルオープンで既存のローカル判定（メインリポジトリ側のコード）にフォールバックする。委譲は1段までとし、二重委譲を環境変数で防止する。既存の判定ロジック（`vault/rules/` 改ざん防止・`main` 直接コミット拒否・verifier/planner/creator の書き込み先制限等）は変更しない。

### 受け入れ基準の候補
- `.claude/hooks/agent_write_guard.py` に worktree 委譲用の関数（例：`delegate_to_worktree`）が実装されている（`grep -n "def delegate_to_worktree" .claude/hooks/agent_write_guard.py` で確認）
- 委譲しない通常経路（非 worktree）で `bash scripts/smoke.sh` の既存ケースが全件 PASS する（回帰が無いこと）
- `git worktree add` 等で作った一時 worktree に、判定結果が変わるよう改変した（例：常に allow を返す）`agent_write_guard.py` を置き、`cwd` をその worktree に向けた PreToolUse 相当のペイロードをメインリポジトリ側の `agent_write_guard.py` の標準入力に渡して実行すると、worktree 側の改変後の判定（allow）が返る（確認手順をテストスクリプトとして用意して実行する）
- 委譲先 subprocess を異常終了・タイムアウトするよう仕込んだ場合に、メインリポジトリ側の既存ロジックへフォールバックし、通常どおりの判定（例：`vault/rules/` 改ざん防止が変わらず効く）が返る（同様にテストで確認）
- 委譲先スクリプトが再度委譲を試みない（環境変数等で二重委譲を防止していることをコードで確認できる）こと

### 決定済み
- 委譲判定は `payload["cwd"]` の git toplevel のみで行う。Write/Edit の対象ファイルパス起点のルート解決（`resolve_root()`）は変更しない
- 委譲失敗時はフェイルオープン（メインリポジトリ側のロジックにフォールバック）
- 委譲ロジックはこのファイル内に閉じて実装する（他ファイルへの import はしない）
- `subprocess.run` のタイムアウトは、`settings.json` 側のフック全体タイムアウト（30秒）より短い値（例：20秒）にする
- 委譲先には同じ payload を JSON で再シリアライズして渡す（標準入力は一度読み切っているため）

## フェーズ2 plan_guard.py・stop_gate.py への同パターン展開

### ゴール文

フェーズ1で `agent_write_guard.py` に実装した worktree 委譲ロジック（`payload["cwd"]` の git toplevel が自リポジトリと異なれば、そのルート配下の同名スクリプトへ委譲し、失敗時はフェイルオープンでフォールバックする）と同じパターンを `.claude/hooks/plan_guard.py`・`.claude/hooks/stop_gate.py` それぞれに複製して実装する。既存の判定ロジック（タスク表整合性チェック・verdict 検証等）は変更しない。

### 受け入れ基準の候補
- `plan_guard.py`・`stop_gate.py` の双方に worktree 委譲用の関数が実装されている（`grep -rn "def delegate_to_worktree" .claude/hooks/plan_guard.py .claude/hooks/stop_gate.py` で確認、各ファイルに1件ずつヒットする）
- 通常経路（非 worktree）で `bash scripts/smoke.sh` の既存ケースが全件 PASS する（回帰が無いこと）
- 一時 worktree に判定結果が変わるよう改変した `plan_guard.py` を置き、`cwd` をその worktree に向けたペイロードをメインリポジトリ側の `plan_guard.py` に渡すと、worktree 側の改変後の判定が返る（`stop_gate.py` についても同様に確認）
- 委譲先 subprocess が異常終了・タイムアウトする場合にフェイルオープンでメインリポジトリ側ロジックへフォールバックする（`plan_guard.py`・`stop_gate.py` それぞれで確認）

### 決定済み
- フェーズ1と同じ実装パターン（関数の形・フェイルオープン・環境変数での二重委譲防止）をそのまま複製する。共通化のための新規モジュール切り出しはしない
- `plan_guard.py`・`stop_gate.py` 内の既存の `project_dir()`（`vault/plans` 等データ読み込み先の解決）は変更しない。委譲はコードの実行先を切り替えるだけで、データ解決順序には触れない

## 今回やらないこと

- issue #56 の提案2（verifier 向けの手作業代替手順を `vault/rules/verifier/` 等に正式な代替手順として明文化すること）：本設計で根本原因（委譲でコードの鮮度を揃える）を直すため、通常のケースでは不要になると判断した。委譲後もなお verifier が手作業代替を要する場面が見つかれば、その時に別途扱う
- `EnterWorktree` の `path` 引数で複数 worktree を行き来するケースの専用テスト：委譲判定は呼び出しごとに `cwd` から動的に求めるため理論上は追随するが、そのシナリオに特化した検証はフェーズ1・2には含めない
- `plan_guard.py`・`stop_gate.py` の `project_dir()` が持つ「`CLAUDE_PROJECT_DIR` を worktree の `cwd` より優先する」というデータ解決順序自体の見直し：issue #56 の症状（フックのコードが古い）とは別の問題であり、今回はコードの実行先切り替えだけを扱う。データ解決順序の妥当性は必要になった時に別の設計文書で扱う
