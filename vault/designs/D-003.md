# ゴール
`run` スキル（issue #9）が、計画のタスク表で `after` 依存の無い（＝互いに依存しない）`todo` タスクを直列にしか処理できない制約を外し、複数タスクを並行して着手・作成・検証できるようにする。「1セッション=1計画=1ブランチ」の枠は変えず、並行ワーカーは Agent ツールの `isolation: "worktree"` で計画ブランチから分岐した隔離コピー上で作業させ、計画票・ログという共有可変ファイルへの書き込みはオーケストレーター（`run` のメインセッション）1プロセスに集約することで、書き込み競合を運用ルールではなく構造で消す。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| `.claude/ai-harness.md` の「`doing` は計画内で常に1件だけ」を「`doing`/`review` は複数件になりうるが、その全ては依存関係の無い集合（着手可能集合）に限り、計画票・ログへの書き込みは常にオーケストレーター1プロセスに集約する」に変更する | 人の判断（並行実行を許すモデルへの変更を承認）。書き込みを1プロセスに集約すれば、複数エージェントが同じファイルに同時に書く場面自体が発生しない |
| 並行タスクの作業隔離は Agent ツールの `isolation: "worktree"` を使う。自前で `git worktree add/remove` を管理しない | 人の判断（推奨案を採用）。既存ツールがまさにこの用途向けに用意されている。生成された worktree のパス・ブランチが呼び出し結果に返るため、後続のマージ・検証で使える |
| 並行数の上限は環境変数 `HARNESS_MAX_PARALLEL`（既定 3）で設定可能にする | 人の判断（推奨案を採用）。既存の `HARNESS_MAX_ATTEMPTS` と同じパターンで一貫性がある |
| verifier もこの設計から並行呼び出しにする（`creator` の並行完了ごとに、対応する verifier をまとめて並行起動する） | 人の判断。verdict はタスクごとに独立したファイル（`vault/verdicts/<計画ID>/<id>.json`）で競合しないため、逐次に留める技術的理由が無い |
| `creator`（run の「作る」パート）を `.claude/agents/creator.md` のサブエージェントとして切り出す。挙動そのもの（受け入れ基準の確認・進捗の書き方）は現行 `run/SKILL.md` の手順3・4を踏襲する | 並行実行するには Agent ツールで複数回同時に呼べる単位が要る。現行は「作る」がメインセッションに内蔵されており、複数同時には呼べない |
| `creator` は `vault/plans/` と `vault/log/` への書き込みを常に拒否される（`agent_write_guard.py` に verifier/planner と同様のハード制限を追加。成果物パスそのものは制限しない） | 計画票のタスク表とログは共有可変ファイルなので、書き込みはオーケストレーターに一本化する。ルール文書だけで守らせる（creator/creator.md に書くだけ）より、フックで機械的に塞ぐ方が並行時の事故を構造的に防げる。成果物は repo 全体に及びうるため verifier/planner のような許可リスト方式は使わず、この2パスだけを明示的に拒否する |
| 並行タスクの verifier は、通常の（非 worktree）Agent 呼び出しとして起動し、プロンプトで対象 worktree のパスを渡す。verifier は `EnterWorktree(path=...)` でその worktree に入ってから検証し、`vault/verdicts/<計画ID>/<id>.json` を書く | `EnterWorktree` は既存 worktree への再入場をサポートし、「pinned agent からの切り替えはそのエージェントだけに効く」ため、verifier が creator と同じ隔離ブランチを見て判定できる。Agent ツールの `isolation: "worktree"` 自体は呼び出しごとに新規 worktree を作るため、verifier 用に流用できない |
| worktree ブランチの計画ブランチへの取り込みは、対象タスクの verifier が PASS を返した後、オーケストレーターが `git merge --no-ff <worktree のブランチ>` を計画ブランチ上で**タスクごとに逐次**実行する。マージでコンフリクトが起きたタスクは自動解決せず `blocked` にし question に状況を書く。他の並行タスクの処理には影響させない | 複数マージを同時に行うとマージ自体が競合しうるため、マージだけはオーケストレーターが1件ずつ順番に行う（着手・作成・検証は並行、状態への反映は逐次、という役割分担）。コンフリクト時に自己判断で解決しないのは既存の `vault/rules/creator/git-workflow.md` の方針をそのまま踏襲 |
| 着手可能集合が1件しかない（＝並行化の余地が無い）場合も同じ経路（creator/verifier をサブエージェント化した経路）を通す。専用の「逐次フォールバック」コードパスは作らない | 分岐を減らし、1件の時も複数件の時も同じ仕組みで動くことを保証する。テストする経路が1つで済む |

## フェーズ1 状態遷移ルールの緩和とフックの整合性検査更新

### ゴール文
`.claude/ai-harness.md` と `docs/vault-spec.md` の状態遷移の記述を、「`doing` は計画内で常に1件だけ」から「`doing`/`review` は複数件になりうるが、その全ては `after` 依存の無い集合に限り、計画票・ログへの書き込みは常にオーケストレーター1プロセスに集約する」に書き換える。`.claude/hooks/plan_guard.py` の「doing が2件以上ならブロック」判定を、「doing/review の集合内に `after` 依存関係が張られていたらブロック」判定に置き換える。`.claude/hooks/stop_gate.py` の「doing/review のタスクは1件だけ想定」というロジック（`next(...)` で1件だけ取り出す部分）を、doing/review の全行をそれぞれ検査するループに変更する。この時点では `run` スキル自体はまだ1タスクずつ逐次処理を続けており、実際に複数タスクを同時に doing にする機能はまだ入れない（フックとルール文書だけを新しい前提に合わせる）。

### 受け入れ基準の候補
- `.claude/ai-harness.md` の「状態遷移」節から「doing は計画内で常に1件だけ」という文言が消え、依存の無い集合に限る旨と、書き込みをオーケストレーターに集約する旨が書かれている。確認: `grep -c "常に1件" .claude/ai-harness.md` が0
- `docs/vault-spec.md` の該当箇所（2節の状態表、9節 Stop フック、10節 plan_guard フック）が同様に更新されている
- `plan_guard.py` が、doing/review の複数行が `after` 依存関係を持たない場合はブロックしない。依存関係がある場合（例: doing の T-02 の `after` に、done でない T-01 が含まれる）はブロックする。確認: 依存の無い2行が doing の計画票と、依存のある2行が doing の計画票をそれぞれ用意し、`plan_guard.py` に標準入力で渡して判定を確認する（`python3 .claude/hooks/plan_guard.py` に該当 payload を渡す手動確認、または既存の `scripts/smoke.sh` に同様のケースがあればそれで代替）
- `stop_gate.py` が doing/review の全行をそれぞれ検査し、いずれか1件でも verdict 不備があればブロックする（1件だけ検査して残りを見落とさない）
- 単一タスクのみが doing/review の既存シナリオでの `stop_gate.py`／`plan_guard.py` の判定結果が、変更前と変わらない（回帰確認）

### 決定済み
- 「依存関係が張られている」の判定は、doing/review の行の `after` 列に、まだ `done` になっていない他の doing/review 行の id が含まれるかで見る（後方参照だけでなく、doing 同士の相互依存も含めて検出する）
- ログ・計画票のフォーマット（列構成・見出し）は変えない。変わるのは状態遷移の許容範囲の文言と、それを検査するロジックだけ
- `HARNESS_MAX_PARALLEL` 環境変数の導入はこのフェーズでは行わない（フェーズ3で導入する）

## フェーズ2 creator のサブエージェント化

### ゴール文
`run` スキルの「3. 作る」「4. review にする」に相当するロジックを `.claude/agents/creator.md` という新しいサブエージェント定義に切り出す。`creator` はタスク ID だけを受け取り、タスク票を読み、`bash scripts/rules.sh creator` が列挙するルールを読み、成果物を作り、確認コマンドを実行し、タスク票の「進捗」に記録して完了を報告する（現行 `run/SKILL.md` 手順3と同じ内容）。ただし計画票のタスク表（`vault/plans/<計画ID>.md`）と `vault/log/<計画ID>.md` への書き込みは行わない（`todo→doing`・`doing→review` の状態更新とログ追記はオーケストレーター側の役目にする）。`.claude/hooks/agent_write_guard.py` に、`agent_type == "creator"` の時は `vault/plans/` と `vault/log/` への書き込みを常に拒否するハード制限を追加する（`vault/rules/` に対する既存の改ザン防止と同じパターン）。`.claude/skills/run/SKILL.md` を、オーケストレーターが状態を `doing` にしてログ追記した後に Agent ツールで `creator` を1回呼び、完了報告を受けたら `review` にしてログ追記する、という流れに書き換える。並行実行はまだ入れず、着手可能な `todo` を1件ずつ処理する現行の逐次フローを維持する。

### 受け入れ基準の候補
- `.claude/agents/creator.md` が存在し、frontmatter に `name: creator` と `tools` があり、本文が現行 `run/SKILL.md` の手順3（作る）の内容（決定済み優先・ルール読み込み・確認コマンド実行・進捗記録）を引き継いでいる
- `agent_write_guard.py` に `agent_type == "creator"` かつ対象が `vault/plans/` または `vault/log/` の書き込みを拒否する分岐がある。確認: `agent_type` を `creator`、書き込み先を `vault/plans/P-xxx.md` にした payload を標準入力で渡すと deny が返る
- `.claude/skills/run/SKILL.md` の手順が、状態更新（`todo→doing`・`doing→review`）とログ追記をオーケストレーター（run 自身）が行い、成果物作成だけを Agent ツール経由の `creator` に委譲する形に書き換わっている
- 既存の1タスクずつの逐次フロー（着手可能な todo が1件のケース）で、状態遷移・ログ・成果物作成の結果が変更前と同じになる（回帰確認：既存の計画・タスクで一連の流れを手動またはスクリプトで確認）
- `vault/rules/creator/creator.md` の記述（「状態を変えたら vault/log に追記する」等）が、新しい役割分担（オーケストレーターが状態・ログを書く）と矛盾しないよう更新されている

### 決定済み
- `creator` の書き込み先は成果物パス（タスクによって repo 全体になりうる）と `vault/tasks/` に限定しない。`vault/plans/` と `vault/log/` だけを明示的に拒否する（verifier/planner のような許可リスト方式ではなく拒否リスト方式にする）
- `creator` は「進捗」の追記まで行ってよい（`vault/tasks/<計画ID>/<id>.md` は書き込み可）。拒否されるのは `vault/plans/` と `vault/log/` のみ
- verifier の呼び出し方（タスク ID だけを渡す）はこのフェーズでは変えない。フェーズ3で worktree 対応の変更を入れる

## フェーズ3 並行実行オーケストレーション

### ゴール文
`run` スキルに、計画票のタスク表から「着手可能集合」（`todo` かつ `after` が全て `done`）を求め、環境変数 `HARNESS_MAX_PARALLEL`（既定 3）を上限にタスクを選ぶ手順を追加する。選んだタスク全部をまとめて1回の書き込みで `doing` にし、`vault/log/<計画ID>.md` に1回（または選んだタスク分まとめて）追記する。その上で、選んだタスクそれぞれについて Agent ツールで `creator` を `isolation: "worktree"` 付きで並行起動する（1メッセージで複数呼び出し）。各呼び出しの結果からタスクごとの worktree パス・ブランチを受け取る。次に、完了した creator それぞれについて verifier を並行起動する。verifier は通常（非 worktree）の Agent 呼び出しとし、プロンプトでタスク ID と対象 worktree のパスを渡し、verifier は `EnterWorktree(path=...)` でその worktree に入ってから検証して `vault/verdicts/<計画ID>/<id>.json` を書く。全 verifier の完了後、オーケストレーターはタスクを1件ずつ逐次処理する：PASS なら該当 worktree のブランチを計画ブランチへ `git merge --no-ff` し、成功したら計画票を `review→done` にしてログ追記し worktree を削除する。マージでコンフリクトが起きたら該当タスクを `blocked` にし question にコンフリクトの状況を書き、worktree は削除せず残す。FAIL なら計画ブランチへはマージせず、attempt 上限未満なら `doing`（attempt+1）に、上限到達なら `blocked` にし、いずれもログに追記する（worktree は次の attempt で再利用するか、破棄して次の attempt 時に作り直すかは実装時に decide しやすいようここでは規定しない）。着手可能集合が1件しかない場合も同じ経路（creator/verifier サブエージェント + worktree）を通す。

### 受け入れ基準の候補
- `run/SKILL.md` に「着手可能集合」の算出手順（`after` が全て `done` な `todo` 行を列挙）と、`HARNESS_MAX_PARALLEL`（既定3、未設定時の既定値を明記）による上限の適用手順が書かれている
- 選んだタスクを `doing` にする計画票への書き込みが1回にまとまっている手順として明記されている（タスクごとに書き込みを分けない）
- `creator` を `isolation: "worktree"` で並行起動する手順と、`verifier` を対象 worktree に `EnterWorktree(path=...)` で入ってから検証する手順がそれぞれ明記されている
- PASS 時の worktree ブランチのマージ・`review→done`・ログ追記・worktree 削除の手順、コンフリクト時の `blocked` 化の手順、FAIL 時の attempt 更新の手順がそれぞれ明記されている
- 着手可能集合が1件だけの場合に、この経路を通しても最終的な計画票・ログ・成果物の状態がフェーズ2までの逐次フローと同じ結果になることが確認できる手順（回帰確認）が書かれている
- `worktree` の分岐元がこのリポジトリの計画ブランチになる（`origin/main` ではない）ことを確認する手順が明記されている（`isolation: "worktree"` の分岐元設定の確認方法を含む）

### 決定済み
- verifier は worktree を新規作成しない。creator の呼び出し結果で得た既存 worktree のパスに `EnterWorktree(path=...)` で入る
- マージは常にオーケストレーターが計画ブランチ上でタスクごとに逐次実行する。複数タスクのマージを同時に行わない
- コンフリクト時は自己判断で解決せず `blocked` にする（`vault/rules/creator/git-workflow.md` の既存方針を踏襲）。他の並行タスクの処理は止めない
- `HARNESS_MAX_PARALLEL` は `HARNESS_MAX_ATTEMPTS` と同じ環境変数パターンで導入する（既定 3、`.claude/ai-harness.md` または `docs/vault-spec.md` に既定値を明記する）
- `isolation: "worktree"` の分岐元が計画ブランチになっていることの確認方法（設定項目名やコマンド）は実装時に調査して確認手順を書く。分岐元が `origin/main` 相当になってしまう場合は、実装タスクの中でその調整方法も決める

## 今回やらないこと
- 複数「計画」をまたぐ並行実行（D-001 の「1セッション=1計画=1ブランチ」設計により、別計画は別ブランチ・別セッションで既に並行できているため対象外）
- 並行数の動的な調整（負荷・コストに応じた自動スケーリング等）。`HARNESS_MAX_PARALLEL` は固定の環境変数のみ
- worktree 作成やマージの失敗に対する自動リトライ・高度な復旧戦略。失敗時は `blocked` にして人に委ねる方針のみ
- planner がタスク票やタスク表に「並行可能グループ」を事前に注釈する機能。着手可能集合は `run` が実行時に `after` から動的に計算するため不要と判断
