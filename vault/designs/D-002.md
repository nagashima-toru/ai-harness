# ゴール
`vault/rules/` の改ざん防止（`.claude/hooks/agent_write_guard.py`）にある `HARNESS_ALLOW_RULES_WRITE` による「人だけが解除できる」という前提を、人の操作（起動時の環境変数）を経由しない設計に置き換える。エージェントは `vault/rules/` に一切書き込めないことにし、ルール変更を成果物とするタスクは提案ファイル（`vault/rules/` の外）に下書きし、実体への反映は人が手作業で行う。これによりローカル・リモートどちらのセッションでも同じ保証が成り立ち、`todo` のうちに編集してから `doing` にする順序迂回も同時に塞がれる（issue #1）。

## 決定事項

| 決めたこと | なぜ |
|---|---|
| 人の操作を前提にしない設計に変える。`HARNESS_ALLOW_RULES_WRITE` による環境変数の明示解除は廃止する | リモートセッションでは人が起動コマンドに環境変数を渡せず、「人だけが解除できる」を表現する手段が無い。ローカル/リモートで挙動が変わらない設計にする |
| `agent_write_guard.py` の `vault/rules/` 拒否判定は、タスクが `todo`/`doing`/`review` のいずれであっても、承認済み計画の有無に関わらず常時ブロックにする（状態を問わない） | 「`doing`/`review` 中だけ拒否」という条件があると、`todo` のうちに編集して `doing` にする順序迂回が成立してしまう（P-021/T-0051 で実際に人が選んだ回避策）。常時ブロックにすればこの迂回自体が構造的に無くなる |
| ルール変更を成果物とするタスクは、実パスではなく `vault/tasks/<計画ID>/<id>-proposal.md` に内容を書く。verifier はこの提案ファイルを検証する | エージェントの下書き機能は残しつつ、`vault/rules/` への実書き込み権限だけをエージェントから完全に外せる。提案ファイルは `vault/rules/` の外なので既存の拒否判定に抵触しない |
| 提案ファイルから実体（`vault/rules/` 配下）への反映は人が手作業で行う。反映作業の自動化・スキル化は今回のスコープに含めない | 今回のゴールは「エージェントが直接書けないこと」の保証。反映の自動化は別の設計判断（署名や別チャネル承認と同様、恒久策の一部だが今回は扱わない） |
| リポジトリ外チャネルでの承認、署名・コミット単位の検証は今回は採用しない | 新しい外部連携や署名基盤が要り、実装コストに見合わない。「人の操作を前提にしない」を満たす別解が提案ファイル方式で足りる |

単一フェーズ。並行なし。

## フェーズ1 agent_write_guard の無条件ブロック化と提案ファイル方式への移行

### ゴール文
`.claude/hooks/agent_write_guard.py` から `HARNESS_ALLOW_RULES_WRITE` による明示解除の仕組み（環境変数の読み取り、`rules_write_allowed`、`doing`/`review` の有無による条件分岐）を削除し、`vault/rules/` への書き込みをタスクの状態や計画の有無に関わらず常にすべてのエージェント（メインエージェント含む）に対して拒否するように変える。`docs/vault-spec.md` 第12節を、新しい「提案ファイル方式」（ルール変更を成果物とするタスクは `vault/tasks/<計画ID>/<id>-proposal.md` に下書きし、verifier がそこを検証し、実体への反映は人が手作業で行う）を正本として書き直す。`vault/rules/creator/` と `vault/rules/planner/` に、ルール変更が成果物のタスクをこの方式で扱う旨の指示を追記する。

### 受け入れ基準の候補
- `.claude/hooks/agent_write_guard.py` から `HARNESS_ALLOW_RULES_WRITE` / `rules_write_allowed` に関する記述が消えている。確認：`grep -c HARNESS_ALLOW_RULES_WRITE .claude/hooks/agent_write_guard.py` が0
- `vault/rules/` への書き込み拒否判定が、`doing`/`review` の有無や承認済み計画の有無を条件にせず常に発火する。確認：計画が無い（`vault/plans/` が空、または全計画が `approved` でない）状態でも `vault/rules/` 配下への `Write` ツール呼び出しが拒否される（手動確認または smoke.sh のケースで）
- `docs/vault-spec.md` 第12節が提案ファイル方式（成果物パスを `vault/tasks/<計画ID>/<id>-proposal.md` にする、verifier はそこを検証する、実体への反映は人が手作業で行う）を記述し、`HARNESS_ALLOW_RULES_WRITE` への言及が消えている。確認：`grep -c HARNESS_ALLOW_RULES_WRITE docs/vault-spec.md` が0
- `vault/rules/creator/` 配下のいずれかのファイルに、ルール変更が成果物のタスクは提案ファイルに書く旨の指示が追記されている
- `vault/rules/planner/` 配下のいずれかのファイルに、ルール変更が成果物のタスクを計画する際は成果物欄を提案ファイルパスにする旨の指示が追記されている
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- 提案ファイルの命名・置き場は `vault/tasks/<計画ID>/<id>-proposal.md` に固定する。複数のルールファイルにまたがる変更は、成果物を1つに保つ既存原則（`vault/templates/task.md` の「成果物」）に従ってタスクを分割する
- `HARNESS_ALLOW_RULES_WRITE` はコードからもドキュメントからも完全に削除する。過去のログ（`vault/log/`）や過去の verdict は書き換えない（`done` の編集禁止に従う）
- 提案ファイルから実体への反映手順は `docs/vault-spec.md` に書くだけで、それを行うスクリプトやスキルは作らない
- `plan_guard.py` 側の変更は不要（この変更は `agent_write_guard.py` と `docs/vault-spec.md`、`vault/rules/` の指示ファイルだけで完結する）
- 既存の `scripts/smoke.sh` に `HARNESS_ALLOW_RULES_WRITE` を使ったケースがあれば新ロジックに合わせて更新する。対応するケースが無ければ、新規追加はこのタスクの必須範囲に含めない（あれば望ましいが、無くても受け入れ基準は満たせる）

- 既存の `HARNESS_ALLOW_RULES_WRITE` を使った過去の運用記録（ログ・verdict・issue 本文）の遡及的な書き換え
