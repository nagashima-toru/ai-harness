# ゴール

`run` スキルの手順6（verdict に従う → PASS 時のマージ）で、creator が対象タスクの成果物をコミットせずに完了報告した場合（`vault/rules/common/git.md` の既存方針「git のコミットはタスク票の受け入れ基準に含まれている場合だけ行う」に従った結果、受け入れ基準にコミット明記が無いタスクでは必ず発生する）、マージ対象ブランチに新しいコミットが無いため `git merge --no-ff` が `Already up to date.` で正常終了し、成果物が計画ブランチに一切取り込まれないまま処理が進みかねない問題（GitHub Issue #32）を直す。

`P-20260924-vcs-finish` の全5タスク（T-01〜T-05）で実際に発生し、その都度オーケストレーターが手動で気づいて worktree 内で成果物をコミットしてから merge し直すことで凌いだ経緯がある。

対応方針は issue #32 の2案を両方組み合わせる（issue 本文も「どちらの案でも安全策をあわせて入れることが望ましい」としている）。
1. マージ直前に、対象 worktree に未コミットの変更が残っていればオーケストレーターがその場でコミットしてから `git merge --no-ff` する
2. 1.を経てもなお対象タスクの worktree のブランチに計画ブランチ分岐時点（`PLAN_HEAD`）からの新規コミットが無い場合を異常として検知し、その対象タスクを `blocked` にして人に確認する

2.の「誤検知（本当に差分ゼロだった場合との区別）」は、1.のコミット手順を必ず先に実行することで解消する：1.を経てもなお新規コミットが0件ということは、staged・unstaged・untracked のいずれの差分も無く、かつ worktree 側で独自のコミットも積まれていない状態を意味する。この harness のタスク粒度の前提（`docs/vault-spec.md` 8節「成果物が1つに特定できる」）では、PASS した以上は何らかのファイル差分を伴う成果物があるはずなので、1.を経た上での新規コミット0件は常に異常とみなしてよいと判断した。この判断（例外を設けず常に blocked にする）は設計判断のため、下記「人への質問」で確認を求める。

対象外（このタスクではやらない）：
- `creator`（`.claude/agents/creator.md` / `vault/rules/creator/`）側の「受け入れ基準に無ければコミットしない」という既存方針そのものの変更
- `vault/rules/common/git.md` の変更（前提として読むが変更しない）
- `docs/vault-spec.md` の変更（マージ手順の実装詳細は同ファイルに記載が無く、スコープ外）

## 分割方針
issue #32 の2つの対応案は、同じファイル（`.claude/skills/run/SKILL.md`）の同じ手順（手順6 の PASS 分岐）に対する一体の安全策であり、2案目は1案目のコミット手順があって初めて誤検知を避けられる（分割方針の理由は上記「誤検知」段落のとおり）。`P-20260924-write-guard-tmp-scope` 等の前例（1本のバグ修正で完結するスコープは契約/実装に分けず1タスクにする）にならい、本計画は1タスク（T-01）のみで構成する。受け入れ基準は7行に収まる見込みのため、分割の必要は無い。
