## 反映後の該当ファイル全文（参考。この形で `vault/rules/planner/planner.md` を上書きすることを想定）

```markdown
## 目的
計画エージェント（planner）が何を作り、何を作らないかを定める。
状態遷移・ファイル形式は `docs/vault-spec.md`、役割間の受け渡しは `vault/rules/common/roles.md` を正本とし、ここでは繰り返さない。

## ルール

**責務**
- ゴールを1コンテキストで終わるタスクに割る（受け入れ基準3〜7行、成果物1つ、人手1〜2時間相当）。
- 計画 ID は `P-YYYYMMDD-<slug>`（採番不要）、タスク ID は計画スコープの `T-01`〜。ID の衝突判定・採番は行わない（`/plan` スキルが決めた計画 ID をそのまま使う）。
- タスク票の6見出しをすべて埋め、「決定済み」には creator が聞きそうなことを先回りで書く（「進捗」は空のまま）。
- 型・API・テスト雛形などの契約タスクを先に切り、実装タスクを `after` でそれに依存させる。
- 1計画は5〜7タスクまで。超える分は計画票末尾に「次フェーズの候補」として書くだけにし、票を起こさない。
- 書き込むのは `vault/plans/` と `vault/tasks/` だけ。承認（`status` を `approved` にすること）は人が行う。
- 計画票の `status` は `draft` のままにする。自分で `approved` にしない。
- 不明点が出てもゴールを広げない。計画票末尾の「## 人への質問」に列挙して人に返す。
- ルール変更（`vault/rules/` 配下のファイル）を成果物とするタスクを計画する時は、タスク票の『成果物』を実体パスではなく `vault/tasks/<計画ID>/<id>-proposal.md` にする。受け入れ基準の確認コマンドも、実体ではなく提案ファイルを対象にする（`agent_write_guard.py` が実体パスへの書き込みを常に拒否するため）。

**やらないこと（このリポジトリで実際に起きた失敗から）**
- run が必ず変えるファイル（計画票のタスク表・`vault/log/<計画ID>.md`・タスク票の「進捗」）の差分不変を受け入れ基準にしない。
  状態ファイルへの `git diff --quiet` を基準にしたため T-0002 が blocked になった（旧方式での失敗例）。
  形式の不変を見たい時は見出し行・列構成に限定する。例：`git diff -- vault/plans/<計画ID>.md | grep -E '^[+-](## |\| id )'` の出力が空。
- 語を数えるだけの緩い確認コマンドを書かない。
  T-0016 の `grep -c 'planner' <file>` が1以上、は「planner を呼ばない」と書けていなくても通ってしまう。
  数えるのではなく、検査したい文言・構造そのものに一致するパターンを書く。
- 成果物本文に無い文字列を grep する受け入れ基準を書かない。
  T-0012（`vault/rules`）・T-0013（「## 構成」ツリーの `rules.sh`）では、基準を通すために creator が後から文言を足す羽目になった。
  grep する文言は、そのタスク票の「成果物」か「決定済み」で「この語を書くこと」と明示する。
- 確認コマンドを、自分で読み取り専用で実行しないまま受け入れ基準に書かない。実行して初めて緩さや期待値の食い違いに気づく。
- 他タスクの成果物ファイルを変更していないことを確認する受け入れ基準の確認コマンドは、`git diff main -- <path>` ではなく `git status --porcelain`（成果物パス以外に変更が無いことを確認する形）で書く。
  `run`/`vault/rules/common/git.md` の運用は1計画=1ブランチに複数タスクを完了順に `git merge --no-ff` で逐次マージしていくため、後続タスクの検証時点では先行タスクの変更が既に計画ブランチに含まれている。この状態で `git diff main` を使うと、後続タスクが変更していないファイルまで（先行タスク由来の差分として）非空になり誤検知する。
  `P-20260925-worktree-baseref-merge` の T-01・T-03 では、この形（`git diff main -- ...` が空）で書かれた基準が字句どおり機能せず、過去2回 verifier が自力に `git status --porcelain` 等の代替確認に切り替えて正しく PASS 判定した（issue #42）。
- 機能テストの受け入れ基準で、一時ディレクトリの後片付けに `rm -rf` を使うことを前提にしない。
  `.claude/settings.json` の `permissions.deny` に `Bash(rm -rf *)` 系パターンがあり、`mktemp -d` で作った一時ディレクトリを確認コマンドの中で `rm -rf` で消す書き方は実行できない。
  `mktemp -d` で毎回新しい場所を作る代わりに、`/tmp/<計画ID>-<タスクID>` のように計画・タスク ID を含む固定パスにし、テスト開始時に `mkdir -p` で作り直す（既存内容を無条件に使う前提にしない）ことで、後片付け無しでも安全に運用できる。
  `P-20260925-vcs-finish-push-and-diff-criteria` の T-01 では、タスク票の確認コマンドが `$(mktemp -d)` と事前の `rm -rf` 前提で書かれていたため、verifier が `.claude/settings.json` の `permissions.deny`（`Bash(rm -rf *)`）に阻まれ、その場で固定パス `/tmp/vftest_a`・`/tmp/vftest_b`・`/tmp/vftest_c` に書き換えて回避した（issue #46）。
- 受け入れ基準に併記する確認コマンドを、パイプ・`&&`・コマンド置換（`$(...)` 等）で組み合わせた複合コマンドにしない。
  Claude Code のツール実行時サンドボックス（worktree 隔離のための git コマンド安全性チェック）が、そのような複合コマンドを「即時拒否」または「無応答ハング」のどちらかで止めることがある（issue #46, #48）。
  対象は "git" という語を含む場合に限らない。issue #48 では、`&&` 連結や、末尾に `git status --porcelain | grep` を含む長い複合コマンドでもハングが再現しており、`rm -rf` 前提を禁じた既存項目（一時ディレクトリの後片付け）とは別に、複合コマンド全般を対象にする必要がある。
  代替として、確認コマンドは素朴な単一コマンドに分解するか、事前にファイルへ書き出してから読み取る（例：先に `> /tmp/<計画ID>-<タスクID>.txt` へリダイレクトし、別コマンドで `grep` する）形にする。
- 「成果物は `<ファイル>` のみで、他ファイルは変更していない」という形の受け入れ基準を書く時は、確認コマンドの除外パスに成果物だけでなく**タスク票自身のパス**（`vault/tasks/<計画ID>/<id>.md`）も含める。
  creator は doing 中にタスク票自身の「進捗」節へ追記するため（`docs/vault-spec.md` 5節）、タスク票自身を除外しないと、成果物の出来に関わらず確認コマンドが毎回非空になり必ずFAILする。`P-20260925-sandbox-hang-timeout`/T-01 ではこの形の基準が3回連続でFAILし、人が個別に確認コマンドを修正してから再開した（issue #51）。
  代替として、このパターンの受け入れ基準自体を書かず、`vault/rules/verifier/verifier.md` に既にある**起点コミット**ベースの検査（creator が「進捗」に `起点コミット: <hash>` を記録し、verifier が `git diff --name-only <起点コミット>..HEAD` で宣言外ファイルの変更を検出する仕組み。計画票・タスク票の「進捗」・`vault/log/`・`vault/verdicts/` は自動的に除外される）に委ねることも検討してよい。ただしこれは creator が起点コミットを記録した場合のみ有効なため、確実性を重視する場合は除外パス方式を優先する。
- コード変更を伴う受け入れ基準では、`grep` 等による単語の出現有無・出現回数だけを唯一の確認コマンドにしない。
  文字列が意図しない場所（コメント・無関係な条件分岐・ログ出力等）に置かれただけでもマッチしてしまい、出現有無・出現回数のチェック単独では実際の動作を保証しない。
  `P-20260926-fix-smoke-sh-failures`/T-03・T-04 の受け入れ基準1（`grep -n "worktrees" <file>` の出力が1行以上）で、verifier が「単語の出現回数のみを見る緩い基準で、単独では実際の除外動作を保証しない」と指摘した（今回は後続の基準が機能検証を兼ねていたため実害なし、issue #68）。
  grep で存在確認する基準を書く場合は、対象コマンドを実際に実行し期待どおりの動作・実行結果になることを確認する基準を必ず併記する。

## 確認方法
- 各受け入れ基準の確認コマンドを planner 自身が読み取り専用で実行でき、期待値が一意に決まるか。
- grep する文言が、そのタスク票の「成果物」か「決定済み」で明示的に要求されているか。
- run で必ず差分が出るファイルの不変検査が、受け入れ基準に混ざっていないか。
- `after` の依存に循環が無く、1計画のタスク数が7以下か。
- 各タスクの成果物が1つに特定できるか（「〜を改善」のような書き方になっていないか）。
- ルール変更が成果物のタスクで、成果物欄を実体パスではなく `vault/tasks/<計画ID>/<id>-proposal.md` にしているか。
- 他ファイル不変の基準が `git status --porcelain` ベース（成果物パス以外に変更が無いこと）になっているか。
- 機能テストの後片付けが `rm -rf` 前提になっていないか（固定パス＋`mkdir -p` 上書き運用になっているか）。
- 確認コマンドがパイプ・`&&`・コマンド置換を含む複合コマンドになっていないか（素朴な単一コマンドか、事前書き出し＋読み取りの形になっているか）。
- 「成果物のみで他ファイル不変」の基準を書く時、除外パスにタスク票自身が含まれているか、または起点コミットベースの検査に委ねているか。
- コード変更を伴う受け入れ基準で、単語の出現有無・出現回数の確認だけを唯一の確認コマンドにしていないか。実際の入出力・実行結果を確認するコマンドが併記されているか。
```
