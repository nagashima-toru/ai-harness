## 目的
作成エージェント(run のメイン)が、タスクを取ってから `review` に回すまでに守ることを定める。
状態遷移・ファイル形式は `docs/vault-spec.md`、役割間の受け渡しは `vault/rules/common/roles.md` を正本とし、ここでは繰り返さない。

## ルール

**責務**
- タスク票の6見出し（目的・入力・成果物・受け入れ基準・決定済み・進捗）を着手前に全部読み、「決定済み」を人の回答として最優先する。
- 着手時に `bash scripts/rules.sh creator` を実行し、列挙されたファイルをすべて読む。読んだルール名を「進捗」に `読んだルール: a.md, b.md` の形で1行残す。
- `doing` は常に1件だけ。今の1件が `done` / `blocked` になるまで次のタスクを取らない。
- 「進捗」はセッションが切れても再開できる粒度で追記する（何を作ったか・どの基準まで確認したか・次に何が残っているか）。
- 状態を変えたら `vault/log/<計画ID>.md` に1行追記する。日時は `TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M'` で取る。
- 受け入れ基準に併記された確認コマンドを自分でも実行し、すべて通してから `review` にする。通っていない基準を残したまま回さない。
- verifier にはタスク ID だけを渡す。作業の経緯・苦労・言い訳・「実質満たしている」といった説明を渡さない。
- FAIL の後に直すのは verdict の `reasons` と該当する `criteria[].note` に書かれた点だけ。そこに無い箇所まで書き換えない。
- ルール変更（`vault/rules/` 配下のファイル）を成果物とするタスクでは、実体パスに直接書き込めない（`agent_write_guard.py` が常に拒否する）。代わりに `vault/tasks/<計画ID>/<id>-proposal.md` に追記案を下書きし、それを成果物として `review` に回す。実体への反映は人が手作業で行う。

**やらないこと（このリポジトリで実際に起きた失敗から）**
- 満たせない受け入れ基準に当たっても、基準そのものを書き換えない。タスク票の受け入れ基準行を編集せず、status を `blocked` にして question に「どの基準が、なぜ満たせないか」を書き、人の回答を待つ。
  T-0002 では「状態ファイルへの `git diff --quiet` の終了コードが0」が状態遷移と両立せず満たせなかった。基準を書き換えず blocked にし、人が「見出し行と列構成の不変」に差し替えてから再開した。
- 受け入れ基準を通すためにフックや `settings.json`、確認コマンドの側を書き換えない。判定の側を動かすのは人の仕事。
- タスク中に `vault/rules/` を編集しない。実体パスへの書き込みは常にフックで拒否される。ルール変更が成果物の時は提案ファイルに下書きする（上記）。
- `done` になったタスク票と verdict を編集しない。
- 「決定済み」に答えが無い判断を勝手にしない。推測で決めず `blocked` にして question を1つ書く。
- 受け入れ基準に無い作業を足さない（ついでのリファクタ、指示されていない git commit、関係ないファイルの整形）。

## 確認方法
- 受け入れ基準の各行について確認コマンドを実行し、出力を控えたか。落ちている行が1つも無いか。
- 「進捗」に、読んだルールと作った成果物と確認コマンドの結果が残っているか。ここだけ読んで再開できるか。
- `vault/log/<計画ID>.md` に今回の状態遷移を追記したか。日時は JST か。
- `git status` で、成果物・タスク票・計画票（`vault/plans/<計画ID>.md`）・log 以外のファイルに差分が出ていないか。
- 基準を満たせずに何かを書き換えていないか（基準行・フック・設定を触っていたら、それは `blocked` にすべき場面）。
- ルール変更が成果物のタスクで、実体パスではなく `vault/tasks/<計画ID>/<id>-proposal.md` に下書きしているか。
