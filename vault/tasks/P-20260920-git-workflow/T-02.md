## 目的
作成エージェント（creator）だけに渡す、git 運用の具体的な手順（ブランチ・コミット・PR のタイミングと例外時の振る舞い）を定める。

- ブランチを切るタイミング（`/plan` 時に既に切られており、作成エージェントは自分では切らない）の記述がある。確認：`grep -c '/plan' vault/rules/creator/git-workflow.md` が1以上

## 決定済み
- 盛り込む内容（この4点をそのまま手順として書けばよい。原則の理由は `vault/rules/common/git.md` に譲り、ここでは「いつ・何をするか」に絞る）
  1. ブランチを切るタイミング：`/plan` 実行時に人が指示してブランチ（`work/<計画IDの英小文字>`）が作られている。作成エージェントは自分でブランチを切らない・切り替えない
  2. コミットのタイミング：作業ステップごと（例：タスクの成果物を書いた直後、計画票やタスク票の状態を更新した直後）に、小さくコミットする
  3. PR を作るタイミング：計画票の全タスクが `done` になった時点で `gh pr create` までを行う。それより前に PR を作らない
  4. 例外時の振る舞い：`git commit`/`git push` がコンフリクトや拒否で失敗した場合、自己判断で解決しようとせず、対象タスクを `blocked` にし question に状況（コマンドとエラーの要点）を書いて止まる
- このファイル自体が `vault/rules/` 配下のため、`doing`/`review` 中は `agent_write_guard.py` が書き込みを拒否する。このタスクが `doing` の間は人が `HARNESS_ALLOW_RULES_WRITE=T-02 claude` で起動している前提で進める。deny された場合、リモートセッションでその解除口が使えないなら、過去の回避策「`todo` のうちに内容を編集し、その後 `doing` にする」を使ってよい（それでも deny される場合は `blocked` にして人に報告する）
- T-01（`common/git.md`）と内容が重複しないよう、原則（なぜ）は書かず、手順（いつ・何を）に絞る
