## 目的

## 決定済み
- 実装位置は `find_done_task_write` の Bash 分岐だけ。既存の `if not any(re.search(p, masked) for p in BASH_WRITE_PATTERNS): return None` の直後（またはその中）に「git add / git commit のみのコマンドか」を判定する関数（例：`is_git_stage_or_commit_only(cmd)`）を呼び、真なら `return None` にする。`BASH_WRITE_PATTERNS`・`targets_vault_rules`・`targets_creator_denied_paths`・`main()` の判定順序・verifier/planner 向けの ALLOWED 判定は変更しない（vault/rules/ 保護や creator の `vault/plans/`・`vault/log/` 拒否、verifier の Bash 制限は従来どおり効く。除外するのは done 判定だけ）
- 「git add / git commit のみ」の判定は、`shlex.split(cmd, posix=True, punctuation_chars=True)` でクォートを解釈したトークンに分け、`;`・`&&`・`||`・`|`・`&` のトークンでセグメントに区切って行う（実装方法は creator が選んでよいが、下記の挙動を満たすこと）。除外が成り立つのは次を全て満たす時：
  1. コマンド文字列に改行・`$(`・バッククォート・`<(`・`>(` を含まない（含む場合は除外しない＝従来判定。commit メッセージ内のコマンド置換で書き込みを隠せないようにするため）。`shlex` が例外（クォートの閉じ忘れ等）を出した場合も除外しない
  2. 全セグメントが、(a) 先頭2トークンが `git`・`add` または `git`・`commit` のセグメント、または (b) 書き込み動詞を含まないセグメント（`git status`・`git diff`・`echo ok` のような、`BASH_WRITE_PATTERNS` から `git add`/`git commit` の分を除いたパターンのどれにもマッチしないセグメント）のいずれか
  3. (a) のセグメントが、リダイレクト演算子のトークン（`>`・`>>`・`>&`・`<` などクォート外の `<`/`>` を含むトークン）を持たない
  - 1つでも満たさなければ除外せず、従来どおりのパス抽出と done 判定に進む（fail-closed）
- 混在の扱い：`git add x && echo x > vault/verdicts/P-FIX/T-01.json`・`git add x && sed -i ... <done verdict>`・`git add x; cp /tmp/y vault/verdicts/P-FIX/T-01.json`・`git rm <done verdict>`・`git checkout -- <done タスク票>` のように、`git add`/`git commit` 以外の書き込み動詞（`git rm`/`git mv`/`git restore`/`git checkout`/`git reset` 等を含む）が1つでも混ざれば除外せず、従来どおり拒否する
- commit メッセージ中のパス文字列：`git commit -m "add vault/verdicts/P-FIX/T-01.json"` の引用符内の文字列は書き込み対象ではないので許可する（shlex がクォートを1トークンにまとめるので、上の判定に自然に乗る）。メッセージに `>` や `;` が含まれていても、引用符内なら演算子として扱わない。ただし `vault/rules/` へのパス文字列を含むコマンドは、従来どおり `targets_vault_rules`（この関数の外）が先に拒否する。これは変更しない
- 対象外にするのは「Bash の `git add` / `git commit`」だけ。Write/Edit/MultiEdit/NotebookEdit の done 判定は一切変えない。`git -C <dir> add ...` のように `git` の直後が `add`/`commit` でない形は除外の対象にしない（従来どおり判定する。run/SKILL.md 手順6.3.4 が使う形はメインリポジトリでの `git add <パス>...`／`git commit -m "..."`）
- main ブランチ上の直接コミット拒否（`main()` 冒頭の `GIT_COMMIT_PATTERN` 判定）は、この変更と無関係に従来どおり効く。smoke のフィクスチャ（`$TMP`）は非 git ディレクトリなので `current_branch` は None になり影響しない
- docstring：`agent_write_guard.py` 冒頭の「done タスクへの書き込み拒否」の段落に、「Bash の書き込み動詞が `git add`/`git commit` だけのコマンドは対象外（ステージ・コミットは内容を変えないため。混在は従来どおり拒否）」を数行で追記する
- smoke.sh の追加ケース（名前は `(done-write)` 接頭辞。既存の `P-FIX` フィクスチャ〔T-01=done〕をそのまま使い、既存7件の直後に置く。`run_guard` の入力 JSON には root 相対パスを使い、既存ケースの書式に合わせる）。許可＝`expect_guard ... allow`、拒否＝`expect_guard ... deny ... "done"`：
  - 許可：メインの `git add vault/verdicts/P-FIX/T-01.json vault/plans/P-FIX.md`（issue #84 再現）／メインの `git commit -m "P-FIX/T-01: done"`／`agent_type=creator` の `git add vault/verdicts/P-FIX/T-01.json`／メインの `git add vault/verdicts/P-FIX/T-01.json && git commit -m x`／メインの `git commit -m "add vault/verdicts/P-FIX/T-01.json"`（メッセージ中のパス）
  - 拒否（reason に done）：`git add x && echo x > vault/verdicts/P-FIX/T-01.json`／`git add x && sed -i s/a/b/ vault/verdicts/P-FIX/T-01.json`／`git add x; cp /tmp/y vault/verdicts/P-FIX/T-01.json`／`git rm vault/verdicts/P-FIX/T-01.json`／`git commit -m "$(echo x > vault/tasks/P-FIX/T-01.md)"`
  - 既存7ケースは変更・削除しない（既知の総数は pass=168。新規10件で pass=178 になる想定だが、件数が増減しても `fail=0` と `168 + 追加数` が一致すれば良い）
- JSON 中の `"` や `$(` は、既存ケースと同様にシェルのシングルクォート内で `\"` にエスケープして渡す。`→` のような非 ASCII 文字は smoke のケースでは使わなくてよい（`done` などの ASCII で足りる）

- コミットは、実装（`agent_write_guard.py`）とテスト（`scripts/smoke.sh`）を分けて行ってよい（`vault/rules/common/git.md` の「作業ステップごとに小さく分ける」に従う）。この計画自体のコミットではブランチ `work/p-20260929-done-guard-git-staging` 上で行い、main へ直接コミットしない
- 追加の決定（2026-09-30、blocked 中に人と合意。実装の参考案。挙動が上の決定と一致すれば実装の細部は変えてよい）
  - `import shlex` を `import subprocess` の次に足す
  - `BASH_WRITE_PATTERNS` は変更せず、その直後に `OTHER_WRITE_PATTERNS`（`tee`、`rm|mv|cp|touch|mkdir|chmod|chown`、`git (push|checkout|switch|reset|restore|clean|stash|merge|rebase|rm|mv)`、`sed -i` の4パターン。リダイレクトと `git add|commit` は含めない）を別に定義する
  - `is_git_stage_or_commit_only(cmd)` の案：
    1. 改行・バッククォート・`$(`・`<(`・`>(` を含めば False。`shlex.shlex(cmd, posix=True, punctuation_chars=True)` に `whitespace_split = True` を設定してトークン化し、`ValueError` なら False
    2. `;`・`&&`・`||`・`|`・`&` のトークンでセグメントに分ける。それ以外の記号だけのトークン（正規表現 `[();<>|&]+` に全体一致。リダイレクトやサブシェル）が1つでもあれば False。クォート内の `>` も同じ扱いになるが、除外されず従来判定に倒れるだけなので許容する（fail-closed）
    3. セグメントの先頭2トークンが `git add` / `git commit` なら「ステージあり」とする。それ以外のセグメントは、トークンを空白で連結した文字列が `OTHER_WRITE_PATTERNS` のどれかにマッチすれば False。最後に「ステージありのセグメントが1つ以上ある」ことを返す（真偽）
  - `find_done_task_write` の Bash 分岐：`BASH_WRITE_PATTERNS` 判定（`return None`）の直後に `if is_git_stage_or_commit_only(cmd): return None` を足す
  - **`)` の巻き込みを塞ぐ修正（必須）**：従来判定は `git commit -m "$(echo x > vault/tasks/P-FIX/T-01.md)"` のリダイレクト先を `vault/tasks/P-FIX/T-01.md)"` と拾い、`TASK_FILE_RE` に合わず拒否できない。受け入れ基準（混在拒否）を満たすため、(1) `find_done_task_write` の path_like 正規表現を `[^\s'\")]*vault/(?:tasks|verdicts)/[^\s'\")]*` に変え、(2) 候補の正規化を `normalize(cand.rstrip(")\"'`"), root)` に変える。この修正は `find_done_task_write` の中だけで行い、`targets_vault_rules`・`targets_creator_denied_paths` は変えない
  - 人がターミナルで実装する場合、フックは全ツール呼び出しで実行されているので、`/tmp` のコピーを編集し `python3 -m py_compile` を通してから `cp` で置き換える（編集途中の構文エラーでセッションが壊れるのを避ける）
- 経緯：最初の creator 呼び出し（attempt=1）は、フックの編集が auto mode の権限分類器に「Self-Modification」として拒否され blocked になった。人が権限設定を整えるか、実装を人が行った後に `blocked → todo` に戻して再開する。再開時に実装が既にコミット済みなら、creator は実装の重複を作らず、確認コマンドの実行とタスク票「進捗」の記録から始める
