# T-05 実地テストで verifier の新責務2つの動作を確認する

## 目的
T-01・T-02 で追加した verifier の2つの新責務（基準妥当性判定・宣言外ファイル検査）が、実際に verifier
サブエージェントを呼んだ時に機能することを、grep によるルール文書の検査だけでなく実地で確認する。

## 入力
- `vault/rules/verifier/verifier.md`（T-01 で改訂済み）
- `.claude/agents/verifier.md`（T-02 で改訂済み）
- `docs/vault-spec.md`（計画票・タスク票・verdict の形式）

## 成果物
- 実地テストの実施記録（本タスク票 `vault/tasks/P-20260920-verifier-scope/T-05.md` の「進捗」に、
  ダミー verdict の `reasons` の実際の文言を引用して記載する）。ダミーの計画票・タスク票・verdict 自体は
  検証後に削除するため vault には残さない。

## 受け入れ基準
- ダミー計画票・タスク票を用意し、緩い基準1行と宣言外ファイルの変更を作り、**それらをコミットして作業ツリーをクリーンにしてから**（実運用では creator が review 前にコミットするため）、**`claude -p` の子プロセス経由で** verifier に `P-20260920-verifier-scope-dummy/T-01` を検証させた。確認：実行したコマンドを「進捗」に引用する（`claude -p` の文字列を含む）
- 生成された verdict の `reasons` に「基準が緩い」旨と「宣言外ファイル」旨の両方が実際に記録されたことを確認し、その文言を引用して「進捗」に書く。確認：`sed -n '/^## 進捗/,$p' vault/tasks/P-20260920-verifier-scope/T-05.md | grep -c -e '緩い' -e '宣言外'` が2以上
- verdict の `result` が `PASS` のままだった（FAIL に繋がっていない）ことを「進捗」に記録する。確認：`sed -n '/^## 進捗/,$p' vault/tasks/P-20260920-verifier-scope/T-05.md | grep -c 'PASS'` が1以上
- 検証後、ダミーの計画票・タスク票・verdict・作成した宣言外ファイルをすべて削除し、リポジトリがクリーンな状態に戻っている。確認：`git status --porcelain | grep -c dummy` が0
- `vault/plans/*.md` の中で `status: approved` が本計画1件だけである（ダミーが approved のまま残っていない）。確認：`grep -l '^status: approved$' vault/plans/*.md | wc -l` が1
- `bash scripts/smoke.sh | tail -1` に `fail=0` が含まれる

## 決定済み
- ダミー計画 ID は `P-20260920-verifier-scope-dummy`、frontmatter は `status: draft` にする（`approved` にしない）。
  `plan_guard.py`・`stop_gate.py`・`agent_write_guard.py` はいずれも `status: approved` の計画票だけを数えるため、
  `draft` のままなら「approved な計画票が2件」というエラーを起こさず、doing/review 中の `vault/rules/` 書き込み
  判定にも影響しない。
- ダミータスク ID は計画スコープの `T-01`（`vault/tasks/P-20260920-verifier-scope-dummy/T-01.md`）でよい。本計画の
  T-01〜T-05 とは別の計画配下なので衝突しない。
- ダミータスク票の受け入れ基準に、わざと「語を数えるだけの緩い基準」を1行含める。例：
  `README.md に「ハーネス」という語が含まれる。確認：grep -c 'ハーネス' README.md が1以上`
  （中身に関わらずほぼ常に通る基準にする）。
- ダミータスク票の「成果物」には1つだけファイルを書く（例：`vault/tmp/dummy-declared.md`）。実際にはそのファイルを
  作らず、代わりに成果物に書かれていない別のファイル（例：`vault/tmp/dummy-unrelated.md`）を1つ作成し、宣言外の
  変更を発生させる。
- **verifier の呼び出しは `claude -p` の子プロセス経由で行う（人の決定）。** 現セッションは
  `.claude/agents/verifier.md`（T-02・T-07 の成果物）をセッション開始時に読み込んでおり、今回の変更が
  反映されていない。`claude -p` は起動ごとに定義を読み直すため（`docs/runbook.md`「困ったとき」）、
  ルール文書とエージェント定義の両方の経路を検証できる。`docs/decisions.md` の 2026-09-17 の記録に
  同じ手段の前例がある。
- 実行するコマンドの形（`--model sonnet` は前例に合わせる）：
  `claude -p --model sonnet "verifier サブエージェントを呼んで P-20260920-verifier-scope-dummy/T-01 を検証させ、vault/verdicts/P-20260920-verifier-scope-dummy/T-01.json を書かせてください"`
  渡すのはタスク ID だけで、作業の経緯や期待する結果は書かない（受け渡し規約どおり）。
- **子プロセスは T-05 が `todo` のうちに起動する。** `doing` にしてから起動すると、子の `stop_gate.py` が
  「T-05 が doing なのに verdict が無い」と判断してブロックする。ダミーの用意・コミット・`claude -p` の
  実行・結果の確認まで `todo` のうちに済ませ、その後 `doing` → `review` にして本タスク自身の verdict を
  取る（`vault/rules/` を成果物にするタスクで使っている回避策と同じ考え方）。
- 本リポジトリは信頼済みなので、`docs/decisions.md` の 2026-09-17 に記録された「一時ディレクトリが未信頼で
  `claude -p` が失敗する」問題は起きない。一時ディレクトリではなく本リポジトリ上で実行する。
- 子プロセスが余計な作業をしないよう、プロンプトは verifier の呼び出しだけに絞る。子プロセスが
  `/run` を始めてしまった場合は中断し、その旨を「進捗」に記録する。
- 確認が終わったら、`vault/plans/P-20260920-verifier-scope-dummy.md`・`vault/tasks/P-20260920-verifier-scope-dummy/`・
  `vault/verdicts/P-20260920-verifier-scope-dummy/`・作成した宣言外ファイル（`vault/tmp/dummy-unrelated.md` 等）を
  すべて削除する。本番の `vault/plans/P-20260920-verifier-scope.md` の `status`（`approved`）は変更しない。
- `git status --porcelain` などの読み取り専用 git コマンドは `agent_write_guard.py` に拒否されない。ダミー
  ファイルの作成・削除は通常の Write/Bash 操作でよい（`vault/rules/` 配下ではないため改ざん防止判定にも
  かからない）。
- **ダミーファイルは verifier を呼ぶ前にコミットする。** 実運用では creator が `review` に回す前に作業
  ステップごとのコミットを済ませており、verifier が動く時点で作業ツリーはクリーンになっている。未コミット
  のまま呼ぶと `git status --porcelain` でも検出できてしまい、実運用の条件を再現しない（T-06 がこの取得
  方法を `git diff --name-only main...HEAD` に直した理由そのもの）。
- 後片付けでダミーファイルを削除した後、その削除もコミットする（Stop フックが未コミット差分でブロックする
  ため）。削除をコミットすれば起点コミットからの差分にダミーのパスが残らない状態になる。
- ダミータスク票の「進捗」の先頭に `起点コミット: <短縮ハッシュ>` を記録する（T-07 で追加したルール）。
  verifier はこれを読んで検査範囲を決める。
