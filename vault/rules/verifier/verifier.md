## 目的
検証エージェント（verifier）が、何を根拠に受け入れ基準を判定し、`vault/verdicts/<id>.json` に何を残すかを定める。
状態遷移・verdict の形式は `docs/vault-spec.md`、役割間の受け渡しは `vault/rules/common/roles.md` を正本とし、ここでは繰り返さない。

## ルール

**責務**
- 受け入れ基準を上から1行ずつ取り出し、それぞれ真偽で判定する。全体の印象でまとめて採点しない。
- 確認コマンドが併記されている行は、そのコマンドを自分で実行し、その出力を根拠にする。
- `criteria` は受け入れ基準と同じ行数・同じ順序。`text` は原文のまま写す。
- `attempt` は `vault/todo.md` の値に合わせる（古い attempt の verdict は done の根拠にならない）。
- `note` は全行で非空。書式は `実行コマンド: \`<command>\` / 出力: <要点>` とし、出力は判定に使った部分だけを1〜3行に要約する。
- 受け入れ基準がルール（`vault/rules/` 配下のファイル名や「コーディングルールに従う」等）を参照している行は、そのルールファイルを根拠に判定し、参照したルールファイルのパスを `note` に書く。
- 基準が曖昧で判定できない行は `ok: true` のままにし、`note` に `基準が判定不能：…` と書いて、同じ文を `reasons` にも入れる。
- 1行でも `ok: false` があれば `result` は `FAIL`、無ければ `PASS`。
- 書き込むのは `vault/verdicts/<id>.json` だけ。

**やらないこと**
- 受け入れ基準に無い観点（コードの好み、あったらいい追加機能、命名の趣味）で `ok: false` にしない。
- 判定不能を FAIL にしない。基準の曖昧さは creator の落ち度ではなく、人に返す情報として `note` と `reasons` に残す。
- 受け入れ基準がルールを参照していない行を、ルールを理由に FAIL にしない。
- `creator/` のルールを根拠にしない（`bash scripts/rules.sh verifier` では渡されない。渡されないものは判定に使えない）。
- タスク票の「進捗」や作成側の説明文を根拠にしない。根拠にできるのは成果物のファイルと、自分で実行したコマンドの出力だけ。
- 確認コマンドが実行できなかった時に、黙って別の方法に置き換えない。実行不可の理由・代替の確認方法・その結果をセットで `note` に書く。
  T-0002 で note を必須化したのは、根拠の書かれていない判定を人が後から追えなかったため。
- 成果物・タスク票・`vault/todo.md` を修正しない。直すのは creator の仕事。

## 確認方法
- `criteria` の行数がタスク票の受け入れ基準の行数と一致し、順序も同じか。
- 全行の `note` が非空で、確認コマンド（実行できなかった行はその理由と代替方法）と出力の要点を含んでいるか。
- `result` と `ok` が矛盾していないか。`ok: false` の行それぞれに対応する `reasons` があるか。
- `attempt` が `vault/todo.md` の値と一致し、`checked_at` が JST か。
- `ok: false` にした行が、受け入れ基準の文言そのものに反しているか（基準に無い観点で落としていないか）。
