# T-01 plan_guard.py に worktree 委譲ロジックを追加する

## 目的
`.claude/hooks/plan_guard.py`（PostToolUse）に、フェーズ1で `agent_write_guard.py` に実装した worktree 委譲ロジック（`payload["cwd"]` の git toplevel が自リポジトリと異なれば、そのルート配下の同名スクリプトへ委譲し、失敗時はフェイルオープンでフォールバックする）と同じパターンを複製して実装する（issue #56 対応、`vault/designs/D-008.md` フェーズ2）。既存のタスク表整合性チェックは変更しない。

- `.claude/hooks/agent_write_guard.py`（実装パターンの一次情報。`delegate_to_worktree`・`git_toplevel`・`existing_ancestor` の3関数をそのまま複製する）
- `.claude/hooks/plan_guard.py`（変更対象。`project_dir()` は変更しない。`main()` の payload 読み込み直後に委譲呼び出しを追加する）

- `.claude/settings.json`（`hooks.PostToolUse` のタイムアウトが30秒であることの確認。委譲の `subprocess.run` タイムアウトはこれより短くする）

## 決定済み
- 委譲判定は `payload["cwd"]` から求めた git toplevel のみで行う。既存の `project_dir()`（`vault/plans` 等データの読み込み先解決。`CLAUDE_PROJECT_DIR` 優先）は変更しない。委譲はコードの実行先を切り替えるだけ
- 「自リポジトリのルート」との比較対象は `CLAUDE_PROJECT_DIR`、無ければ `git_toplevel(os.path.dirname(os.path.abspath(__file__)))` を使う（フェーズ1の `agent_write_guard.py` と同じ扱い）
- `git_toplevel`・`existing_ancestor` の2関数は `agent_write_guard.py` から同じ実装をそのまま `plan_guard.py` 内にコピーして定義する（`import` はしない。`stop_gate.py` が既存ロジックをコピーして使う流儀と同じ）
- 委譲は `_HOOK_DELEGATED=1` を委譲先プロセスの環境変数にセットして呼び出す。自分自身の環境で既に設定されている場合は委譲せず、必ずローカル判定にフォールバックする（1段まで）
- 委譲先には同じ payload を `json.dumps()` で再シリアライズし、標準入力として渡す
- 委譲呼び出しは `main()` の payload 読み込み直後（他の判定より前）に行う。委譲が成功した場合は委譲先の stdout をそのまま自分の stdout として出し `exit 0` する（委譲先の判定をそのまま採用し、自分でさらに判定を続けない）
- 委譲先が存在しない・`subprocess.run` が例外を送出する・タイムアウトする・非0で終了する、のいずれの場合もフェイルオープンとし、通常どおりメインリポジトリ側のローカル判定（`project_dir()` 以降の既存フロー）に進む
- 既存の判定ロジック（`after` 依存違反・blocked の question 空・status 5値外・id 重複・列数6でない・approved 計画票2件以上）はメインリポジトリ側・委譲先側のどちらのコードも変更しない
- `scripts/smoke.sh` の新規テストケースは、224〜264行目の `agent_write_guard.py` 向け `(delegate)` ケース（`git worktree add` で一時 worktree を作り、その `.claude/hooks/` に判定結果が変わる短い差し替えスクリプトを置き、`cwd` をそのworktreeに向けたペイロードをメインリポジトリ側のフックに渡す）と同じ型を踏襲する。判定結果の違いは PostToolUse の出力 `{"decision": "block", ...}` の有無で見分けられるので、委譲先の差し替えスクリプトは「常に `{"decision": "block", "reason": "delegated"}` を返すだけの短いスクリプト」にすると、通常なら許可される正常な計画票に対してもブロックが返ることで worktree 側の判定が採用されたことを確認できる
- （issue #59 対応）受け入れ基準5「`bash scripts/smoke.sh` を実行した時...」の判定は、今回の変更（`delegate_to_worktree` 追加分）と無関係な既存の環境依存の失敗（`(worktree)`・`(worktree nested)`・discard_worktree.sh の `(a)`、`.claude/worktrees/` 配下に未削除 worktree が残ることに起因する「参照される scripts」チェックのフレーキーな失敗等）をスコープ外として無視してよい。判定は「新規追加した `(delegate plan_guard)` の3件以上がすべて `ok` であること」「既存の失敗の件数・内容が着手前HEAD時点から悪化していないこと（新たな失敗が増えていないこと）」の2点のみで行う。`rc=0`・`fail=0` の字義通りの達成は求めない。着手時（doing 開始時）に起点コミットで一度 `bash scripts/smoke.sh` を実行し、その結果（`pass=<N> fail=<M>` と失敗ケース名）をタスク票の「進捗」に記録しておくこと
- コミットは行わない（受け入れ基準にコミットの指示が無いため）。`vault/rules/common/git.md` の既存のブランチ運用に従うこと
