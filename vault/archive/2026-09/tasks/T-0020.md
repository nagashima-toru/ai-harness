# T-0020 planner の責務と「やらないこと」をルール化する

## 目的
計画エージェント（planner）の責務・入出力と、このリポジトリで実際に起きた失敗から導いた「やらないこと」を `vault/rules/planner/` に1ファイルで定義し、以後の計画票・タスク票の品質を上げる。

## 入力
- `vault/rules/common/roles.md`（T-0019 の成果物。受け渡しの契約。ここと重複させない）
- `.claude/agents/planner.md`（現在の責務記述。重複させすぎない）、`vault/templates/rule.md`（3見出し）
- 失敗例の一次情報：`vault/tasks/T-0002.md`（進捗と決定済みに blocked の経緯）、`vault/tasks/T-0016.md`（受け入れ基準3行目 `grep -c 'planner'`）、`vault/tasks/T-0012.md`・`vault/tasks/T-0013.md`（本文に無い文字列を grep する基準）
- `docs/decisions.md`、`docs/vault-spec.md` 第9節（粒度の基準）

## 成果物
- `vault/rules/planner/planner.md`（新規1ファイル）

## 受け入れ基準
- `vault/rules/planner/planner.md` が存在し、見出しが `## 目的` / `## ルール` / `## 確認方法` の3つだけ。確認：`grep -c '^## ' vault/rules/planner/planner.md` が3
- 100行以内。確認：`grep -c '' vault/rules/planner/planner.md` が100以下
- 「ルール」に、実際の失敗から導いた「やらないこと」が3件以上あり、各件が根拠のタスク ID を明記している。確認：`grep -c 'T-00' vault/rules/planner/planner.md` が3以上
- 「やらないこと」に (a) run-queue で必ず変わるファイル（`vault/todo.md`・`vault/log/queue.md`・タスク票の「進捗」）の差分不変を受け入れ基準にしない、(b) 単語数を数えるだけの緩い確認コマンドにしない、(c) 成果物本文に無い文字列を grep する基準を書かない（基準で参照する文言はタスク票本文で明示的に要求する）、の3点がすべて含まれる
- `bash scripts/rules.sh planner` の出力に `vault/rules/planner/planner.md` が含まれ、`bash scripts/rules.sh creator` と `bash scripts/rules.sh verifier` の出力には含まれない
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含む

## 決定済み
- ファイル名は `vault/rules/planner/planner.md` で固定
- 「ルール」は「責務」と「やらないこと」の2つの箇条書きの塊で書いてよい（見出しは3つのままにし、塊の区切りは太字の行か空行で表す）
- 責務として書くこと（各1行）：ゴールを1コンテキストで終わるタスクに割る／`P-`3桁・`T-`4桁を既存最大値+1で採番する／タスク票の6見出しを埋め「決定済み」に creator が聞きそうなことを先回りで書く／契約タスクを先に切り実装を `after` で依存させる／1計画5〜7タスク／`vault/plans/` と `vault/tasks/` 以外に書かない／`status` を `approved` にしない／不明点はゴールを広げず計画票末尾の「## 人への質問」に出す
- 「やらないこと」に書く失敗例（根拠を括弧で明記する）：
  - `git diff --quiet -- vault/todo.md` のように run-queue が必ず変えるファイルの不変を基準にした（T-0002 が blocked）。形式を見たいときは見出し行・列構成に限定した確認コマンドにする
  - 確認コマンドが `grep -c 'planner' <file>` のように緩く、本来検査したい内容を検査できていない（T-0016）。数えるのではなく、検査したい文言・構造に一致するパターンを書く
  - 成果物本文に無い文字列を grep する基準を書き、creator が基準を通すために後から文言を足す羽目になった（T-0012 の `vault/rules`、T-0013 の構成ツリー）。grep する文言は、タスク票の「成果物」か「決定済み」で「この語を書くこと」と明示する
- 「確認方法」には計画提出前のセルフチェックを3〜5行で書く（例：各受け入れ基準の確認コマンドを planner 自身が読み取り専用で実行できるか、依存に循環が無いか、タスク数が7以下か）
- `vault/rules/` は `doing`/`review` 中は書き込みが拒否される。人が `HARNESS_ALLOW_RULES_WRITE=T-0020` を設定して起動している前提で進め、Write が deny されたらフックや設定を自分で変えず `blocked` にして question に設定方法を書く
- `.claude/agents/planner.md`・`docs/`・`README.md`・`scripts/` は変更しない（配布と文言修正は T-0023）
- git commit はしない（人が確認してからコミットする）
