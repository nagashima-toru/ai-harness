# T-01 vault/rules/verifier/verifier.md に2つの新責務を追加する

## 目的
verifier の判定範囲を「creator が通した確認コマンドの再実行」から一歩広げ、(1) 受け入れ基準が緩くないかの判定、
(2) 宣言外ファイルの変更検査、の2つを正本ルールとして明記する。どちらも `FAIL` には繋げない。

## 入力
- `vault/rules/verifier/verifier.md`（改訂対象。既存の「やらないこと」は変更しない）
- `vault/tasks/P-20260920-git-workflow/T-01.md` と `vault/verdicts/P-20260920-git-workflow/T-01.json`
  （緩い基準がそのまま PASS になった実例）
- `docs/vault-spec.md` の「## 6. verdict.json」（`note`/`reasons` の既存の意味論）

## 成果物
- `vault/rules/verifier/verifier.md`（既存ファイルの改訂。「責務」に2ブレット追加のみ）

## 受け入れ基準
- 「責務」に基準妥当性判定の記述がある。確認：`grep -F '目的」の達成を意味するか' vault/rules/verifier/verifier.md` の出力が1行
- 「責務」に宣言外ファイル検査と除外リスト4項目の記述がある。確認：`grep -F '計画票（\`vault/plans/<計画ID>.md\`）' vault/rules/verifier/verifier.md`、`grep -F 'タスク票の「進捗」' vault/rules/verifier/verifier.md`、`grep -F '\`vault/log/<計画ID>.md\`' vault/rules/verifier/verifier.md`、`grep -F '\`vault/verdicts/\` 配下' vault/rules/verifier/verifier.md` がそれぞれ1行以上
- 追加した2つの責務はどちらも FAIL に繋がらないと明記されている。確認：`grep -c 'FAIL にはしない' vault/rules/verifier/verifier.md` が2以上
- 既存の「やらないこと」節のブレット数が7のまま変わっていない。確認：`sed -n '/\*\*やらないこと\*\*/,/^## 確認方法/p' vault/rules/verifier/verifier.md | grep -c '^- '` が7
- ファイルが100行以内に収まっている。確認：`wc -l < vault/rules/verifier/verifier.md` が100以下

## 決定済み
- 追加する2ブレットは「責務」節の末尾（既存の最後のブレットの後、`**やらないこと**` の前）にそのまま追記する。以下の文面をそのまま使ってよい（意味を変えない範囲で言い回しの調整は可）。
  1. `- 各受け入れ基準について、確認コマンドが通ることがタスク票の「目的」の達成を意味するかを判定する。基準が緩い（確認コマンドは通るが目的の達成を保証しない）と判断した場合は \`ok: true\` のまま \`note\` に理由を書き、同じ文を \`reasons\` にも入れる（\`ok: false\` にはしない。FAIL にはしない）。`
  2. `- \`git status --porcelain\` 等で変更されたファイル一覧を取得し、タスク票の「成果物」に書かれていないファイルが含まれていないかを確認する。含まれていた場合は該当行（無ければ最後の基準行）の \`note\` に対象ファイルを書き、同じ文を \`reasons\` にも入れる（\`ok: false\` にはしない。FAIL にはしない）。ただし次は宣言外でも正常として扱い記録しない：計画票（\`vault/plans/<計画ID>.md\`）・タスク票の「進捗」・\`vault/log/<計画ID>.md\`・\`vault/verdicts/\` 配下。`
- どちらの新責務も既存の「判定不能」の機構（`ok: true` のまま `note` と `reasons` に記録）をそのまま流用する。新しい `ok` の値や verdict のフィールドは追加しない。
- 「やらないこと」節は削除・変更しない（人の決定済み事項）。追記するのは「責務」節だけ。
- このファイルは `vault/rules/` 配下のため、`doing`/`review` 中は `agent_write_guard.py` が書き込みを拒否する。人が `HARNESS_ALLOW_RULES_WRITE=T-01 claude` で起動している前提で進めてよいが、このセッションでは使えない場合、承認済みの回避策「`todo` のうちに内容を編集し、その後 `doing` にする」を使ってよい。
- 「確認方法」節への追記は不要（既存の確認方法の記述で新責務もカバーできる範囲。追記したい場合のみ、100行以内に収まる範囲で追記してよい）。

- `todo` のうちに `vault/rules/verifier/verifier.md` の「責務」末尾（`書き込むのは vault/verdicts/...` の後、

  （`doing` にする前に編集を完了させる）を使用

  - `目的」の達成を意味するか`=1
  - 除外リスト4項目：計画票=2 / タスク票の「進捗」=2 / `vault/log/<計画ID>.md`=1 / `vault/verdicts/` 配下=1
  - `FAIL にはしない`=2
  - 「やらないこと」のブレット数=7（変更なし）
  - 行数=35（100行以内）
- `vault/rules/common/git.md` のルールに沿い、作業ステップごとにコミットする
