# T-01 plan_guard.py に draft 計画のタスク票の受け入れ基準3〜7行の検査を追加し smoke.sh にテストを足す

## 目的
`.claude/hooks/plan_guard.py` に、Write/Edit の対象が `vault/tasks/<計画ID>/T-xx.md` で、対応する計画票の status が `draft` の時、「## 受け入れ基準」節の箇条書きが3〜7行でなければブロックする検査を追加する。`scripts/smoke.sh` に回帰テストを足す（issue #77、D-010 フェーズ3）。

## 入力
- `vault/designs/D-010.md` フェーズ3（ゴール文・決定済み）
- `.claude/hooks/plan_guard.py`：`main()`（approved が0件なら `sys.exit(0)` する。粒度検査はその判定より前に置く）、`plan_id_and_status`、`project_dir`、`block`、`delegate_to_worktree`
- `scripts/smoke.sh` の `== plan_guard.py ==` セクション（375行付近〜）と、`make_plan`・`expect` ヘルパー

## 成果物
- `.claude/hooks/plan_guard.py` の修正と `scripts/smoke.sh` への回帰テスト追加（1PR分の関連する2ファイル変更）

## 受け入れ基準
- draft 計画のタスク票（`vault/tasks/<計画ID>/T-xx.md`）の受け入れ基準が2行または8行の時、plan_guard が `{"decision": "block", ...}` を返し、reason にその行数（`2`・`8`）を含む。確認：`bash scripts/smoke.sh` の出力に `ok   (granularity-task)` で始まる該当ケースがあり `NG` が無い
- 受け入れ基準が3行・7行の時はブロックしない（同上のケースで確認）
- 計画票の status が `approved` の時は、タスク票の受け入れ基準が8行でも粒度検査でブロックしない。計画票が無い場合、`T-xx-proposal.md` など `T-` + 2桁 + `.md` 以外のファイル、Bash による書き込み（`tool_name` が `Bash`）も検査しない（いずれも smoke.sh のケースで確認）
- 既存の approved 計画の検査（`(a-1)`〜`(f)` のケース）の結果が変わらない。確認：`bash scripts/smoke.sh > /tmp/P-20260930-task-granularity-guard-T-01-smoke.txt 2>&1; grep -c '^  NG' /tmp/P-20260930-task-granularity-guard-T-01-smoke.txt` の出力が `0`
- `bash scripts/smoke.sh | tail -1` が `smoke: pass=<N> fail=0` になる

## 決定済み
- 検査するのは計画票が `draft` の時だけ。承認後に creator が「進捗」を編集するたびに直せない指摘を出さないため
- 契機は Write/Edit の `tool_input.file_path` がそのファイルを指す時だけ（`tool_name` が `Write` または `Edit`）。Bash は対象外。`file_path` は絶対パス・相対パスの両方があり得るので、`project_dir(payload)` を基準に root 相対へ正規化してから、`^vault/tasks/([^/]+)/(T-\d{2})\.md$` に一致するかを見る
- 計画票は `vault/plans/<計画ID>.md` を `plan_id_and_status` で読む。無い・読めない・status が取れない場合は検査しない（fail-open）
- 数え方：「## 受け入れ基準」の次の行から次の `## ` 見出し（または EOF）までの間で、行頭（インデント無し）が `- ` または `数字. ` の行を数える。ファイルはブロック時点のディスク上の内容（PostToolUse なので書き込み後）を読む
- 判定位置：`delegate_to_worktree` の後、`approved_plans` の判定より前。粒度検査が該当しない（対象外のパス）場合は、従来の処理へそのまま進む。既存の approved 計画の検査は変えない
- 他ファイルからの import はしない（既存方針）。関数は `plan_guard.py` 内に足す
- ブロックの形式は既存と同じ `{"decision": "block", "reason": ...}`。reason には計画 ID・タスク ID・実際の行数・3〜7行であることを書く（例：`[plan_guard] P-X/T-01 の受け入れ基準が8行です。3〜7行にしてください。`）
- 「真偽で判定できる文か」は機械では検査しない
- smoke.sh のケース名には接頭辞 `(granularity-task)` を付ける。フィクスチャは既存の `$TMP` を使い、`make_plan` で `draft`/`approved` の計画票を作ってから、`$TMP/vault/tasks/P-TEST/` にタスク票を作る（既存の `make_task` は受け入れ基準の行数を引数に取るので流用できる）。既存の `run_plan_guard` は `tool_input` を渡せない形なので、`file_path` を渡す新ヘルパーを足す
- コミットは実装とテストを分けてよい（`vault/rules/common/git.md`）
