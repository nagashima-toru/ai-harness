# T-03 plan SKILL A 手順2に push 先ブランチの切り直しを足す

## 目的
push 先ブランチが決められている環境（クラウドセッション）で、1つ目の計画の PR がマージされた後、同じセッションで2つ目の `/plan` を始められるようにする（Issue #206）。前の計画の変更がベースブランチに取り込まれていない時は、従来どおり止まる。

## 入力

- `docs/vault-spec.md` 1節の `HARNESS_PUSH_BRANCH` の段落（36行目。今の開始条件の正本。このタスクでは変えない）

- `.claude/settings.json`（`permissions.allow` の `Bash(git *)`・`Bash(env *)`。`permissions.deny` は `git push --force` 系だけで、`git checkout -B`・`git merge-tree`・`git ls-remote` は止めない）

## 決定済み
- 書く場所：A 手順2（`2. ` で始まる行）の直後に、3文字の空白で字下げした箇条（`   - `）として足す（手順2の1行が長いため。手順3の `3. ` の行より前に置く）。手順2の本文の「どちらの条件も満たさなければ従来どおり、ブランチを切らず「ベースブランチ（`<値>`）に戻ってから `/plan` を実行してください」と伝えて**止まる**」は、「どちらの条件も満たさず、下の切り直しもできなければ従来どおり、…止まる」の趣旨に直す（案内の文言「ベースブランチ（`<値>`）に戻ってから `/plan` を実行してください」は変えない）。手順2のほかの文（fetch・detached HEAD・`HARNESS_PUSH_BRANCH` の条件・`env HARNESS_PUSH_BRANCH=… ` の渡し方）は変えない
- 足す箇条の内容（この順・この判定で書く。`<push先>` は `HARNESS_PUSH_BRANCH` の値（前後の空白を除いたもの）、`<ベースブランチ>` は手順2のベースブランチ）：
  - 切り直しは、既存の条件（ベースブランチ上・detached HEAD・`HARNESS_PUSH_BRANCH` の条件）のどれも満たさない時に、既存の `git fetch origin <ベースブランチ>:<ベースブランチ>` の後で判定する。目的（Issue #206。1つ目の計画の PR がマージされた後に、同じセッションで2つ目の `/plan` を始めるため）を1文で書く
  - (1) `HARNESS_PUSH_BRANCH` が設定され、現在のブランチ（`git branch --show-current`）が `work/` で始まるか `<push先>` である
  - (2) `git status --porcelain` の出力が空である（未コミットの変更・未追跡のファイルが無い。前の計画の作業を新しい計画に持ち込まないため）
  - (3) `HEAD` と、ローカルに `<push先>` のブランチがあれば（`git rev-parse --verify refs/heads/<push先>` が成功すれば）`<push先>` も、内容がベースブランチに取り込み済みである。判定は対象ごとに `git merge-tree --write-tree <ベースブランチ> <対象>` を実行し、終了コードが0で出力の1行目が `git rev-parse <ベースブランチ>^{tree}` の出力と同じなら取り込み済みとする。スカッシュマージでも取り込み済みなら同じになる（`git merge-base --is-ancestor` は、スカッシュマージの後は偽になるので、この判定には使わない）。終了コードが0でない時（衝突、git 2.38 より古く `--write-tree` が無い時を含む）は取り込まれていないとみなす
  - (4) `git ls-remote --heads origin <push先>` が終了コード0で、出力が空（リモートに push 先ブランチが無い）か、出力の1列目の sha について `git merge-base --is-ancestor <sha> <ベースブランチ>` が終了コード0である。ls-remote が失敗した時（ネットワーク不可など）は止まる。is-ancestor が0でない時（スカッシュマージの後でリモートの push 先ブランチが残っている時、ローカルにそのコミットが無い時を含む）は、「push 先ブランチ（`<push先>`）のリモートに、ベースブランチ（`<値>`）に取り込まれていないコミットがあります。スカッシュマージした後なら、リモートの push 先ブランチを削除してから `/plan` を実行してください」と伝えて**止まる**。理由も1文で書く（切り直しても、次の `vcs_finish.sh` の push が non-fast-forward で失敗し、force はしないため）
  - (1)〜(3) のどれかを満たさない時は切り直さず、手順2の従来の案内（「ベースブランチ（`<値>`）に戻ってから `/plan` を実行してください」）で止まる
  - すべて満たせば `git checkout -B <push先> <ベースブランチ>` で push 先ブランチをベースブランチから切り直す。失敗した時は止まる。`git checkout -f`・`git reset`・`git stash`・`git branch -D` は使わない。前の `work/…` ブランチは消さない
  - 切り直した後は、現在のブランチが `<push先>` で `git rev-parse HEAD` がローカルのベースブランチと同じになるので、手順2の `HARNESS_PUSH_BRANCH` の条件でベース上とみなし、手順3へ進む
- 「リモートの push 先ブランチを削除」の文字列は、(4) の案内の1か所だけに書く（受け入れ基準4で `1` を数えるため）
- 各 git コマンドは1回の Bash 呼び出しに1つずつ書く前提にする（`&&`・`;`・コマンド置換で組み合わせない）。どのコマンドも `.claude/settings.json` の `Bash(git *)` で通り、`permissions.deny` には当たらない（planner が確認した）。`HARNESS_PUSH_BRANCH` が環境変数に無い時の値の渡し方は、手順2の既存の文（`env HARNESS_PUSH_BRANCH=<指定ブランチ> …`）のままでよく、変えない
- `HARNESS_PUSH_BRANCH` が設定されていない時の `work/…` からの開始は対象外（ベースブランチに checkout し直せば従来の条件で始められるため）。(1) を満たさないので従来どおり止まる
- `/design` 手順1（`.claude/skills/design/SKILL.md`）の同じ開始条件には足さない（ゴールが `/plan` のため。変えない）
- `docs/vault-spec.md`・`docs/runbook.md` は T-04 が変える。このタスクでは変えない
- 手順2の判定は、planner が一時リポジトリ（git 2.43）で確かめた：スカッシュマージ済みのブランチは `git merge-tree --write-tree main <branch>` の1行目が `git rev-parse main^{tree}` と同じで、`git merge-base --is-ancestor <branch> main` は偽。マージ後にコミットを足したブランチはツリーが違う
