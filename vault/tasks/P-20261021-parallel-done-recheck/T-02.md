## 決定済み
- 実装される挙動（T-01）：`--worktree` 付きの done は、PASS の verdict の確認・新規コミットの判定・差分ゲートの後、メインの作業ツリーで `git rev-list --count --merges --first-parent <plan-head>..HEAD` が1以上なら計画ブランチにマージしない。計画ブランチの今の HEAD（H）が worktree のブランチの祖先でなければ worktree の中で `git merge --no-ff H -m "<計画ID>/<id>: 計画ブランチを取り込み"` を行い、log に再開情報の記録行（`plan_head=<H>`）と `review→review` の行を書いて log だけをコミットし、メインの作業ツリーの verdict を消して、標準出力に `<計画ID>/<id>: review→review attempt=<n> 計画ブランチを取り込み再検証 plan_head=<H>` を出し終了コード6で返す。計画票（status は review・attempt）は変えない。取り込みが衝突・失敗したら `git merge --abort` で中止して review→blocked（終了コード4。question は `計画ブランチの取り込みで衝突したファイル: ...` か `計画ブランチの取り込みに失敗した: ...`、補足は `マージコンフリクト` か `マージ失敗`）。run は verifier を呼び直してから `--plan-head <H>` で done を呼び直す。H..HEAD には状態のコミット（非マージ）しか無いので、2回目は今のままマージと done に進む
- 2節の done（review→done）の箇条：差分ゲートの後に再検証の判定を足す。文に「同じ組の他タスクが先に done になって計画ブランチにマージされていたら」（この文字どおり）を含めて、上の挙動を書く。判定にマージコミットを数える理由（計画ブランチは状態のコミットで毎回進むので HEAD と plan-head の比較では常に真になり、他タスクの変更は done の `--no-ff` マージでだけ入る）と、verdict を消す理由（古い worktree で判定した PASS で done にできないようにする）も書く
- 2節の終了コードの箇条：今の「／5 `--resume-worktree` で worktree を引き継げなかった（何も変えていない）」の後に「／6 再検証のため計画ブランチを worktree に取り込んだ（done にしていない。verifier を呼び直す）」を足す。続く「終了コード 3・4 の時は、何をしたかを標準出力に1行で出す」の文は「終了コード 3・4・6 の時は」に直す
- 7節：`transition.py` の worktree 運用が書く行の段落に、次の文を足す：done の前に再検証のため計画ブランチを取り込んだ時は、再開情報の記録行（取り込んだ計画ブランチの HEAD を `plan_head` にしたもの）と `- <日時> <id> review→review attempt=<n> 計画ブランチを取り込み再検証` の行をこの順に同じ日時で書く（モデルは付けない。attempt は変えない）。中断した時は run の手順2の2が review の行として最後の記録行から再開する
- 一意にするため：「同じ組の他タスクが先に done になって計画ブランチにマージされていたら」の文は2節の done の箇条にだけ書く。log の行の形 `- <日時> <id> review→review attempt=<n> 計画ブランチを取り込み再検証` は7節にだけ書き、2節では「7節の形の記録行と review→review の行」のように7節を指す（標準出力の形 `<計画ID>/<id>: review→review ...` は2節に書いてよい）
- 7節の「done の前に blocked にした時の補足は …のいずれか」の列挙に `マージ失敗` が無ければ足してよい（取り込みの失敗でも使うため）
- 1節の証跡の段落の「worktree 側の取り込みのマージコミット（`--resume-worktree` が作る `<計画ID>/<id>: 計画ブランチを取り込み`）」は「（`--resume-worktree` と done の再検証が作る `<計画ID>/<id>: 計画ブランチを取り込み`）」に直す
- 2節の遷移表（7つ）・2節冒頭の5状態の表は変えない（状態は増やさない）
- `docs/decisions.md` の表の末尾に1行足す。日付 `2026-10-21`。「何を」：通常の並行実行で、同じ組の他タスクが先に done になって計画ブランチにマージされていたら、transition.py の done は計画ブランチにマージせず、計画ブランチを worktree に取り込んで verdict を消し、終了コード6で返す。run は verifier を呼び直してから done を呼び直す。状態は review のまま（log は review→review の行）で5状態は増やさない。planner が after を付けて並行にしない案（案B）は採らない。末尾に「（Issue #212）（P-20261021-parallel-done-recheck）」（この文字どおり）を付ける。「なぜ」：案Bは「リポジトリ全体を見る基準か」を planner が判断する運用で機械的に確かめられず（原則2）、smoke の (ref-1) のように多くのタスクが持つ基準まで並行をやめることになる。案Aは判定と強制を transition.py が行い、増える費用は同じ組で2件目以降に PASS したタスクの verifier の呼び出し1回ずつ（1組で最大 HARNESS_MAX_PARALLEL−1 回）
- decisions の行の中に `|` を書かない（表の列が崩れるため）
- バッククォートで書くパスは今あるファイルだけにする（smoke の `(ref-1)` が存在しないパスを NG にする）。smoke は1分ほどかかる
