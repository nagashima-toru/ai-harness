## 決定済み
- 追記するのは次の4行だけ（各行の「何を」の末尾に `（D-20261010-async-agent-wait）` を全角括弧で付ける。日付は `2026-10-10`。表の既存の行は変えず、表の末尾に足す）。各行の列の中に `|` を書かない
  1. subagent の前景固定に環境変数 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` を使わず、run・plan の手順に「バックグラウンドに回った時の待ち方（ターンを終えて完了通知を待つ）」を書いて対応する。なぜ：対話セッションでは subagent が常にバックグラウンドになりうるうえ前景を要求できない。env で固定すると Bash の `run_in_background` など他のバックグラウンド機能も止まる（人の選択）。この行に `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` の語を書く
  2. `stop_gate.py` の判定は変えず、記録行の無い doing でブロックする時の理由の文面だけを「完了通知を待っているならそのままターンを終えて待つ」旨にする。なぜ：記録行の無い doing は「creator 実行中」と「creator が中断して終わった」を区別できないのでゲートは緩めない。対話実行では `stop_hook_active` で2回目の停止は許可されるので待ちのターンは詰まらない（人の選択）。この行に `stop_gate.py` の語を書く
  3. バックグラウンドに回った creator・verifier（と planner）のハングの基準は「出力ファイル（transcript）の最終更新から10分進まない」とし、同期で返らない呼び出しの目安15分（issue #48）は据え置く。ハングと判定したら TaskStop で止め、既存の「ハング時の復旧」と同じ手順で扱う（planner は止めて人に報告する）。なぜ：#157 で4分・15分の停止が観測された。10分は確認コマンドの長い実行を誤判定しにくく、15分より早く復旧できる。復旧手順を2系統にしない（人の選択）。この行に「10分」の語を書く
  4. worktree の置き場は `.claude/worktrees/`（Claude Code の既定）のまま変えない。なぜ：`.claude/worktrees/` は保護パス（`.claude/`）の例外で Edit の権限確認の原因になりにくい。外に出すと作業ディレクトリの外として新たな権限確認が出うるうえ、`worktree.baseRef`・再開時の再進入・自動掃除が効かなくなる。#157 前半の Edit 停止は、待ち方とハングの基準の効果を見てから再発したら別 Issue で扱う（人の判断）。この行に `.claude/worktrees/` の語を書く
- 文言は上の要旨から多少変えてよいが、各行に指定の語を必ず入れ、指定の語を他の3行には入れない（受け入れ基準の awk が各語を1行ずつ数えるため。例：1の行に「10分」、3の行に `stop_gate.py` を書かない）
