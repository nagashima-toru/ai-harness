## フェーズ3 タスク粒度（受け入れ基準3〜7行・1計画7タスク以下）をフックで検査する（#77）

### ゴール文

`.claude/hooks/plan_guard.py` に粒度の検査を追加する。Write/Edit の対象が `vault/tasks/<計画ID>/T-xx.md` で、対応する計画票の frontmatter の status が `draft` の時は、「## 受け入れ基準」節の箇条書きが3〜7行でなければブロックする。対象が `vault/plans/<計画ID>.md` で、status が `draft` の時は、タスク表のデータ行が7行を超えればブロックする。`docs/vault-spec.md` の8節と10節に、機械で検査される旨を追記する。`scripts/smoke.sh` にテストを足す（issue #77）。

### 受け入れ基準の候補
- draft 計画のタスク票で受け入れ基準が2行または8行の時、plan_guard がブロックし、reason に行数を含む（smoke.sh で確認）
- draft 計画のタスク票で受け入れ基準が3行・7行の時は、ブロックしない（smoke.sh で確認）
- draft 計画票のタスク表が8行の時ブロックし、7行の時はブロックしない（smoke.sh で確認）
- approved 計画のタスク票を編集した時は、受け入れ基準が8行でも粒度検査でブロックしない（smoke.sh で確認）
- `bash scripts/smoke.sh` の最終行が `fail=0` になる

### 決定済み
- 検査するのは計画票が `draft` の時だけ。承認後に creator がタスク票の「進捗」を編集するたびに、直せない指摘を出さないため
- 検査の契機は、Write/Edit の `file_path` がそのファイルを指す時だけ。Bash による書き込みは対象外（planner は Write を使う）
- `plan_guard.py` は現状 PostToolUse で approved 計画だけを見ている。粒度検査は、それとは別に `tool_input.file_path` から対象の計画・タスクを特定して行う。既存の approved 計画に対する検査は変えない
- 箇条書きの数え方：「## 受け入れ基準」の次の行から次の `## ` 見出しまでの間で、行頭（インデント無し）が `- ` または `数字. ` の行を数える
- `T-xx-proposal.md` など、`T-` + 2桁 + `.md` 以外のファイルは対象外
- 「真偽で判定できる文か」は機械では検査しない。planner・verifier の既存の運用に残す
- ブロックの形式は既存と同じ `{"decision": "block", "reason": ...}`

## フェーズ4 マージを deny し、人だけが行う遷移をフックで警告する（#75）

### ゴール文

`.claude/settings.json` の `permissions.deny` に `Bash(gh pr merge*)` と `Bash(glab mr merge*)` を追加する。`.claude/hooks/plan_guard.py` に、人だけが行う遷移の検出を追加する。Write/Edit の対象が `vault/plans/*.md` の時、または Bash のコマンド文字列に `vault/plans/` を含む時、作業ツリーの計画票を `git show HEAD:<path>` の版と比べる。(1) frontmatter の status が approved になっているのに HEAD では approved でない（HEAD に無い場合も含む）、(2) HEAD で blocked の行が blocked 以外になっている、のどちらかを検出したら、ブロックせず PostToolUse の `additionalContext` で警告を出す。`docs/vault-spec.md` 10節と `docs/runbook.md` に追記し、`scripts/smoke.sh` にテストを足す（issue #75）。

### 受け入れ基準の候補
- `.claude/settings.json` の deny に `Bash(gh pr merge*)` と `Bash(glab mr merge*)` がある（`jq -r '.permissions.deny[]' .claude/settings.json` の出力で確認）
- HEAD で draft の計画票を approved に書き換えた後に plan_guard を実行すると、`additionalContext` に警告が出て、`decision: block` は出ない（smoke.sh の git フィクスチャで確認）
- HEAD で blocked の行を todo に書き換えると同様に警告が出る。todo→doing などの通常の遷移では警告が出ない（smoke.sh で確認）
- 非 git ディレクトリ、または HEAD が無い状態では警告を出さず、既存の検査結果も変わらない（smoke.sh で確認）
- `bash scripts/smoke.sh` の最終行が `fail=0` になる

### 決定済み
- 警告だけでブロックしない（人の回答）。`/plan approve` は従来どおりエージェントが status を書き換える。その時も警告は出るが、文面を「人の指示による承認・解除であれば問題ありません。そうでなければ元に戻してください」とし、正当な操作を妨げない
- 既存のブロック条件（依存違反など）と警告が同時に当たった時は、ブロックを優先し、reason の末尾に警告文を添える
- HEAD との比較は `git -C <root> show HEAD:<相対パス>` で行う。失敗した時（非 git・HEAD 無し・未追跡）は、(1) では「HEAD に無い」として扱い、(2) では何もしない。非 git ディレクトリでは両方とも何もしない
- `merge_settings_json.py` は src の deny を導入先に足すので、導入先にも `--update` で deny が届く。マージャは変更しない
- run・design・plan スキルの「マージは人が行う」旨の記述はそのまま残す
- done→他 の遷移は、このフェーズでは扱わない（F2 がタスク票・verdict を保護しており、タスク表の行の遷移の保護は「今回やらないこと」に含める）

## フェーズ5 run の再開情報（worktree・ブランチ・PLAN_HEAD）をログに記録し、中断から再開できるようにする（#78）

### ゴール文

`.claude/skills/run/SKILL.md` を改訂し、オーケストレーターが creator の完了時に受け取る worktree のパス・ブランチ名と、手順3.1の `PLAN_HEAD` を、`vault/log/<計画ID>.md` に記録行 `- <日時> <id> worktree path=<パス> branch=<ブランチ名> plan_head=<sha>` として1行追記するようにする。手順2.2の再開手順を次のとおり書き換える。review の行は、log の最新の記録行から worktree を復元して手順5へ進む。記録された worktree が `git worktree list` に無ければ、doing に戻して attempt+1 で作り直す。doing の行は、中断を1回の試行として attempt+1 にし、creator を呼び直す（上限に達したら blocked）。`docs/vault-spec.md` 7節に記録行の書式を追記する（issue #78）。

### 受け入れ基準の候補
- `.claude/skills/run/SKILL.md` の手順3に、記録行 `worktree path=... branch=... plan_head=...` を `vault/log/<計画ID>.md` へ追記する手順がある（`grep -n 'plan_head=' .claude/skills/run/SKILL.md` がヒットする）
- 手順3.4の「ファイルへの永続化は不要」という記述が削除されている（`grep -n '永続化は不要' .claude/skills/run/SKILL.md` がヒットしない）
- 手順2.2に、review 行の再開手順（記録行から worktree を復元する／worktree が無ければ doing・attempt+1）と、doing 行の再開手順（attempt+1 で creator を呼び直す・上限なら blocked）が書かれている（目視で確認）
- `docs/vault-spec.md` 7節に記録行の書式が追記されている（`grep -n 'plan_head=' docs/vault-spec.md` がヒットする）
- `bash scripts/smoke.sh` の最終行が `fail=0` になる（log の新しい書式が既存のフックを壊さない）

### 決定済み
- 記録先は log（タスク票の「進捗」ではない。理由は決定事項を参照）。計画票のタスク表の列は変えない
- 記録行は、手順3.7で creator の完了報告を受けた直後に、タスクごとに1行ずつ書く。複数タスクの場合は、手順3の中でまとめて追記する
- 再開時に参照するのは、その id の**最後の**記録行
- doing の中断では attempt+1 にする。無人実行のラッパー（F6）が同じ地点でタイムアウトし続けても、上限（`HARNESS_MAX_ATTEMPTS`）で blocked になって止まるようにするため。log の補足は `中断から再開`
- doing の中断時に残った worktree（記録行が無く、場所が分からないもの）は自動で削除しない。完了報告に `git worktree list` の出力を添えて、人に知らせる
- stop_gate.py・plan_guard.py は log を読まないので変更しない
- 「ハング時の復旧」節の手順は、このフェーズでは変えない（F6 で扱う）

## フェーズ6 無人実行用のタイムアウト付きラッパーを追加する（#79）

### ゴール文

### 受け入れ基準の候補

## 今回やらないこと

- **draft→approved・blocked→他 の遷移をフックでブロックすること**：人の回答で警告にとどめた。「決めるのは人だけ」という原則9はそのまま維持する。残るのは、原則2に照らした「エージェントの独断による承認・解除を機械的には止められない」という一点。フックが人の指示と独断を見分けられないことによる技術的な制約で、見分けるための人の手作業を増やして自律性を下げるよりも、警告で見えるようにする方を選んだ。見分ける手段が見つかったら、別の設計文書で扱う
- **タスク表の done→他 の遷移の保護**：F2 はタスク票・verdict だけを保護する。計画票の行の保護は、上記の遷移ブロックと同じ論点（人の操作との見分け方）なので、同時に扱う
- **Agent 呼び出しをバックグラウンドで起動し、Monitor・TaskStop で監視する方式**：人の回答で、外側のラッパーだけにした
- **creator を haiku などの安いモデルに切り替えること**：F7 の集計で十分な件数が集まってから、別の計画で判断する
- **verifier のモデル別の集計**：F7 で記録はするが、集計の出力は creator のモデル別だけにする
- **「受け入れ基準が真偽で判定できる文か」の機械的な検査**：機械では判定しにくいので、planner・verifier の運用に残す
- **`vault/rules/` 実体への提案の反映を自動化すること**：既存の方針どおり、人が手作業で反映する
