作成エージェント・verifier・planner の全員に渡す git 運用ルールを1本のファイルに定め、`bash scripts/rules.sh creator`（および `verifier`・`planner`）で読めるようにする。

## 受け入れ基準
- 見出しが「目的 / ルール / 確認方法」の3つで、100行以内である。確認：`grep -c '^## ' vault/rules/common/git.md` が3、`wc -l < vault/rules/common/git.md` が100以下
- ブランチ粒度（1計画=1ブランチ、`/plan` が1つだけ切る）の記述がある。確認：`grep -c 'ブランチ' vault/rules/common/git.md` が1以上
- コミット粒度（作業ステップごとに小さく分ける）の記述がある。確認：`grep -c '作業ステップ' vault/rules/common/git.md` が1以上
- `gh pr create` までで、マージは人が行うこと・破棄は `git restore` のみを使うことの記述がある。確認：`grep -c 'gh pr create' vault/rules/common/git.md` と `grep -c 'git restore' vault/rules/common/git.md` がそれぞれ1以上
- `bash scripts/rules.sh creator` の出力に `vault/rules/common/git.md` が含まれる

## 決定済み
- 盛り込む内容（この6点をそのままルールとして書けばよい。書きぶりは `vault/rules/common/roles.md` に合わせる）
  1. ブランチは `/plan` 時に計画ごとに1つだけ切る（`work/<計画IDの英小文字>`）。1ブランチ=1計画で、作業はそのブランチに閉じる
  2. コミットは作業ステップごとに小さく分けて行う（例：タスクの成果物ができた時、状態遷移を書いた時）。1タスクの作業を1コミットにまとめない
  3. `main` へ直接コミットしない。すべてのコミットは計画のブランチ上で行う（フックで強制する。T-03 が対応する）
  4. 全タスクが `done` になったら `gh pr create` までを行う。マージは人が行い、エージェントは `gh pr merge` を実行しない
  5. 変更を破棄する時は `git restore` のみを使う。`git clean` / `git reset --hard` は使わない（`.claude/settings.json` の `permissions.deny` で拒否済み。外さない）
  6. コンフリクトが起きたら自己判断で解決せず、計画票のタスク表の該当タスクを `blocked` にして question に状況を書き、人の判断を仰ぐ
- このファイル自体が `vault/rules/` 配下のため、`doing`/`review` 中は `agent_write_guard.py` が書き込みを拒否する。このタスクが `doing` の間は人が `HARNESS_ALLOW_RULES_WRITE=T-01 claude` で起動している前提で進める。deny された場合、リモートセッションでその解除口が使えないなら、過去の回避策「`todo` のうちに内容を編集し、その後 `doing` にする」を使ってよい（それでも deny される場合は `blocked` にして人に報告する）
- `目的` の見出しには「1セッション1計画1ブランチの前提で、ブランチ・コミット・PR・破棄の運用を定める」旨を1〜2行で書く
- `確認方法` の見出しには「`bash scripts/rules.sh creator` の出力に含まれるか」「各行が真偽で判定できるか」を書く
