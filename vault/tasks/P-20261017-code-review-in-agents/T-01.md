# T-01 verifier の tools に Skill を足し、コードレビューを参照する基準の判定規則を書く

## 目的
verifier が Claude Code 組み込みの `/code-review`（Skill の `code-review`）を呼べるようにし、受け入れ基準がコードレビューを参照する時の判定方法（対象範囲・FAIL にする指摘・判定から外す指摘・人に渡す指摘）をドメインに依らない一般の規則として定める（GitHub Issue #214 の提案1・2）。

## 入力
- `.claude/agents/verifier.md`（今の定義。tools・手順・受け渡し・禁止・やらないこと）
- `docs/vault-spec.md` の6節（verdict.json の `reasons` の使い方）・11節（ルールと受け入れ基準の関係）
- `docs/vision.md` の原則5・7
- `.claude/skills/run/SKILL.md` の手順5（verifier に渡されるのはタスク ID と対象 worktree のパスだけ）

## 成果物
- `.claude/agents/verifier.md`（1ファイル）

## 受け入れ基準
- `grep -c '^tools: Read, Grep, Glob, Bash, Write, Skill$' .claude/agents/verifier.md` の出力が `1` である
- `grep -c '^## コードレビューを参照する基準の判定$' .claude/agents/verifier.md` の出力が `1` である
- `grep -c 'クラッシュ・データ破損・誤った結果' .claude/agents/verifier.md` と `grep -c '対象外（既存コード）:' .claude/agents/verifier.md` と `grep -c '人の判断が必要:' .claude/agents/verifier.md` の出力がどれも `1` である
- 「## コードレビューを参照する基準の判定」節が、決定済みの (1) 対象の行の見分け方 (2) 範囲と呼び方（worktree のパスを引数で明示する） (3) 差分で変えた行への致命的な指摘が残れば その行を `ok: false` にすること (4) 差分の外への指摘は FAIL の根拠にせず note と reasons に接頭辞付きで残すこと (5) 設計・仕様の変更が要る指摘は `ok: true` のまま reasons に接頭辞付きで書くこと (6) 致命的でない指摘では落とさないこと (7) 呼べなかった時の扱い の7点をすべて書いている（Read で節を読んで確かめる）
- `bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (ref-1) '` の出力が `1` である
- `bash scripts/smoke.sh 2>&1 | tail -1` の出力が `fail=0` で終わる

## 決定済み
- tools の行は `tools: Read, Grep, Glob, Bash, Write, Skill` にする（`Skill` を末尾に足すだけ。他のツールは足さない・順序を変えない）。`model` などほかの frontmatter は変えない
- 新しい節の見出しは `## コードレビューを参照する基準の判定` とし、「## 手順」節の後・「## 受け渡し」節の前に置く。「## 手順」の手順2（基準を1行ずつ判定する）か手順3（基準にない観点で落とさない）の近くに、コードレビューを参照する行はこの節に従う旨の1文を足してよい
- 節に書く内容（語句は次のとおりに書く）：
  - (1) 対象の行：受け入れ基準の行が `/code-review` の結果で真偽を決める行である時だけ、この節に従う。書き方の既定は「`/code-review` で差分に致命的な指摘が残っていない」。行の中で `/code-review` を説明・引用しているだけの行（文書の文言を確かめる行など）は対象にしない。どのタスクにレビューを求めるかは導入先の planner ルールが決め、ハーネスはレビューを強制しない（基準に無ければ `/code-review` を呼ばない）
  - (2) 範囲と呼び方：対象はそのタスクの差分で、`git -C <worktree のパス> diff --merge-base work/<計画IDの英小文字>` の差分（計画ブランチとの分岐点 PLAN_HEAD から HEAD まで。verifier の時点では収集コミットの後なので PLAN_HEAD..HEAD と同じ）。Skill ツールで `code-review` を呼び、引数に対象 worktree のパスを引数で明示して渡す（例：「対象は <worktree の絶対パス>。cd してから `git diff --merge-base work/<計画IDの英小文字>` の差分をレビューする」）。明示しないと呼び出し元の作業ディレクトリ（メインリポジトリ）をレビューしてしまうことを理由として書く。受け入れ基準の行に `/code-review` の引数（`effort`・`--max-findings` など）が書かれていればそのまま渡し、無ければ付けない（ハーネスは既定値を持たない）
  - (3) 致命的な指摘：差分で変えた行への指摘のうち、クラッシュ・データ破損・誤った結果 に当たるものが1件でも残っていれば、その受け入れ基準の行を `ok: false` にし、reasons に指摘の要点（ファイルと行・何が起きるか）を書く。語句「クラッシュ・データ破損・誤った結果」はファイル中に1回だけ書く
  - (4) 差分の外：差分で変えていない既存コードへの指摘は FAIL の根拠にしない。その行は `ok: true` のまま、`note` に `対象外（既存コード）: <指摘の要約>` を書き、同じ文を `reasons` にも入れる（run の手順7の取り出しで Issue にできるように。タスクで直せない指摘で FAIL が続き attempt を使い切るのを防ぐため）。根拠として差分の外のコードを読んでいても、指摘の場所が差分で変えた行なら差分内として扱う
  - (5) 人の判断：直すのに設計・仕様の変更が要る指摘は FAIL にしない。その行は `ok: true` のまま、`reasons` に `人の判断が必要: <指摘の要約と、何を決める必要があるか>` を書く（同じ文を `note` にも書く）。run はこの接頭辞の要素がある PASS を done にせず blocked にして人に渡す（run 側の手順は別タスクで書く）
  - (6) 致命的でない指摘（好み・軽微な改善）は、差分の内外を問わず FAIL の根拠にしない（既存の「基準にない観点で落とさない」と同じ）。note に件数程度を書くのはよい
  - (7) 呼べなかった時：`code-review` を呼べない・結果が返らない時は、その行を `ok: true` のまま、(5) と同じ接頭辞で「/code-review を実行できなかった（<理由>）」の要素を `reasons` と `note` に書く（run が blocked にして人に渡す。代わりの確認で済ませない。原則5）
- 接頭辞 `対象外（既存コード）:`・`人の判断が必要:` はコロンを半角にし、どちらもファイル中に1回だけ書く（(4) と (5) の説明の中で1回ずつ。(7) は「(5) と同じ接頭辞で書く」と書いて接頭辞そのものを繰り返さない）
- 「起点コミット」の語は使わない（smoke の `(agents-1)` が禁じている）
- 新しく作るファイルへのバッククォート参照は書かない（`(ref-1)` のため。既存の `scripts/transition.py` などは書いてよい）
- 6節の reasons の仕様（`docs/vault-spec.md`）への追記は T-05 で行うので、このタスクでは変えない
