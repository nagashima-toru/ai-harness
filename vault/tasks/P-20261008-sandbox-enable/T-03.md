# T-03 docs/install.md に導入先でサンドボックスを有効にする手順と既知の制約を書く

## 目的
`docs/install.md` に、導入先でサンドボックスを有効にしたい人向けの節を足す。`install.sh` は導入先の既存の `.claude/settings.json` に `sandbox` を足さないこと、手で足す時の設定、必要な `allowedDomains`、既知の制約を書く。

## 入力
- `vault/designs/D-013.md` の「フェーズ5 サンドボックスを有効にする」（ゴール文・受け入れ基準の候補・決定済み）
- `.claude/settings.json` の `sandbox`（T-01 で足したもの）
- `docs/install.md`（「ハーネスを更新する（2回目以降）」節と「アンインストール」節）
- `scripts/merge_settings_json.py` の docstring（足すのは hooks・`permissions.deny`・`worktree.baseRef` だけ）

## 成果物
- `docs/install.md`（1ファイル。節の追加だけ）

## 受け入れ基準
- 決定済みの見出しの節が1つ足され、ほかの `## ` 見出しは変わっていない：`grep -n '^## サンドボックスを有効にする（任意）$' docs/install.md` の出力が1行で、`grep -c '^## ' docs/install.md` の出力が `7`
- 節の中の JSON の例の `sandbox` が、`.claude/settings.json` の `sandbox` と同じ値である（Read で見比べる。キー・値・`allowedDomains` の3つのドメイン `github.com`・`*.github.com`・`*.githubusercontent.com` がそろっている）
- 節に、`install.sh`（`merge_settings_json.py`）は導入先の既存の `.claude/settings.json` に `sandbox` を足さないので、有効にしたい時は手で足すことが書かれている（Read）
- 節に、既知の制約として決定済みの3つ（Windows は WSL2 だけ・`gh` の認証・ssh の remote）が書かれている（Read。`grep -n 'WSL2' docs/install.md` の出力が1行以上）
- 節に、有効にした後の確かめ方として `docs/runbook.md` の「9. サンドボックスを確かめる」を参照するよう書かれている：`grep -n 'runbook.md.*サンドボックスを確かめる' docs/install.md` の出力が1行以上
- 節に、サンドボックスが使えない環境でもハーネスは動くこと（サンドボックスは任意で、使えない時はフックの Bash の解析が守りになる）と、Linux・WSL2 で必要な `bubblewrap`・`socat` の入れ方の案内が書かれている（Read。`grep -n 'bubblewrap' docs/install.md` の出力が1行以上）

## 決定済み
- 節の見出しは `## サンドボックスを有効にする（任意）` で、「ハーネスを更新する（2回目以降）」節の後、「アンインストール」節の前に置く。ほかの節は変えない
- 書くこと（順に）：
  1. 何のためのものか：Bash とその子プロセス（`python3`・`bash -c` を含む）の書き込みと通信を OS で制限し、フックの Bash の解析の抜け道（`python3 -c` による `vault/rules/` への書き込みなど）を塞ぐ。ハーネス本体（ai-harness）では有効にしてある
  2. 導入先には既定では入れない：`install.sh`（`merge_settings_json.py`）は導入先の既存の `.claude/settings.json` に `sandbox` を足さない。有効にしたい時は、導入先の `.claude/settings.json` に手で足す
  3. 足す設定：T-01 で `.claude/settings.json` に足した `sandbox` と同じ JSON の例（`json` のコードブロック）。`denyWrite` の2つ（`vault/rules/` と会話記録 `~/.claude/projects/`）と `allowedDomains` の3つの意味を一言ずつ添える。`allowedDomains` に Anthropic の API のドメインを入れない理由（入れ子の claude を動かさないため）、プロジェクトで必要な通信先（パッケージのレジストリなど）があれば足すことも書く
  4. 既知の制約：Windows は WSL2 だけ（WSL1・ネイティブの Windows では使えない）。`gh` の認証（キーチェーンなど OS の資格情報を読めず、サンドボックスの中で `gh` が認証に失敗することがある）。ssh の remote（通信先の制限は HTTP(S) の通信が対象で、`git@github.com:` の形の remote への ssh の push は通らないことがある。その時は https の remote にするか、人がサンドボックスの外で push する）。`failIfUnavailable` を設定していないので、サンドボックスが使えない環境では制限なしで起動し、その時はフックの Bash の解析だけが守りになる
  5. 確かめ方：設定はセッションの開始時に読まれるので、足した後は Claude Code を起動し直し、`docs/runbook.md` の「9. サンドボックスを確かめる」の手順で確かめる
- サンドボックスは任意の追加の守りで、ハーネスはサンドボックス無しでも同じに動く（フック・`permissions`・`agent_write_guard.py` は変えない）。節の冒頭の近くにこの一文を置く。サンドボックスが使えるかの前提も書く：macOS はそのまま、Linux と WSL2 は `bubblewrap` と `socat` が要る（導入先のパッケージマネージャで入れる、と書く。具体的なコマンドはディストリビューションごとに違うので書き切らない）。使えるかどうかは `/sandbox` で確かめる（`docs/runbook.md` の9節）
- 新規導入（導入先に `.claude/settings.json` が無い時）も `sandbox` は入らない（T-06 で `merge_settings_json.py` の `create` の経路が `sandbox` を除いて書く。計画票の人への質問1：案A）。節の「導入先には既定では入れない」の説明に「新規導入でも既存でも」と書く。`uninstall.sh` が取り除くのは足したもの（hooks など）だけで、手で足した `sandbox` は残るので、不要になったら人が消す、と一言書く
- `docs/runbook.md` の節は T-05 が作る。このタスクでは参照するだけで、`docs/runbook.md` は変えない
- 「アンインストール」節は変えない
