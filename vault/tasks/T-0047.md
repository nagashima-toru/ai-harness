# T-0047 `stop_gate.py` の読む先を計画票に変える（判定ロジックは保つ）

## 目的
`.claude/hooks/stop_gate.py` の読む先を `vault/todo.md` から「自分のブランチの計画票」
（`vault/plans/*.md` のうち `status: approved` の1件）のタスク表に変える。verdict の形式検査・
鮮度照合（`task`/`attempt` の一致）・attempt 上限の判定ロジックは意味を変えず、パス（タスク票・
verdict の場所）とメッセージ文言だけを計画票ベースに直す。

## 入力
- `.claude/hooks/stop_gate.py`（現行）
- `.claude/hooks/plan_guard.py`（T-0046 で新規作成。approved な計画票を1件見つける規則・
  `## タスク表` 以降の行を読む規則を同じ形でこのファイル内にコピーする。import はしない）
- `docs/vault-spec.md` 6節（verdict.json）・9節（Stop フックの判定）
- `vault/designs/D-001.md`「## フェーズ3」「### 新しいディレクトリ構造」
- `scripts/smoke.sh` の `== stop_gate.py ==` セクション（12ケース）と `make_todo`／
  `make_verdict`／`make_task` ヘルパー、T-0046 が追加した `make_plan`／`make_plan_task`

## 成果物
- `.claude/hooks/stop_gate.py`
- `scripts/smoke.sh` の `== stop_gate.py ==` セクション（新形式への書き換え）

## 受け入れ基準
- approved な計画票が1件見つかった時だけ、そのタスク表の doing/review 行と
  `vault/verdicts/<計画ID>/<タスクID>.json` を照合する。approved が0件なら判定を進めず許可し、
  2件以上なら「approved な計画票が2件以上ある」旨の理由でブロックする。確認：`scripts/smoke.sh` の
  新規ケース（0件→allow、2件以上→block）が通る
- 既存の `== stop_gate.py ==` の12ケース（doing・verdict無し／FAIL再試行／FAIL上限／PASS→done／
  PASS→done で許可／doing・review無し／attempt不一致／stop_hook_active／HARNESS_STRICT_STOP／
  HARNESS_MAX_ATTEMPTS、および形式不正5種）が `make_plan_task` ベースに書き換わり、全件通る。確
  認：`bash scripts/smoke.sh 2>&1` の `== stop_gate.py ==` セクションに `NG` が無い
- `.claude/hooks/stop_gate.py` から `vault/todo.md` への直接参照が消えている。確認：
  `grep -c 'todo.md' .claude/hooks/stop_gate.py` が0
- verdict の `task` フィールドは `<計画ID>/<タスクID>` 形式で比較し、一致しなければ「古い verdict」
  として扱う（従来どおり鮮度不一致でブロック）
- `bash scripts/smoke.sh | tail -1` が `fail=0` を含む

## 決定済み
- 計画票を見つける規則・タスク表を読む規則は `plan_guard.py`（T-0046）と同じにする（見出し
  `## タスク表` の前方一致、データ行の集め方）。ただしこのファイルへは import せず、関数をコピーし
  て持つ（`agent_write_guard.py` が既にこの方式を取っている。同じ流儀に合わせる）
- 計画 ID は frontmatter の `id:` を使う。無ければファイル名から `.md` を除いた文字列を使う
- approved が**0件**の場合は「判定しない＝許可」にする（fail-open）。まだ計画が無い状態や、この
  フェーズの移行中を通すため
- approved が**2件以上**の場合は**ブロックする**（fail-open にしない）。1ブランチ1計画の不変条件が
  壊れており、どの計画票を見て判定すべきか決まらない。ここで許可すると「壊れている時だけ検証ゲート
  が黙って無効になる」ことになり、安全機構として向きが逆になる。`plan_guard.py` は PostToolUse な
  ので、異常が編集以外の経路（マージ・チェックアウト・ファイルの持ち込み）で入った場合は次の編集
  まで検知できず、その間 Stop の強制が失われる。理由の文言は
  `[stop_gate] approved な計画票が2件以上あります（<ID>, <ID>）。1つだけ approved にしてください。`
  の形にする
- タスク票のパスは `vault/tasks/<計画ID>/<タスクID>.md`、verdict のパスは
  `vault/verdicts/<計画ID>/<タスクID>.json` に変わる（`count_acceptance_criteria` が読む先もこれに
  合わせる）
- メッセージ文言の言い換え：「`vault/todo.md` の status を…」→「計画票（`vault/plans/<計画
  ID>.md`）のタスク表の status を…」、「`vault/log/queue.md` に…」→「`vault/log/<計画ID>.md` に…」
- `stop_hook_active`／`HARNESS_STRICT_STOP`／`HARNESS_MAX_ATTEMPTS` の扱いは変更しない
- smoke ヘルパーは T-0046 の `make_plan_task <id> <status> <attempt>`（常に計画 ID `P-TEST`・
  `status: approved`）をそのまま使う。`make_verdict` は書き込み先を
  `$TMP/vault/verdicts/P-TEST/<id>.json` に、`make_task` は `$TMP/vault/tasks/P-TEST/<id>.md`
  （ディレクトリを `mkdir -p`）に変える。`write_verdict` も同様に保存先ディレクトリを変える。既存の
  `make_todo` 呼び出しは全部 `make_plan_task` に置き換え、このセクションからは `make_todo` を呼ばな
  くなる（ただし関数定義自体は T-0048 まで残す）
- 既存ケースの block/allow の期待値・部分文字列（"verifier"・"doing に戻し"・"blocked"・"done"・
  "古い"・"不正"・"一致しません" など）は変えない。読む先が変わるだけ

## 進捗
- 読んだルール: roles.md, creator.md
- `.claude/hooks/stop_gate.py` を全面書き換え。`plan_id_and_status`／`approved_plans` を

  判定を `vault/todo.md` の存在から `vault/plans` ディレクトリの存在に変更
- `parse_tasks` を「## タスク表」前方一致以降の行を読む形に変更（旧「## タスク」からの変更）。
  approved 0件→許可、2件以上→`[stop_gate] approved な計画票が2件以上あります（<ID>, <ID>）。
  1つだけ approved にしてください。` でブロック（決定済みの文言どおり）
  タスク票・verdict のパスを `vault/tasks/<計画ID>/<タスクID>.md`・
  `vault/verdicts/<計画ID>/<タスクID>.json` に変更。`task_key = "<計画ID>/<タスクID>"` を導入し
  verdict の鮮度照合をこの形式で行う。メッセージ文言を計画票ベースに言い換え（決定済みの対応表どおり）
- `scripts/smoke.sh`：`make_verdict`／`make_task`／`write_verdict` を `P-TEST` スコープ
  （`vault/verdicts/P-TEST/`・`vault/tasks/P-TEST/`）に変更し、`make_verdict` の JSON は
  `"task":"P-TEST/<id>"` にした。`== stop_gate.py ==` セクションの `make_todo` 呼び出しを全部

  approved 0件・2件以上の新規2ケースを追加（2件以上のケースは P-TEST の計画票が残ったままだと
  3件になってしまうため、先に `vault/plans` をリセットしてから P-A/P-B のみを作る形にした）
