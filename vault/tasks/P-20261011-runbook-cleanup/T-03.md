# T-03 runbook の4〜10節と「困ったとき」を人向けに整理する

## 目的
`docs/runbook.md` の4〜10節と「困ったとき」を「人が打つコマンド・人が判断すること・人が見る場所」に絞り、エージェントの内部動作は1〜2行の要約とリンクにする。環境変数の説明は `docs/configuration.md` へのリンクにする。

## 入力
- `docs/runbook.md`（4〜10節・「困ったとき」。冒頭と0〜3節は T-02 で整理済み）
- `docs/vault-spec.md`（1節・2節・5節・7節・11節と、T-01 で足した12節の「### 作業ブランチの git の復旧」）
- `.claude/skills/plan/SKILL.md`（A の手順2・B）・`.claude/skills/run/SKILL.md`（手順3・手順7）
- `docs/configuration.md`・`docs/guide.md`（runbook の節へのリンク）
- 設計文書 `vault/designs/D-20261011-user-guide.md` の「決定事項」とフェーズ3

## 成果物
- `docs/runbook.md`（1ファイル。4〜10節と「困ったとき」だけを変える）

## 受け入れ基準
- 4〜10節と「困ったとき」の各節の本文が人の打つコマンド・判断・見る場所で、エージェントの内部動作は1〜2行の要約とリンクだけになっている。節ごとの方針（残したもの・削ってリンクにしたもの・その移し先）がタスク票の「進捗」に書かれ、verifier が節ごとに読んで確かめる
- `grep -c 'blocked→todo 人の指示' docs/runbook.md` が `0` で、`sed -n '/^## 4\./,/^## 5\./p' docs/runbook.md | grep -cF '`.claude/skills/plan/SKILL.md`'` が1以上
- `grep -cE '^[0-9]\. (計画 ID が|現在のブランチの計画でない|計画票が `status: done`|タスク表が全行)' docs/runbook.md` が `0` で、`sed -n '/^## 5\./,/^## 6\./p' docs/runbook.md | grep -cF '`docs/vault-spec.md` 1節'` が1以上
- `grep -c 'permissions.deny' docs/runbook.md` が `0` で、`sed -n '/^## 困ったとき/,$p' docs/runbook.md | grep -cF '`docs/vault-spec.md` 12節'` が1以上
- `grep -cE '^ *- 環境変数 `HARNESS_' docs/runbook.md` が `0` で、`sed -n '/^## 8\./,/^## 9\./p' docs/runbook.md | grep -c 'docs/configuration.md'` と `sed -n '/^## 10\./,/^## 困ったとき/p' docs/runbook.md | grep -c 'docs/configuration.md'` がどちらも1以上
- `grep -n '^## ' docs/runbook.md` の出力の見出しの文言が「決定済み」の12行と同じ順で一致し、`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (guide-1) '` が `1`
- `bash scripts/smoke.sh 2>&1 | tail -1` が `smoke: pass=<数> fail=0`、`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (ref-1) '` が `1`

## 決定済み
- `## ` 見出しは変えない。期待する `grep -n '^## ' docs/runbook.md` の見出しの文言（行番号は変わってよい）：`## 0. 大きなゴールは先に設計する`・`## 1. ゴールを入れる`・`## 2. 計画は自動で承認される`・`## 3. キューを回す`・`## 4. blocked に答えて戻す`・`## 5. 一括削除の手順`・`## 6. ルールを足す`・`## 7. ハーネス自体の更新を取り込む`・`## 8. creator のモデルを比べる`・`## 9. 権限モードの選び方`・`## 10. push 先が決められている環境（クラウドセッション）`・`## 困ったとき`。節の中に `###` の小見出しを足すのはよい。
- 冒頭と0〜3節は変えない（T-02 で整理済み）。
- 削る基準（設計の決定済み）：同じ内容が `docs/vault-spec.md` かスキルにある時だけ削ってリンクにする。下の一覧に無い内部の記述で、vault-spec にもスキルにも同じ内容が無いものを見つけたら、消さずに runbook に残し、「進捗」に「移し先が無いため残した」と書く（blocked にしない。vault-spec はこのタスクの成果物ではない）。
- リンクの書き方は runbook の既存の形にそろえ、パスをバッククォートで書いて節・手順を続ける（例：`` `docs/vault-spec.md` 1節 ``・`` `docs/vault-spec.md` 12節 ``・`` `.claude/skills/plan/SKILL.md` ``・`` `docs/configuration.md` ``）。受け入れ基準の grep はこの文字列を探すので、この形で書くこと。
- 節ごとの方針：
  - 4節：コマンド、人の手順（計画票の `question` を読む、`/plan unblock <計画ID> <id> <回答>` を打つ、回答を省いてよい場合、1回で1行だけ解除）、解除の後は `/run` で再開すること、エディタで直す代替手段を残す。エージェントが行う4つの箇条書き（決定済みへの追記・行を todo に戻す・log の行・コミット）は1〜2行の要約と `.claude/skills/plan/SKILL.md` の「B. blocked を解除する」へのリンクにする。log の行の形（`blocked→todo 人の指示: …`）は書かず、代替手段の説明では「log に `docs/vault-spec.md` 7節の blocked の解除の形の行を追記してコミットする」とリンクで示す。「フックでは確かめない（D-015 フェーズ2 で廃止）」の経緯は削る（`docs/vault-spec.md` 2節にある）。エージェントが人の指示なしに解除しないことは1行で残してよい。
  - 5節：目的（ベースブランチに残ったマージ済みの計画一式と旧方式の `vault/archive/` を片づける）、実行するコマンドのブロック（`git switch -c …` から `git commit …` まで）、PR を作って人がマージすること、`--report` を見て未解決のもの・改善提案を人が Issue 化してから `--apply` すること、`--apply` は人だけが実行しコミットはしないこと、未コミットの変更があると何も消さずに終了コード1になること、旧形式の計画・タスク票は対象外で人が `git rm` すること、`vault/harness-improvements/<計画ID>.md` も対象外であること、を残す。番号付きの対象の条件（1〜5）と `--report` の出力の形と人だけが実行する理由は削り、`docs/vault-spec.md` 1節へのリンクにする（同じ内容が1節の `purge_plan.sh --merged` の段落にある。1節が「手順は `docs/runbook.md` 5節」と参照しているので、手順は5節から動かさない）。
  - 6節：人の手順1〜3はそのまま。手順4のフックと差分ゲートの説明は1行の要約にし、`docs/vault-spec.md` 11節（ルール）と5節（差分ゲート）へのリンクにする。
  - 7節：人向けなのでそのまま（詳細は `docs/install.md` の「ハーネスを更新する（2回目以降）」へのリンクのまま）。
  - 8節：人の手順はそのまま残す。手順1の環境変数 `HARNESS_CREATOR_MODEL` の説明は `docs/configuration.md` へのリンクを添える。「起動後に変えても run の Bash には効かない場合があるので起動し直す」の注意は残す（`docs/configuration.md` が「`docs/runbook.md` 8節と同じ注意」と参照しているため）。手順3（creator の呼び出しが失敗した時の run の動き）は `.claude/skills/run/SKILL.md` 手順3へのリンクのまま。手順5（`usage_stats.py` の model 列の表記の違い）は人が出力を読む時の注意なので残す。
  - 9節：人の判断なのでそのまま。
  - 10節：人がすること（`HARNESS_PUSH_BRANCH` に指定ブランチ名を渡す、値が毎回同じなら `.claude/settings.json` の `env` に書いてよい、ローカルでは `work/…` で作業し push 先と PR の head がその値になること、non-fast-forward で止まった時は人が判断すること）を残し、`docs/configuration.md` へのリンクを足す。オーケストレーターがコマンドに値を渡す仕組み（`/plan`・`/design` の開始条件の確認と `vcs_finish.sh` に付ける、`Bash(env *)` で通る）は1〜2行の要約と `.claude/skills/plan/SKILL.md` 手順A の2・`.claude/skills/run/SKILL.md` 手順7へのリンクにする。`env HARNESS_PUSH_BRANCH=<指定ブランチ> bash scripts/vcs_finish.sh` のコード例は残してよい。
  - 困ったとき：表は人が見る場所なので残す。表の後の段落（エージェントが自分で直してよいこと・`permissions.deny` に残っているもの・D-015・診断スクリプトが無いこと）は削り、「上の git の3行の復旧をエージェントがどこまで自分で行うかは `docs/vault-spec.md` 12節の「作業ブランチの git の復旧」」の1行にする（T-01 で移し済み）。
- 文体は今の runbook に合わせる（である調、パスはバッククォート）。存在しないパスをバッククォートで書かない（smoke の `(ref-1)` が検査する）。
