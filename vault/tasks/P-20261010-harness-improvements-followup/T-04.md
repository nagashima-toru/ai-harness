## 決定済み
- run 手順7（「全タスクが `done` になったら、次の順で PR を作る」）の番号付きの段を次の6つにする（1つ目は今のまま、2つ目を足し、今の2〜5を3〜6に繰り下げる）
  - 2（足す）：`git add vault/plans/<計画ID>.md` を実行し、続けて `git commit -m "<計画ID>: approved→done" -- vault/plans/<計画ID>.md` を実行する（それぞれ1回の Bash で。ほかの変更を混ぜない）。理由の1文：`scripts/vcs_finish.sh` は計画票の変更をコミットしないので、ここでコミットしないと未コミットのまま push される。この2つのコマンドは上の字面のまま書く
  - 5（今の4。`vcs_finish.sh` の実行）：GitHub は `gh api`（REST）で PR を作り、作った PR の URL が標準出力に出る、と書き足す。ほかは今のまま
- run 手順7の後ろの2つの箇条（引数なしの経路と MCP の代替）を次の趣旨に直す
  - 引数なしの経路：計画が見つかればタスク履歴表を本文に `<計画ID>: <ゴールの1行目>` のタイトルで作る（今のまま）。計画が見つからない時（`design/d-xxx` など）は、GitHub は最新コミットの件名と本文で REST の PR を作り、GitLab は `glab mr create --fill --yes` を使う。引数がある時は既定を付けず、GitHub は `gh pr create`、GitLab は `glab mr create` にそのまま渡す（`gh pr create --fill` の字面は書かない）
  - MCP の代替：対象は `vcs_finish.sh` が `gh`/`glab` が無いことで終わった時（終了コード127、または「コマンドが見つかりません」の明示エラー）のまま。引き継ぐものは「`gh api` の PR 作成に渡すはずだった」タイトル（`HARNESS_PR_TITLE` の値）・本文（本文ファイルの中身）・head（現在のブランチ）・base（`main`）と書き、この「`gh api` の PR 作成に渡すはずだった」の字面を段落に1回書く。`gh` はあるが REST の呼び出しが失敗した時（認証エラー・ネットワークエラー・owner/repo が取れない終了コード2など）は代替の対象外とし、標準エラーの内容を添えて人に報告して止まる。`gh pr merge`/`glab mr merge` を実行しないことは今のまま
- run 手順8の3・4を次の趣旨に直す
  - 3：構造的な改善点に気づいたら、本文を Write ツールで一時ファイル（例：`/tmp/<計画ID>-issue-body.md`）に書き、`gh api repos/{owner}/{repo}/issues -X POST -f title=<タイトル> -F body=@<本文ファイル> --jq .html_url` で issue を1件起票する。`{owner}`・`{repo}` は `gh` がカレントのリポジトリの remote から埋めるプレースホルダで、そのまま書く。理由の1文：Claude Code の Web セッションでは GraphQL が使えず `gh issue create` が HTTP 403 で失敗するため（理由の文でも `gh issue create` の字面は書かず「GraphQL を使う `gh` のサブコマンド」などと書く）
  - 4：`gh api` の起票が失敗した場合（権限の確認で拒否された場合を含む）は、今どおり提案を `vault/harness-improvements/<計画ID>.md` に書き残し、完了報告で人に伝える
  - 6（足す）：提案ファイル `vault/harness-improvements/<計画ID>.md` の扱い：提案に対応した計画が、その計画の中でそのファイルを削除する（削除はその計画のタスクの成果物にする。対応していない提案のファイルは残す）。この「提案に対応した計画が、その計画の中でそのファイルを削除する」の字面のまま書く
- `.claude/settings.json` は変えない（`Bash(gh api *)` は許可リストに足さない。任意の API を呼べ `gh pr merge` の拒否を迂回できるため）。権限で止まった時は上の4で扱う
- 「## 注意」の `vault/rules/` の行を次の趣旨に直す：オーケストレーターはタスク中に `vault/rules/` を編集しない（verifier の判定基準を自分で変えないため）。フックは止めない。creator のタスクでは「成果物」に宣言した時だけ変えられ、宣言の無い変更は差分ゲート（`scripts/diff_gate.py`）が差し戻す。「フックでも拒否される」の字面は書かない
- design スキル手順8の MCP の段落：対象（`gh`/`glab` が無い時）は今のまま。「`gh pr create` に渡すはずだった」を「`gh api` の PR 作成に渡すはずだった」に直し（この字面を1回書く）、認証エラー等の対象外の文は「`gh` はあるが REST の呼び出しが失敗した時」の趣旨に直す
- バッククォートで `vault/harness-improvements/` のディレクトリだけを書かない（T-07 で4ファイルを消すとディレクトリが無くなり、smoke の参照切れの検査（`(ref-1)`）が落ちる）。書く時は `vault/harness-improvements/<計画ID>.md` の形にする
- 足す smoke のケース（`scripts/smoke.sh` の末尾の「主な文書の参照切れの検査」の前に置く。名前は `(run-skill-<番号>)` で始め、1ケース1行の `ok`/`NG`）：
  - `(run-skill-1)` `.claude/skills/run/SKILL.md` の `## 7.` から `## 8.` の手前までで、`git add vault/plans/<計画ID>.md` を含む最初の行が、`bash scripts/vcs_finish.sh` を含む最初の行より前にある
  - `(run-skill-2)` `.claude/skills/run/SKILL.md` に `gh issue create` が無く、`gh api repos/{owner}/{repo}/issues` がある
  - `(run-skill-3)` `.claude/skills/run/SKILL.md` と `.claude/skills/design/SKILL.md` の両方に「`gh api` の PR 作成に渡すはずだった」がある
