# T-01 planner.md に「成果物以外の変更が無いこと」の恒久指針を追記する提案を書く（issue #51）

## 目的
`vault/rules/planner/planner.md` の「やらないこと（このリポジトリで実際に起きた失敗から）」節に、「成果物は `<ファイル>` のみで、他ファイルは変更していない」という形の受け入れ基準を書く際の恒久的な指針を追記する提案をまとめる。creator が doing 中にタスク票自身の「進捗」節へ追記するため、この形の確認コマンドが成果物の出来に関わらず毎回非空でFAILする問題（issue #51）を、今後 planner が同種のタスクを計画するたびに再発させないようにする。ルール実体への反映は人が行うため、このタスクでは提案ファイルを書くところまでとする。

## 決定済み
- 提案ファイル方式に従う（`docs/vault-spec.md` 12節）。実体（`vault/rules/planner/planner.md`）は `agent_write_guard.py` が常に拒否するため直接編集しない
- 追記先は「やらないこと（このリポジトリで実際に起きた失敗から）」節の末尾（issue #46 対応で追記済みの `rm -rf` 前提の項目の直後）に1項目追加する形。既存項目の書き換えはしない
- 選択肢A・Bのどちらを採用するかは issue #51 で planner（このタスクの creator）に委ねられている。人からの直接指示により、この計画では**両方を併記する**方針とする。具体的には次の2点を1項目（見出し1行＋説明段落）としてまとめる：
  1. 「成果物は `<ファイル>` のみで、他ファイルは変更していない」という形の受け入れ基準を書く場合、確認コマンドの除外パスに成果物だけでなく**タスク票自身のパス**（`vault/tasks/<計画ID>/<id>.md`）も含める。理由：creator は doing 中にタスク票自身の「進捗」節へ追記するため（`docs/vault-spec.md` 5節）、除外しないと成果物の出来に関わらず毎回非空でFAILする（`P-20260925-sandbox-hang-timeout`/T-01 で3回連続FAILした実例、issue #51）
  2. 代替として、このパターンの受け入れ基準自体を書かず、`vault/rules/verifier/verifier.md` に既にある**起点コミットベースの検査**（creator が「進捗」に `起点コミット: <hash>` を記録し、verifier が `git diff --name-only <起点コミット>..HEAD` で宣言外ファイルを検出する仕組み。計画票・タスク票の進捗・`vault/log/`・`vault/verdicts/` は自動的に除外される）に委ねることも検討する。ただしこれは creator が起点コミットを記録した場合のみ有効なため、確実性を重視する場合は1の除外パス方式を優先する
- 成果物ファイルの構成は自由（`T-03-proposal.md` の「追記内容」「反映後の該当ファイル全文（参考）」という構成を踏襲してよいが必須ではない）
- `.claude/settings.json`・`.claude/hooks/`・`vault/rules/` の実体は変更しない（触らない）
- verifier が確認する grep 対象語（「vault/rules/planner/planner.md」「タスク票自身」「起点コミット」「#51」）は本タスク票の受け入れ基準・この決定済みで明示済みなので、提案文に必ずこれらの語を使うこと
- `P-20260925-sandbox-hang-timeout`/T-01 の経緯（3回連続FAILし人が個別に確認コマンドを修正した記録）は、issue #51 本文の「経緯」節にも転記されている。creator は git 履歴や archive を探しに行く必要はない（当時の関連コミットは `39bfc9c` 等。参照したい場合は `git show 39bfc9c:vault/tasks/P-20260925-sandbox-hang-timeout/T-01.md` で読める）
