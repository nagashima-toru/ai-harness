# ゴール

D-012（done の不変条件・状態遷移スクリプト・差分ゲート）で扱わなかったハーネスの課題を片づける。扱うのは次の7つ。

- Stop フックが計画の無いセッションでも働いてしまい、無人実行では2回目の停止を必ず通してしまう
- verifier の指摘（基準が緩い・判定不能など）がどこにも使われていない
- creator を安いモデルに下げてよいかを判断する材料が無い
- 標準の役割定義が `vault/rules/` と `.claude/agents/` に二重にあり、ハーネス自身の作業では直せない
- 許可リストの `python3`・`bash` などを経由すると deny を回り込める
- worktree 委譲で、creator が書き換えたフックが creator 自身の worktree の外への書き込みを判定する
- 文書の記述が古くなっていて、参照切れが再発する

## フェーズ1 Stop フックの適用範囲と無人実行での厳格化

### ゴール文

`.claude/hooks/stop_gate.py` の判定順を変える。

- 承認済みの計画票が0件なら、未コミットの検査も含めて何もせずに許可する
- 2件以上なら、今どおりブロックする
- 1件の時だけ、未コミットの検査と既存の判定を行う

あわせて、`scripts/run_unattended.py` が子プロセスを起動する時、環境変数 `HARNESS_STRICT_STOP` が設定されていなければ `1` を入れて渡すようにする。`docs/vault-spec.md` 9節の判定表と、`docs/runbook.md` の無人実行の説明を合わせて更新する。

### 受け入れ基準の候補
- 承認済みの計画票が無い git リポジトリで、未コミットの変更があっても `stop_gate.py` が許可する（smoke にケースとして追加する）
- 承認済みの計画票が1件ある git リポジトリでは、未コミットの変更があれば今どおり「未コミットの変更があります」でブロックする（smoke）
- `run_unattended.py` は、`HARNESS_STRICT_STOP` が未設定なら子プロセスに `1` を渡し、設定済みならその値を変えない。確認は、`HARNESS_RUN_CMD` に環境変数を出力するコマンドを渡して行う（smoke）
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む
- `docs/vault-spec.md` 9節の判定表が新しい判定の順序になっており、`docs/runbook.md` の無人実行の節に `HARNESS_STRICT_STOP` の既定が書かれている

### 決定済み
- 判定の順序：
  1. `stop_hook_active`（今どおり）
  2. approved な計画票の件数（0件なら許可、2件以上ならブロック）
  3. 未コミットの変更
  4. doing/review の行の検査（D-012 フェーズ1が済んでいれば、done の行の検査もここに入る）
- ブランチ名は見ない。承認済みの計画票はその計画のブランチにしか無く、`main` では PR を作った時点で done になっているため
- `HARNESS_STRICT_STOP=0` を明示すれば、無人実行でも従来の動きにできる
- 既存の smoke の (f)・(g) と、worktree で未コミットの変更を検査するケースは、承認済みの計画票を置く前提に直してよい。期待値は変えない。直したケースは PR 本文に列挙する
- `run_unattended.py` が vault に書かないという既存の方針は変えない
- 対話実行での `stop_hook_active` の既定（2回目は通す）は変えない

### 依存
D-012 フェーズ1（同じ `stop_gate.py` を編集するため、順に進める）

## フェーズ2 verifier の指摘を見えるようにする

### ゴール文

1つの計画の verdict の `reasons` を一覧にする `scripts/verdict_notes.py <計画ID>` を新設する。run の手順7（全タスクが done になった後）で、その出力を完了報告に含め、PR 本文にも入れる。そのために `scripts/vcs_finish.sh` に、環境変数 `HARNESS_PR_BODY_FILE`（本文のファイル）と `HARNESS_PR_TITLE` を受け取る経路を足す。あわせて、`scripts/model_stats.py` に、最後の verdict の `reasons` が空でないタスクの割合の列を足す。

### 受け入れ基準の候補
- `verdict_notes.py <計画ID>` は、その計画の verdict のうち `reasons` が空でないものを `<id>: <reason>` の形で1行ずつ出す。1件も無ければ「指摘なし」の1行だけを出す（smoke にケースとして追加する）
- `vcs_finish.sh` は `HARNESS_PR_BODY_FILE` が設定されていて引数が無い時、GitHub では `gh pr create` に `--title` と `--body-file` を渡し、GitLab では `glab mr create` に `--title`・`--description`・`--yes` を渡す（smoke：`gh`・`glab` をスタブにして、渡された引数を確かめる）。未設定の時の動きは変わらない（既存のケース）
- `model_stats.py` の出力の末尾に列 `noted_rate`（最後の verdict の `reasons` が空でないタスクの割合）が足され、既存の列と値は変わらない（smoke）
- `run/SKILL.md` の手順7に、次の2つが書かれている
  - `verdict_notes.py` の出力を本文ファイルに書き、`HARNESS_PR_BODY_FILE` で `vcs_finish.sh` に渡すこと
  - 同じ出力を完了報告に含めること
- `docs/vault-spec.md` の6節（reasons の使われ方）と7節（`model_stats.py` の出力列）が更新されている
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- `reasons` は言い換えずにそのまま出し、分類はしない（verifier の書き方に決まった接頭辞が無いため）
- 読み込み先は、既定で `vault/verdicts/<計画ID>/*.json`。`--dir <ディレクトリ>` で別の場所（archive など）を指定できる
- PR のタイトルは、`HARNESS_PR_TITLE` が無ければ計画 ID にする
- run が作る本文には、次の3つを入れる
  - 計画 ID
  - タスク一覧（id と title）
  - 「verifier の指摘」節（`verdict_notes.py` の出力）
- `noted_rate` の verdict の場所は、log ファイルのパスから決める（`<base>/log/<計画ID>.md` → `<base>/verdicts/<計画ID>/<id>.json`）。verdict が無いタスクは「指摘なし」として数える
- 新しい列は末尾に足す（既存の列を読む処理を壊さないため）
- verifier の定義とルールは変えない（人の回答：見えるようにするだけ）

## フェーズ3 creator のモデルの切り替えと計測

### ゴール文

1. 環境変数 `HARNESS_CREATOR_MODEL` が設定されていれば、run は creator を呼ぶ Agent ツールの `model` にその値を指定する。
2. D-012 の `scripts/transition.py` が log に書く `creator=` の値は、`HARNESS_CREATOR_MODEL` を優先し、無ければ `.claude/agents/creator.md` の frontmatter の値にする。
3. `scripts/usage_stats.py` を新設する。会話記録に残る Agent 呼び出しの結果から、エージェントの種別×モデルごとに、呼び出し回数・トークン数・所要時間を集計して出す。
4. `docs/runbook.md` に、安いモデルを試して比べる手順を書く。

### 受け入れ基準の候補
- `HARNESS_CREATOR_MODEL=haiku` の時、`transition.py` の doing→review の log の行に `creator=haiku` が付く。未設定の時は今どおり frontmatter の値が付く（smoke にケースとして追加する）
- `usage_stats.py` は、smoke の中で作ったサンプルの会話記録（JSONL）から、`agentType`・`resolvedModel` ごとの呼び出し回数・トークン数の合計と平均・所要時間の平均をタブ区切りで出す（smoke）
- 想定と違う行（JSON でない行、`toolUseResult` が無い行、キーが欠けている行）は読み飛ばし、エラーで止まらない（smoke）
- `run/SKILL.md` の creator の呼び出しの手順に、`HARNESS_CREATOR_MODEL` があれば Agent ツールの `model` に渡すことと、その値の確かめ方が書かれている
- `docs/runbook.md` に次の手順が書かれている：`HARNESS_CREATOR_MODEL=haiku` で計画を回し、`model_stats.py` と `usage_stats.py` の出力を sonnet の時と比べる
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- 切り替えの対象は creator だけ。verifier・planner のモデルは変えない
- run が環境変数を確かめる方法は `echo "${HARNESS_CREATOR_MODEL:-}"`（許可リストの `echo` で通る）
- 値の検査はしない。Agent ツールが受け付けない値なら呼び出しが失敗するので、run はその時点で止めて報告する
- `usage_stats.py` の読み込み先：
  - 既定は `~/.claude/projects/<プロジェクトの絶対パスの / を - に置き換えたもの>/*.jsonl`（メインセッションの会話記録）
  - 引数でファイルやディレクトリを渡せる
  - 読むだけで書かない（会話記録への書き込みはフックが拒否する）
- 読む項目は、各行の `toolUseResult` のうち `agentType` を持つものの `resolvedModel`・`totalTokens`・`totalDurationMs`・`totalToolUseCount`。`prompt` から `<計画ID>/<id>`（正規表現 `P-\d{8}-[a-z0-9-]+/T-\d{2}`）が取れれば、`--plan <計画ID>` で絞り込める
- 出力はタブ区切りで、見出しは `agent	model	calls	tokens_total	tokens_avg	duration_avg_s`
- 会話記録の形式は公開仕様ではない（`docs/vault-spec.md` 12節と同じ扱い）。形式の変化は smoke のサンプルで検知する
- haiku でどの計画を試すかは人が決める。この設計で作るのは仕組みまで

## フェーズ4 標準の役割定義をエージェント定義に統合する

### ゴール文

`vault/rules/` にある標準の役割定義6本の内容を `.claude/agents/creator.md`・`verifier.md`・`planner.md` に統合し、`vault/rules/` を導入先のルール専用にする。6本は次のとおり。

- `common/roles.md`
- `common/git.md`
- `creator/creator.md`
- `creator/git-workflow.md`
- `verifier/verifier.md`
- `planner/planner.md`

あわせて、次のものを「ハーネスは標準ルールを同梱しない。役割定義は `.claude/agents/` にある」という形に合わせる。

- `scripts/install.sh`：6本を配らないようにし、`--update` では既存の導入先にある6本のうち未編集のものを削除する
- `scripts/uninstall.sh`
- `docs/vault-spec.md` 11節
- `README.md` の拡張ポイントの節

エージェントは `vault/rules/` に書き込めないため、6本の削除と `vault/rules/README.md` の書き換えは人が行う。`vault/rules/README.md` の書き換え内容は提案ファイルにする。

### 受け入れ基準の候補
- `.claude/agents/creator.md`・`verifier.md`・`planner.md` に、統合元の各ファイルの「ルール」節の箇条が同じ意味で書かれている。ただし、決定済みで落とすと決めたものは除く（統合元1本ごとに、対応する統合先の定義と見比べて判定する）
- `bash scripts/install.sh <一時ディレクトリ>` が6本を複製しない（smoke にケースとして追加する）
- 6本が入っている既存の導入先に `install.sh --update` を実行すると、未編集のものは削除され、編集済みのものは残って `note` の行で案内される（smoke）
- `uninstall.sh` が6本の有無にかかわらず正しく動き、利用者が置いたルールには触れない（smoke）
- `docs/vault-spec.md` 11節と `README.md` の拡張ポイントの節が、「ハーネスは標準ルールを同梱しない。役割定義は `.claude/agents/` にある」という形になっている
- `vault/rules/README.md` の変更案が `vault/tasks/<計画ID>/<id>-proposal.md` にある
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- 統合の対応：
  - `roles.md` の各節（人→planner、planner→creator、creator→verifier、verifier→creator/人、creator→人）は、その節の送り手と受け手にあたるエージェント定義に、それぞれ必要な分を書く
  - `git.md`・`git-workflow.md` は主に `creator.md` に書く。verifier・planner に関係する部分（git 操作をしない、など）だけをそれぞれに書く
- 統合する時、今の `run/SKILL.md`・`docs/vault-spec.md` と矛盾する記述は落とす。落としたものは PR 本文に列挙する。例：
  - 「doing は常に1件だけ」
  - 「`vault/log` に追記したか」
  - 「作成エージェント（run のメイン）」
- 「やらないこと（このリポジトリで実際に起きた失敗から）」にある失敗の例（T-0002 など）は残す
- 1つのエージェント定義の長さは、150行以内を目安にする
- `vault/rules/planner/ai-harness-lessons.md`（このリポジトリ固有で、配布しない）は残す
- `scripts/rules.sh` は変えない（標準ルールが無くなれば、導入先のルールだけを列挙する）
- `install.sh --update` が「未編集」かどうかは、既存のマニフェストのハッシュで判定する
- 6本の削除（`git rm`）と、提案ファイルを `vault/rules/README.md` へ反映するのは、人が PR のマージ前に同じブランチで行う。それまでの間、エージェントは両方を読むことになるが、内容は同じ趣旨なので害は無い
- タスクはエージェント定義ごとに分ける（成果物を1つに保つ）

## フェーズ6 worktree 委譲の範囲を絞る

### ゴール文

`.claude/hooks/agent_write_guard.py` が worktree の版のフックへ判定を委譲するのを、書き込み対象がすべて委譲先の worktree の中にある時だけにする。

- 書き込み対象に worktree の外のパス（メインリポジトリ・`~/.claude/projects/` など）が1つでもあれば、委譲せずにメインリポジトリ側のコードで判定する
- 書き込み対象が無い呼び出し（読み取りだけ）は、今どおり委譲する

`docs/vault-spec.md` 12節に委譲の範囲を書く。

### 受け入れ基準の候補
- cwd が worktree で、書き込み対象がその worktree の中だけの時は、今どおり委譲先の判定が使われる（既存の (delegate) ケースが PASS する）
- cwd が worktree で Write の `file_path` がメインリポジトリの `vault/rules/` 配下の絶対パスの時、委譲先を常に allow を返すものに差し替えても、メインリポジトリ側の判定で拒否される（smoke にケースとして追加する）
- Bash の書き込み対象にメインリポジトリ側の絶対パスや `~/.claude/projects/` を含む時も、同じく拒否される（smoke）
- 解析できない Bash（和集合の候補で判定する形）で、候補に worktree の外のパスが1つでもあれば委譲しない（smoke）
- `docs/vault-spec.md` 12節に、委譲するのは書き込み対象がすべて worktree の中にある時だけであることが書かれている
- 既存の smoke が全件 PASS する。確認：`bash scripts/smoke.sh | tail -1` が `fail=0` を含む

### 決定済み
- 書き込み対象は、既存の `file_path` と `bash_write_targets` から求める。相対パスは payload の `cwd`（worktree）を基準に解決する
- 委譲するかどうかは、`agent_write_guard.py` の中で `delegate_to_worktree` を呼ぶ前に判定する。`plan_guard.py`・`stop_gate.py` の委譲は変えない（書き込み対象という考え方が無いため）
- worktree の中の判定は、今どおり worktree 側のコードが行う（D-008 の目的を保つ）
- パスの比較は `os.path.realpath` で行う。macOS の `/var` → `/private/var` の食い違いに気をつける（smoke の既存のコメントを参照）
