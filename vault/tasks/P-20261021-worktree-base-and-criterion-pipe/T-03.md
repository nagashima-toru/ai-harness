# T-03 run 手順3で creator の worktree を add_worktree.sh で作り、3.6 に既知の原因と回避策を書く

## 目的
Issue #209。`/run` の手順3で、creator の worktree を Agent ツールの worktree 隔離ではなく `scripts/add_worktree.sh`（T-02 で作成）で `PLAN_HEAD` から作り、パスを prompt で渡す経路に切り替える。手順3の6に、分岐元が計画ブランチにならない症状の既知の原因と回避策を書く。

## 入力
- `.claude/skills/run/SKILL.md`（手順3の1〜8、「ハング時の復旧」の1、「Agent 呼び出しがエラーで返った時」の2の creator）
- `scripts/add_worktree.sh`（T-02 の成果物。冒頭のコメントに使い方・出力・終了コードがある）
- `.claude/agents/creator.md` の「入力」節（`作業する worktree: <パス>` を受け取った時の動き）
- `docs/runbook.md`（`/plan unblock` の `--fresh` の説明）

## 成果物
- `.claude/skills/run/SKILL.md`（1ファイル）

## 受け入れ基準
- creator を worktree 隔離で呼ぶ指示が無い：`grep -c 'isolation: .worktree.. オプションを付ける' .claude/skills/run/SKILL.md` の出力が `0`
- `isolation: "worktree"` の語は手順3の6の既知の原因の説明の1か所だけ：`grep -c 'isolation: .worktree.' .claude/skills/run/SKILL.md` の出力が `1`
- baseRef で分岐元が決まる前提の記述が無い：`grep -c 'baseRef: .head.. 設定により' .claude/skills/run/SKILL.md` の出力が `0`
- worktree を作る呼び出しがある：`grep -c 'bash scripts/add_worktree.sh .PLAN_HEAD.' .claude/skills/run/SKILL.md` の出力が `1` 以上
- 手順3の6に回避策がある：`grep -c 'セッションを作り直して ./run. で再開する' .claude/skills/run/SKILL.md` の出力が `1`
- 文書のバッククォートのパスがすべて存在する：`bash scripts/smoke.sh 2>&1 | grep -c '^  ok   (ref-1) '` の出力が `1`
- smoke 全体が通る：`bash scripts/smoke.sh 2>&1 | tail -1` の出力が `smoke: pass=<n> fail=0` の形（`<n>` は任意）

## 決定済み
- 手順3の2：creator を呼ぶ前に、手順2で引き継がなかった id ごとに `bash scripts/add_worktree.sh <PLAN_HEAD>` を1回ずつ（1回の Bash に1回）実行し、標準出力の `path=`・`branch=` を控える（この呼び出しの形をこのまま書く）。終了コードが0でなければ、その id の creator は呼ばず、標準エラーの内容を人に報告してその id の処理を止める（状態は変えない。doing のまま残り、次の `/run` の手順2の2で扱われる）
- 手順3の2：creator はすべての id で `isolation` を付けずに呼び、prompt を `<計画ID>/<id> の成果物を作ってください。作業する worktree: <パス>` にする（`<パス>` は add_worktree.sh の `path=`、引き継いだ id は `--resume-worktree` の `path=`）。今の「呼び出しには `isolation: "worktree"` オプションを付ける（…）」の文と「prompt は既存どおりタスク ID だけ」の文は消す。`CREATOR_MODEL`・`run_in_background`・起動通知の扱いは変えない
- 手順3の4：保持する worktree のパス・ブランチ名は、add_worktree.sh の標準出力の値（引き継いだ id は `--resume-worktree` の標準出力の値）にする
- 手順3の5の確認コマンド（`git -C <worktree のパス> merge-base --is-ancestor <PLAN_HEAD> HEAD`）は残す（起点を明示しても念のため確かめる）
- 手順3の6：今の「`.claude/settings.json` の `worktree.baseRef: "head"` 設定により計画ブランチ（`PLAN_HEAD`）になる想定」の書き方を消し、worktree は add_worktree.sh が `PLAN_HEAD` から作ると書く。非0の時に自己判断で作り直さず blocked にする運用（質問文を一時ファイルに書き、手順3の8と同じ呼び出し）は変えない。あわせて既知の原因と回避策を書く：
  - 既知の原因：Agent ツールの `isolation: "worktree"` で creator の worktree を作らせていた頃、`worktree.baseRef` が `head` のままでも、セッションの途中で primary working directory が一時的に変わった後に worktree が計画ブランチではなく main（push 先ブランチの tip）から切られ、worktree に計画票・タスク票が無い状態になった（Issue #209。原因は未確定）。`isolation: "worktree"` の語はこの説明の中に1回だけ書く
  - 回避策：その id の blocked を `/plan unblock <計画ID> <id> --fresh` で解除し、セッションを作り直して `/run` で再開する（「セッションを作り直して `/run` で再開する」をこの文字どおり書く）
- 「ハング時の復旧」の1と「Agent 呼び出しがエラーで返った時」の2の creator の「worktree のパスとブランチ名が返っていれば」などの、Agent の結果から worktree を受け取る前提の書き方は、手順3の2で控えた add_worktree.sh の出力の値を使う書き方に直す。破棄の方法（`bash scripts/discard_worktree.sh <worktree のパス> <ブランチ名>`）は変えない
- 手順5の verifier の呼び出し（`isolation` オプションは付けない）は変えない
- transition.py の早見表・終了コードの表は変えない（add_worktree.sh は状態を変えないので表に足さない）
- `.claude/settings.json` の `worktree.baseRef` は変えない（このタスクの成果物ではない）
