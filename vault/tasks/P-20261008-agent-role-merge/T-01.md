# T-01 標準ルールの creator 向けの内容を .claude/agents/creator.md に統合する

## 目的
`vault/rules/` の標準ルールのうち creator に関わる内容（`common/roles.md` の creator が送り手か受け手の節・`common/git.md`・`creator/creator.md`・`creator/git-workflow.md`）を、今の run の手順と矛盾しない形で `.claude/agents/creator.md` に統合する。統合後は6本が無くても creator の振る舞いが定義どおりになる。

## 入力
- `vault/designs/D-013.md` の「フェーズ4 標準の役割定義をエージェント定義に統合する」（決定済み）
- 統合元：`vault/rules/common/roles.md`（「planner → creator」「creator → verifier」「verifier → creator / 人」「creator → 人」の節）、`vault/rules/common/git.md`、`vault/rules/creator/creator.md`、`vault/rules/creator/git-workflow.md`
- 統合先：`.claude/agents/creator.md`（今の定義）
- 矛盾の判定の正本：`.claude/skills/run/SKILL.md`（手順3〜6）、`docs/vault-spec.md`（2節・5節・7節）、`scripts/transition.py` の docstring（review・done で行うこと）

## 成果物
- `.claude/agents/creator.md`（1ファイル）

## 受け入れ基準

- 今の手順と矛盾する記述が無く、収集のコミットの説明が直っている：`grep -nE 'は常に1件だけ|PASS (の)?後にオーケストレーター|作成エージェント（run のメイン）|状態遷移を追記したか' .claude/agents/creator.md` の出力が空で、`grep -n '収集のコミットと差分チェック' .claude/agents/creator.md` の出力が1行以上あり、その行に `transition.py` が含まれる
- 失敗の例が残っている：見出し `## やらないこと（このリポジトリで実際に起きた失敗から）` の節があり、T-0002 の例（基準を書き換えず blocked にし、人が「見出し行と列構成の不変」に差し替えた）が書かれている。確認：`grep -n 'T-0002' .claude/agents/creator.md` の出力が1行以上（あわせて Read で節の中にあることを確認）
- 6本への参照が無い：`grep -nE 'vault/rules/(common/roles|common/git|creator/creator|creator/git-workflow|verifier/verifier|planner/planner|planner/ai-harness-lessons)\.md' .claude/agents/creator.md` の出力が空

- 既存の smoke が全件通る：`bash scripts/smoke.sh 2>&1 | tail -1` の出力が `fail=0` を含む

## 決定済み
- 変えるのは `.claude/agents/creator.md` だけ。`vault/rules/` は書けない（フックが拒否する）ので触れない。6本の削除は人が行う
- frontmatter（`name`・`description`・`tools`・`model`）は1文字も変えない（`model` は `scripts/transition.py` が読む）
- 今の見出し（入力 / 読むもの / 手順 / 書き込んでよいもの / 書き込まないもの / 禁止 / 出力）は残し、次の節を足してよい：`## 受け渡し`（roles.md 由来）、`## git`（git.md・git-workflow.md 由来）、`## やらないこと（このリポジトリで実際に起きた失敗から）`（creator.md 由来）。統合元の「確認方法」節は統合の必須対象ではない。矛盾しないものだけを `## 完了前の確認` として書いてよい
- 「読むもの」の `bash scripts/rules.sh creator` は残す（導入先のルールを読む口として使い続ける）。ルールが列挙されなければ何もしない
- 落とすもの（今の手順と矛盾する）：
  - 「`doing` は常に1件だけ」（並行実行と矛盾）
  - 「`vault/log/<計画ID>.md` に今回の状態遷移を追記したか」（log はオーケストレーターと transition.py が書く）
  - 「作成エージェント（run のメイン）」の呼び方（creator は run から呼ばれるサブエージェント）
  - 「承認前の draft を creator は取らない」（creator はタスクを選ばない。run が選ぶ）
  - 「`attempt` が一致しない verdict は受け取らない」（transition.py が検査する）
  - 「手順の詳細は `vault/rules/creator/git-workflow.md` と ... に従う」（統合先そのもの）
- 言い換えるもの：
  - 「未コミット分は PASS の後にオーケストレーターがまとめてコミットする」→「creator の完了直後に、`transition.py` が収集のコミットと差分チェックを行う」。この文言（「収集のコミットと差分チェック」と `transition.py`）を同じ行に書く。差分チェックで「成果物」に宣言されていないファイルの変更があると差し戻される（`scripts/diff_gate.py`）ことを添える
  - 「verifier にはタスク ID だけを渡す」→ creator は verifier を呼ばないので、「完了報告に作業の経緯・苦労・言い訳・『実質満たしている』の説明を書かない（オーケストレーターは verifier にタスク ID と worktree のパスだけを渡す）」にする
  - 「`git status` で成果物・タスク票・計画票・log 以外に差分が出ていないか」→「『成果物』に宣言されていないファイルを変えていないか（差分チェックで差し戻される）」
  - `vault/tasks/<id>.md`・`vault/verdicts/<id>.json` は `vault/tasks/<計画ID>/<id>.md`・`vault/verdicts/<計画ID>/<id>.json` に直す
  - 計画ブランチへのマージ・コンフリクト時の blocked・PR の作成（`scripts/vcs_finish.sh`）・不採用の worktree の破棄（`scripts/discard_worktree.sh`）は、「creator は行わない（オーケストレーターと transition.py が行う）」の形で短くまとめる
- 残すもの（例）：起点コミットの記録（作業開始時に `git rev-parse --short HEAD` を取り、「進捗」の先頭に `起点コミット: <短縮ハッシュ>`）、creator のコミットは受け入れ基準にある時だけ、ブランチを切らない・切り替えない、`main` に直接コミットしない、破棄は `git restore` だけ（`git clean`・`git reset --hard` は使わない）、`gh pr create`・`gh pr merge` を実行しない、FAIL の後に直すのは `reasons` と該当する `criteria[].note` の点だけ、blocked の質問は人が1回で答えられる形にする、ルール変更は提案ファイル `vault/tasks/<計画ID>/<id>-proposal.md` に下書きする、「やらないこと」の各項目
- 6本・`vault/rules/planner/ai-harness-lessons.md` のパスを書かない（導入先には無くなるため）。`vault/rules/` という語自体（書き込めない、導入先のルール）は書いてよい
- 長さは150行以内を目安にする（受け入れ基準では上限）。同じ内容を節をまたいで繰り返さない
- 「進捗」に「落とした記述:」「言い換えた記述:」で始まる行を書き、上の一覧（と、ほかに落とした・言い換えたもの）を統合元のファイル名付きで列挙する
- `run/SKILL.md`・`docs/`・他のエージェント定義は変えない
