# T-02 vault-spec.md 12節に gh api / curl の検知範囲と残存リスクを明記する

## 目的
`docs/vault-spec.md` 第12節（agent_write_guard フックの改ざん防止判定）を、T-01 で実装した検知範囲（`gh api` / GitHub API への直接 `curl` を含む）に合わせて更新し、拒否リスト方式である以上コマンド経路を完全には列挙できないという残存リスクを明記する。

## 入力
- `docs/vault-spec.md` 第11節・第12節（現行の正本）
- T-01 完了後の `.claude/hooks/agent_write_guard.py`（実際に追加された検知ロジック・関数名）
- `vault/designs/D-002.md`（改ざん防止の設計思想）

## 成果物
- `docs/vault-spec.md` 第12節の追記・更新（既存の表・文言は残したまま、検知範囲の記述を追加する）

## 受け入れ基準
- 第12節に、Bash 経由の `vault/rules/` 書き込み検知が `gh api` および GitHub Contents API への直接 `curl` を含むことが明記されている。確認：`grep -n 'gh api' docs/vault-spec.md` の出力が1行以上
- 同節に、拒否リスト方式である以上未知のコマンド経路を完全には列挙できないという残存リスクが明記されている
- 第11節・第12節の既存の記述（「常に拒否」「提案ファイル方式」等）が削除・書き換えられていない。確認：`git diff docs/vault-spec.md | grep -E '^-.*(提案ファイル方式|常に拒否)'` の出力が空
- `HARNESS_ALLOW_RULES_WRITE` という文字列が新たに追加されていない（廃止済みの仕組みを復活させない）。確認：`git diff docs/vault-spec.md | grep -c '^+.*HARNESS_ALLOW_RULES_WRITE'` が0

## 決定済み
- 追記位置は第12節の表の直後（表を変更せず、表の後に文章として追記する）を想定するが、章立てを崩さない範囲であれば追記位置の細部は作成エージェントの判断に委ねる
- 「残存リスク」の書き方は、D-002 が採用した「到達できない経路だけが安全」という設計思想と対比する形にする。今回の対応はその理想への完全な到達ではなく、既知の抜け穴（`gh api`・GitHub API 直叩き）を塞ぐ拡張であることが分かるようにする
- 表（12節冒頭の状況/判定の対表）の列構成・既存行は変更しない。追加は表の外側（前後の説明文）に書く
- T-01 の実装で実際に追加された関数・変数の名前をそのまま仕様書に書く必要はない（実装詳細ではなく検知範囲の説明でよい）。ただし「`gh api`」「`curl`」という語そのものは本文に含めること（受け入れ基準1のgrep対象）
