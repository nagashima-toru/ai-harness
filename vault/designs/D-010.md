## フェーズ3 タスク粒度（受け入れ基準3〜7行・1計画7タスク以下）をフックで検査する（#77）

### ゴール文

`.claude/hooks/plan_guard.py` に粒度の検査を追加する。Write/Edit の対象が `vault/tasks/<計画ID>/T-xx.md` で、対応する計画票の frontmatter の status が `draft` の時は、「## 受け入れ基準」節の箇条書きが3〜7行でなければブロックする。対象が `vault/plans/<計画ID>.md` で、status が `draft` の時は、タスク表のデータ行が7行を超えればブロックする。`docs/vault-spec.md` の8節と10節に、機械で検査される旨を追記する。`scripts/smoke.sh` にテストを足す（issue #77）。

### 受け入れ基準の候補
- draft 計画のタスク票で受け入れ基準が2行または8行の時、plan_guard がブロックし、reason に行数を含む（smoke.sh で確認）
- draft 計画のタスク票で受け入れ基準が3行・7行の時は、ブロックしない（smoke.sh で確認）
- draft 計画票のタスク表が8行の時ブロックし、7行の時はブロックしない（smoke.sh で確認）
- approved 計画のタスク票を編集した時は、受け入れ基準が8行でも粒度検査でブロックしない（smoke.sh で確認）
- `bash scripts/smoke.sh` の最終行が `fail=0` になる

### 決定済み
- 検査するのは計画票が `draft` の時だけ。承認後に creator がタスク票の「進捗」を編集するたびに、直せない指摘を出さないため
- 検査の契機は、Write/Edit の `file_path` がそのファイルを指す時だけ。Bash による書き込みは対象外（planner は Write を使う）
- `plan_guard.py` は現状 PostToolUse で approved 計画だけを見ている。粒度検査は、それとは別に `tool_input.file_path` から対象の計画・タスクを特定して行う。既存の approved 計画に対する検査は変えない
- 箇条書きの数え方：「## 受け入れ基準」の次の行から次の `## ` 見出しまでの間で、行頭（インデント無し）が `- ` または `数字. ` の行を数える
- `T-xx-proposal.md` など、`T-` + 2桁 + `.md` 以外のファイルは対象外
- 「真偽で判定できる文か」は機械では検査しない。planner・verifier の既存の運用に残す
- ブロックの形式は既存と同じ `{"decision": "block", "reason": ...}`

## フェーズ4 マージを deny し、計画の承認を人の指示（会話記録）で裏付ける（#75 その1）

### ゴール文

`.claude/settings.json` の `permissions.deny` に `Bash(gh pr merge*)`・`Bash(glab mr merge*)`・`Bash(claude *)` を追加する。計画票の承認（frontmatter の status を approved にすること）は、人が `/plan approve <計画ID>` で指示した時だけ許可する。`.claude/hooks/agent_write_guard.py`（PreToolUse）は、Write/Edit/MultiEdit で `vault/plans/<計画ID>.md` の status を approved 以外（ファイルが無い場合を含む）から approved にする書き込みを検出する。その時、メインセッション（`agent_type` が空）であり、かつフックに渡される会話記録（`transcript_path`）の人の発言に `/plan approve <計画ID>` がある場合だけ許可し、それ以外は拒否する。`.claude/hooks/plan_guard.py`（PostToolUse）は、Bash による書き込みの取りこぼしを補う。作業ツリーの計画票を `git show HEAD:<path>` と比べて同じ判定を行い、裏付けが無ければブロックして元に戻すよう指示する。会話記録が読めない時は、どちらのフックもブロックせず、plan_guard が `additionalContext` で警告を出す。あわせて、会話記録（`~/.claude/projects/` 配下）への書き込みを agent_write_guard で拒否する。`.claude/skills/plan/SKILL.md` の B（承認）を、承認後すぐに log へ根拠を1行追記してコミットする手順に改める。`docs/vault-spec.md` の7・10・12節に追記し、`scripts/smoke.sh` にテストを足す（issue #75 のうち承認とマージ）。

### 受け入れ基準の候補
- `.claude/settings.json` の deny に `Bash(gh pr merge*)`・`Bash(glab mr merge*)`・`Bash(claude *)` がある（`jq -r '.permissions.deny[]' .claude/settings.json` の出力で確認）
- 会話記録のサンプルの人の発言に `/plan approve P-TEST` がある時、メインセッションによる P-TEST の draft→approved の Edit が許可される。サンプルに無い時、または `agent_type` が planner の時は拒否される（smoke.sh で確認）
- 同じコマンドが tool_result や `isMeta: true` の行にしか無い会話記録では、承認が拒否される（smoke.sh で確認）
- 会話記録のパスが存在しない時は承認がブロックされず、plan_guard が `additionalContext` に警告を出す（smoke.sh で確認）
- Bash で draft→approved に書き換えた後、裏付けが無ければ plan_guard がブロックする（smoke.sh の git フィクスチャで確認）
- `~/.claude/projects/` 配下のファイルへの Write が拒否される（smoke.sh で確認）
- `bash scripts/smoke.sh` の最終行が `fail=0` になる

### 決定済み
- 人の発言とみなすのは、会話記録（JSONL）のうち `type` が `user`、`message.content` が文字列、`isMeta` が真でない行だけ。`content` が配列の行（`tool_result` など）は対象外。このリポジトリの実際のセッション記録で、この区別ができることを確認済み
- コマンドの一致判定：人の発言が `<command-name>/plan</command-name>` と `<command-args>approve <計画ID></command-args>` の両方を含む（スラッシュコマンドとして打った場合）か、先頭が `/plan approve <計画ID>` である（文として打った場合）。計画 ID は完全一致で比べる
- 裏付けとして探す範囲は、そのセッションの会話記録全体
- 「会話記録が読めない」とは、`transcript_path` が無い・ファイルが無い・どの行も JSON として読めない・人の発言が1件も見つからない、のいずれか。この時はブロックせず警告に落とす（人の回答）。読めたうえでコマンドが無い時はブロックする
- PreToolUse の判定では、書き込み後の内容を組み立てて比べる：Write は `content`、Edit は現在のファイルに `old_string`→`new_string`（`replace_all` を考慮）を適用したもの、MultiEdit は順に適用したもの。比較の相手はディスク上の現在の内容
- PostToolUse の判定では HEAD の版と比べる。同じ承認に何度も当たらないよう、`/plan approve` は承認の直後にコミットする。HEAD 取得の失敗（HEAD 無し・未追跡）は「HEAD では approved でない」として扱う。非 git ディレクトリでは何もしない
- `/plan approve` の log 行は `- <日時> - draft→approved 人の指示: /plan approve <計画ID>`（タスク ID の位置は `-`）。`docs/vault-spec.md` 7節に、計画単位の行としてこの形を追記する
- `Bash(claude *)` の deny は、エージェントが入れ子で `claude -p "/plan approve ..."` を起動し、子セッションの会話記録に人の発言を偽造するのを防ぐため
- 会話記録の改ざん防止：Write/Edit のパス、または Bash の書き込み対象パスが `~/.claude/projects/`（`os.path.expanduser` で展開）配下なら拒否する。`vault/rules/` の改ざん防止と同じ判定の流れに置く
- フック間で関数を import しない既存の方針に従い、会話記録の解析は両フックにコピーして持つ
- `merge_settings_json.py` は src の deny を導入先に足すので、導入先にも `--update` で届く。マージャは変更しない
- blocked の解除は F5 で扱う。このフェーズでは blocked→他 を検査しない

### 依存

## 今回やらないこと

- **自由な文章による承認・解除の指示を裏付けとして認めること**：F4・F5 はコマンド（`/plan approve`・`/plan unblock`）だけを裏付けにする。「T-03 解除して」のような文や、`AskUserQuestion` への回答（会話記録では `tool_result` になる）では通らない
- **会話記録が読めない時に承認・解除をブロックすること**：人の回答で警告に落とした。会話記録の形式の変化で運用が止まるのを避けるため
- **タスク表の done→他 の遷移の保護**：F2 はタスク票・verdict だけを保護する。done を戻す運用自体が無いので、計画票の行を保護するなら F2 と同じ無条件の拒否になる。必要になったら別の計画で扱う
- **Agent 呼び出しをバックグラウンドで起動し、Monitor・TaskStop で監視する方式**：人の回答で、外側のラッパーだけにした
- **creator を haiku などの安いモデルに切り替えること**：F8 の集計で十分な件数が集まってから、別の計画で判断する
- **verifier のモデル別の集計**：F8 で記録はするが、集計の出力は creator のモデル別だけにする
- **「受け入れ基準が真偽で判定できる文か」の機械的な検査**：機械では判定しにくいので、planner・verifier の運用に残す
- **`vault/rules/` 実体への提案の反映を自動化すること**：既存の方針どおり、人が手作業で反映する
