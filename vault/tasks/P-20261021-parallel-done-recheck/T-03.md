## 決定済み
- 実装される挙動（T-01）：`--worktree` 付きの done は、同じ組の他タスクが先に done になって計画ブランチにマージされていたら（`git rev-list --count --merges --first-parent <plan-head>..HEAD` が1以上）、計画ブランチにマージせず、計画ブランチを worktree に取り込み、log に記録行（`plan_head=<H>`）と `review→review attempt=<n> 計画ブランチを取り込み再検証` の行を書いてコミットし、メインの作業ツリーの verdict を消して、標準出力に1行 `<計画ID>/<id>: review→review attempt=<n> 計画ブランチを取り込み再検証 plan_head=<H>` を出し終了コード6で返す。status は review・attempt はそのまま。取り込みの衝突・失敗は review→blocked（終了コード4。今の4の扱いのまま）。2回目の done は `--plan-head <H>` で呼べば今のままマージと done に進む
- 早見表の「終了コードごとの次の行動」の表の5の行の後に、6の行を足す。行は `| 6 | 再検証のため計画ブランチを worktree に取り込んだ。` で始め（この文字どおり）、続けて「done にしていない（review のまま。verdict は transition.py が消した）。手順6の3の6のとおり verifier を呼び直す」旨を書く
- 手順6の3の done の「終了コードごとの次の行動」の箇条（0・4・1）の、4の後に次の箇条を足す。先頭は `6：再検証のため計画ブランチを worktree に取り込んだ`（この文字どおり。他の箇条と同じく `- ` で始める）。中身：done にしていない（status は review のまま、verdict は transition.py が消した）。同じ組の他タスクが先に done になっていて、verifier がその変更を含まない worktree で判定していたため。標準出力の1行を完了報告に写し、標準出力の `plan_head=` の値をその id の `PLAN_HEAD` にする。文「次のタスクへ進む前に、その id の verifier を手順5と同じ呼び出しで1回呼び直し」（この文字どおり）に続けて、完了を待ってから、その id について手順6の1から処理し直す（PASS なら新しい `PLAN_HEAD` で done を呼ぶ。FAIL なら手順6の4）ことを書く
- 次のタスクへ進む前に呼び直す理由も1文で書く：先に他のタスクを done にすると、そのマージで再検証がもう1回要るため（手順6は逐次なので、すぐ呼び直せば再検証は1タスクにつき1回で済む）
- 呼び直しの途中で中断した時は、その id は review の行として手順2の2で扱われる（最後の記録行の `plan_head` が取り込み後の値で、verdict が無いので手順5の verifier から再開する）ことを1文で書く。手順2の2そのものの文は変えなくてよい
- 早見表の PASS の行（手順6。マージ・done・後始末）の説明に「同じ組の他タスクが先に done なら再検証（終了コード6）」を足してよい
- 状態遷移（5つ）・手順4・手順5の本文は変えない
- バッククォートで書くパスは今あるファイルだけにする（smoke の `(ref-1)` が存在しないパスを NG にする）。smoke は1分ほどかかる
