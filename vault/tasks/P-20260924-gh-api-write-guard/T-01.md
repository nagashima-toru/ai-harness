# T-01 agent_write_guard.py に gh api / curl 経由の GitHub Contents API 直叩き検知を追加する

## 目的
`gh api -X PUT repos/<owner>/<repo>/contents/vault/rules/...` や、GitHub Contents API を直接叩く `curl` が `vault/rules/` 書き込み拒否（`targets_vault_rules`）をすり抜けられる穴（issue #6）を塞ぐ。

## 入力
- `.claude/hooks/agent_write_guard.py`（`BASH_WRITE_PATTERNS`、`targets_vault_rules` 関数）
- `scripts/smoke.sh` の `== agent_write_guard.py ==` セクション（既存ケースの書き方の前例）
- `vault/designs/D-002.md`（「人の操作を前提にしない」「到達できない経路だけが安全」という設計思想。今回もこれを踏襲する）
- GitHub issue #6 本文

## 成果物
- `.claude/hooks/agent_write_guard.py` の検知拡張と、対応する `scripts/smoke.sh` の新規テストケース（密結合のため1タスクの成果物とする）

## 受け入れ基準
- `gh api -X PUT repos/o/r/contents/vault/rules/x.md -f content=Zm9v -f message=m` 相当の Bash コマンドを `agent_write_guard.py` に渡すと deny になる。確認：`scripts/smoke.sh` に追加した該当ケースが `ok`
- GitHub Contents API を直接叩く `curl`（例：`curl -X PUT -H 'Authorization: token x' https://api.github.com/repos/o/r/contents/vault/rules/x.md -d '{"message":"m","content":"Zm9v"}'`）も deny になる。確認：同様に追加ケースが `ok`
- `vault/rules/` に触れない `gh api repos/o/r/issues` や `vault/rules/` を含まない `curl` コマンドは引き続き allow のまま（回帰なし）。確認：追加ケースが `ok`
- `bash scripts/smoke.sh | tail -1` の出力が `fail=0` を含む
- 既存の `== agent_write_guard.py ==` セクションの全ケースが `ok` のまま。確認：`bash scripts/smoke.sh` の出力に `NG` を含む行が無い

## 決定済み
- 対象は `targets_vault_rules` 関数の Bash 分岐。`gh api` は `-X` の指定有無を問わず検知対象にする（`gh api` は `-f`/`-F`/`--field`/`--input` を渡すだけで POST 相当になり、明示的な `-X` が無くても書き込みになり得るため）。`curl` は `api.github.com` または `raw.githubusercontent.com`（あるいは `githubusercontent.com`）を含む呼び出しを対象にする
- 既存の `path_like`/`redirect_targets` は `normalize()` でリポジトリルートからの相対パスとして解決する方式で、`repos/<owner>/<repo>/contents/vault/rules/x.md` のように `vault/rules/` の前に `contents/` 等の接頭辞が付く文字列には一致しない（正規化後のパスが `vault/rules/` で始まらないため）。そのため `gh api`/`curl` 系コマンドの判定は、既存の path 正規化とは別に「コマンド文字列に `vault/rules/` というリテラルが含まれるか」を直接見る経路にする（既存の `redirect_targets`/`path_like`/`normalize()` の仕組みは変えず、並行する判定を追加する形でよい）
- 誤検知よりも見逃しを避ける方針にする（D-002 の設計思想の踏襲）。`gh api`・対象 `curl` は method 指定が無くても、コマンド文字列に `vault/rules/` が含まれていれば deny にしてよい
- `gh repo edit`・`gh workflow` など、リポジトリ設定を変更する `gh` サブコマンドはこのタスクの対象外（`vault/rules/` 配下ファイルの中身を直接書き換える経路ではないため）
- `BASH_WRITE_PATTERNS`（役割別の `ALLOWED` 判定にも使われる共通リスト）に `gh api`/`curl` を追加するか、`targets_vault_rules` 専用の別リストにするかは実装者の判断に委ねる。ただし追加した結果、既存の `verifier`/`planner` の Bash 制限（`vault/verdicts/`・`vault/plans/`・`vault/tasks/` へのリダイレクトのみ許可）に予期しない副作用（無関係な `curl`/`gh api` コマンドまで deny になる等）が出ないことを、受け入れ基準5（既存ケース回帰なし）で確認する
- テストケースの `owner`/`repo`/トークンはダミー値でよい（実際に GitHub へ通信するテストは書かない。`agent_write_guard.py` は文字列判定のみで通信しない）
