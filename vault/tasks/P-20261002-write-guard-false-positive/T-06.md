## 決定済み
- 小節の位置：12節の「### 検知範囲：`gh api` / `curl` によるリモート直叩き（issue #6）」の直後、「### 提案ファイル方式（ルール自体を変更するタスク用）」の直前
- 小節に書くこと（文言は creator が整えてよい。ただし受け入れ基準が grep する次の3つの文言はそのまま使う：`解析できない形は従来の判定に落とす`、行頭が `- 解析できない形：` の箇条書き1行、`issue #87` を含み `6.3.4` と `git add` も含む1行）：
  1. 方式：Bash コマンドは `analyze_bash_writes` が shlex でトークン化し、セグメント（`;`・`&&`・`||`・`|`・`&`・引用符外の改行）ごとに実際の書き込み対象（verb と target）を求める。引用符内の文字列・ヒアドキュメント本文・読み取りコマンド（grep・cat・git show 等）の引数は対象にしない。解析できない形は従来の判定に落とす（fail-closed）
  2. verb ごとの対象：リダイレクト・tee・sed -i・cp/mv（宛先）・rm/mkdir/touch/chmod/chown・git add・git commit・git の書き込み系サブコマンド。T-01 の決定済みと実装に合わせる
  3. `- 解析できない形：` の1行：コマンド置換（`$(`・バッククォート・`<(`・`>(`）、サブシェル、`cd` などの作業ディレクトリ変更、変数・グロブを含む書き込み対象、インタプリタやラッパー（`bash -c`・`python3`・`awk`・`xargs`・`find`・`env` 等）、`git -C` のような git の前置オプション、本文に `$(` がある展開されるヒアドキュメント
  4. 5つの判定の使い方：vault/rules/・会話記録・creator の拒否は verb を問わず target で判定する。done 判定は `git add`・`git commit` の対象を除く（issue #87。done 遷移の運用は run/SKILL.md 手順6.3.4 でコマンドを分け、コミットメッセージにコマンド置換を使わない）。verifier/planner の ALLOWED 判定は T-04 の5段の順序
  5. 採らなかったこと：`$(cat <<'EOF' …)` の標準形の許可（案2）は採らない。理由はコマンド置換の中身が任意のコマンドを実行でき、すり抜けを作りやすいため
  6. 残存リスク：拒否リスト方式であることは変わらない。`ln`・`dd of=`・`rsync` などは現行どおり検出しない。従来判定にも `cd vault/rules/ && ...`（末尾の `/`）や `F=vault/rules/...; ... $F` を取りこぼす既知の穴がある（今回は直していない）
- 12節の表（判定の行）は変えない。表の done の行にある「`git add` / `git commit` だけのコマンドも対象外」は、従来判定の範囲の説明として今も正しいため
- 起点コミット欄は採らなかった（計画票の「分割方針」）。vault-spec には書かない（4節・5節の表・見出しの形式は変えない）
- コミットは受け入れ基準に無いので creator は行わない
