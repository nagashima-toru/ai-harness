# T-05 smoke.sh の全件PASSを基準にする際の指針を planner ルールへ追記する提案を書く

## 目的
`.claude/hooks/` や `scripts/` を変更するタスクの受け入れ基準に「`bash scripts/smoke.sh` が全件PASS」を確認コマンドとして書くと、着手前 HEAD 時点で既に存在する環境依存の失敗（今回のような macOS 固有のシンボリックリンク解決の食い違いや、未削除 worktree に由来するフレーキーな失敗）のせいで creator が blocked にせざるを得なくなる（issue #59 で実際に発生した事象）。同じ blocked が繰り返し起きないよう、planner が受け入れ基準を書く時の指針を `vault/rules/planner/planner.md` に追記する提案を書く。

## 入力
- `vault/rules/planner/planner.md`（追記先の実体。「やらないこと」節に既存の同種の失敗事例（T-0002・T-0016・T-0012/T-0013 等）が列挙されている書式を踏襲する）
- `docs/vault-spec.md` 12節「改ざん防止」（`vault/rules/` への書き込みはエージェントに常に拒否されるため、提案ファイル方式で進める根拠）
- `vault/tasks/P-20260926-write-guard-worktree-delegate/T-01.md`・`vault/tasks/P-20260926-hook-worktree-delegate-phase2/T-01.md`（「決定済み」に、着手前HEAD時点の `bash scripts/smoke.sh` 結果をベースラインとして記録し、新規追加分のPASSと既存失敗の非悪化のみを基準にする、という運用が既に2回実例として書かれている。今回の提案はこの運用を毎回書かなくて済むよう標準ルール化するもの）

## 成果物
- `vault/tasks/P-20260926-fix-smoke-sh-failures/T-05-proposal.md`（`vault/rules/planner/planner.md` への追記案の下書き。実体ファイルではなく提案ファイル。`docs/vault-spec.md` 12節の提案ファイル方式に従う）

## 受け入れ基準
- 提案ファイルが存在し、`vault/rules/planner/planner.md` のどこに何を追記するか（追記先の見出し名、追記する具体的な文章）が読み取れる。確認コマンド: `test -f vault/tasks/P-20260926-fix-smoke-sh-failures/T-05-proposal.md && echo exists` の出力が `exists`
- 提案の中身に、`bash scripts/smoke.sh`（または類似の網羅的なスクリプトテスト）の「全件PASS」を確認コマンドにする時は、着手前 HEAD 時点の実行結果をベースラインとして記録し、新規追加分のPASSと既存失敗の非悪化（新たな失敗が増えていないこと）を基準にする、という趣旨の文が含まれる。確認コマンド: `grep -c "着手前" vault/tasks/P-20260926-fix-smoke-sh-failures/T-05-proposal.md` の出力が1以上
- 提案の中身が、今回の issue #59 の経緯（`P-20260926-write-guard-worktree-delegate/T-01` が blocked になった実例）を根拠として挙げている。確認コマンド: `grep -c "issue #59\|write-guard-worktree-delegate" vault/tasks/P-20260926-fix-smoke-sh-failures/T-05-proposal.md` の出力が1以上
- 提案ファイル以外（`vault/rules/` 配下の実体ファイル）を変更していない。確認コマンド: `git status --porcelain -- vault/rules/` の出力が空

## 決定済み
- 追記先は `vault/rules/planner/planner.md` の「やらないこと（このリポジトリで実際に起きた失敗から）」節。既存の同節にある他の項目（T-0002・T-0016 等）と同じ書式（見出し無しの箇条書き1項目、1〜2行の要約＋具体例の参照）で1項目追加する体裁の下書きにする
- 内容の骨子（下書きに必ず含めること）：「`bash scripts/smoke.sh` のような、対象が広く環境依存になりうる網羅テストの『全件PASS』をそのまま確認コマンドにしない。着手時（doing 開始時）に着手前 HEAD で一度実行し、結果（`pass=<N> fail=<M>` と失敗ケース名）をタスク票の『進捗』に記録させ、受け入れ基準は『新規追加分がすべて ok』『既存の失敗件数・内容が着手前から悪化していない』の2点にする」
- 「1ファイルは100行以内を目安に」（`docs/vault-spec.md` 11節）を踏まえ、下書きが長くなりすぎないよう3〜8行程度に収める
- 実体（`vault/rules/planner/planner.md`）への反映は人が手作業で行う。このタスクは下書きの作成までで、実体の書き換えは行わない・行えない（`agent_write_guard.py` が拒否する）
- 他タスク（T-01〜T-04）の成果物ファイルは変更しない
