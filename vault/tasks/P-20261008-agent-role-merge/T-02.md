# T-02 標準ルールの verifier 向けの内容を .claude/agents/verifier.md に統合する

## 目的
`vault/rules/` の標準ルールのうち verifier に関わる内容（`verifier/verifier.md`・`common/roles.md` の verifier が送り手か受け手の節・`common/git.md` の verifier に関係する部分）を、今の run の手順と矛盾しない形で `.claude/agents/verifier.md` に統合する。統合後は6本が無くても verifier の判定のしかたが定義どおりになる。

## 入力
- `vault/designs/D-013.md` の「フェーズ4 標準の役割定義をエージェント定義に統合する」（決定済み）
- 統合元：`vault/rules/verifier/verifier.md`、`vault/rules/common/roles.md`（「creator → verifier」「verifier → creator / 人」の節）、`vault/rules/common/git.md`（verifier に関係する部分：git の書き込み操作をしない、など）
- 統合先：`.claude/agents/verifier.md`（今の定義。手順10は D-012 フェーズ5に合わせて直してある）
- 矛盾の判定の正本：`.claude/skills/run/SKILL.md`（手順4〜6）、`docs/vault-spec.md`（6節 verdict.json）

## 成果物
- `.claude/agents/verifier.md`（1ファイル）

## 受け入れ基準
- 統合元（`verifier/verifier.md` の全箇条、`roles.md` は verifier が関わる2節、`git.md` は verifier に関係する部分）の「ルール」節の箇条が、`.claude/agents/verifier.md` に同じ意味で書かれている。ただし決定済みで落とす・言い換えると決めたものは除く（Read で統合元1本ずつ見比べて確認）
- 今の手順と矛盾する記述が無い：`grep -nE 'PASS (の)?後にオーケストレーター|git status --porcelain|作成エージェント（run のメイン）|vault/verdicts/<id>\.json' .claude/agents/verifier.md` の出力が空
- 失敗の例が残っている：見出し `## やらないこと` の節があり、確認コマンドが実行できなかった時に黙って置き換えないことと、T-0002 で note を必須化した理由が書かれている。確認：`grep -n 'T-0002' .claude/agents/verifier.md` の出力が1行以上（あわせて Read で節の中にあることを確認）
- 6本への参照が無い：`grep -nE 'vault/rules/(common/roles|common/git|creator/creator|creator/git-workflow|verifier/verifier|planner/planner|planner/ai-harness-lessons)\.md' .claude/agents/verifier.md` の出力が空
- frontmatter が変わっておらず、長さが150行以内：`git diff main -- .claude/agents/verifier.md | grep -E '^[+-](name|description|tools|model):'` の出力が空で、`wc -l .claude/agents/verifier.md` の数が150以下
- 既存の smoke が全件通る：`bash scripts/smoke.sh 2>&1 | tail -1` の出力が `fail=0` を含む

## 決定済み
- 変えるのは `.claude/agents/verifier.md` だけ。`vault/rules/` は書けない（フックが拒否する）ので触れない。6本の削除は人が行う
- frontmatter（`name`・`description`・`tools`・`model`）は1文字も変えない（`model` は `scripts/transition.py` が読む）
- 今の見出し（入力 / 読むもの / 手順 / 禁止 / 出力）と verdict.json の例・各キーの説明は残す。足してよい節：`## 受け渡し`（roles.md 由来）、`## やらないこと`（verifier.md 由来）。統合元の「確認方法」節は統合の必須対象ではない。矛盾しないものだけを `## 書き終えた後の確認` として書いてよい
- 「読むもの」の `bash scripts/rules.sh verifier` と、「受け入れ基準がルールを参照している行は、ルールファイルを根拠にし、そのパスを `note` に書く」は残す（導入先のルールのため）
- 落とすもの（今の手順と矛盾する）：
  - `verifier.md` の起点コミットの箇条のうち「creator のコミットは受け入れ基準にある時だけで、未コミット分は PASS の後にオーケストレーターがまとめてコミットする」「`git status --porcelain` に出るファイルを合わせて変更ファイル一覧とする」の部分。今の定義の手順10（verifier を呼ぶ前に `scripts/transition.py` の review で収集のコミット済み。未コミット・未追跡のファイルは検査の対象にしない）を正とする
  - `roles.md` の「`attempt` が計画票と一致しない verdict は受け取らない」は受け手（run・transition.py）の話なので、verifier 側は「`attempt` は計画票のタスク表の値に合わせる」だけを書く
- 言い換えるもの：
  - `vault/verdicts/<id>.json` は `vault/verdicts/<計画ID>/<id>.json` に直す
  - `roles.md` の「verifier の呼び出しにはタスク ID 以外を書かない」は、今の run に合わせて「入力はタスク ID と、あれば対象 worktree のパスだけ」にする
  - `git.md` からは「git の書き込み操作（コミット・ブランチ・マージ・PR）をしない」「対象 worktree に入らない」だけを書く（今の「禁止」の「git 操作」と重ねてよいが、二重に書かない）
- 残すもの（例）：基準を上から1行ずつ真偽で判定する、`criteria` は同じ行数・同じ順序で `text` は原文のまま、`note` は全行で非空、判定不能は `ok: true` のまま `note` と `reasons` に書く、緩い基準の3つの観点、`creator/` のルールを根拠にしない、「進捗」や作成側の説明を根拠にしない、成果物・タスク票・計画票を修正しない、verdict はメインリポジトリ側に書く（issue #61）
- 6本・`vault/rules/planner/ai-harness-lessons.md` のパスを書かない（導入先には無くなるため）。`vault/rules/` という語自体は書いてよい
- 長さは150行以内を目安にする（受け入れ基準では上限）。同じ内容を節をまたいで繰り返さない
- 「進捗」に「落とした記述:」「言い換えた記述:」で始まる行を書き、上の一覧（と、ほかに落とした・言い換えたもの）を統合元のファイル名付きで列挙する
- `run/SKILL.md`・`docs/`・他のエージェント定義は変えない。verifier の判定のしかたそのもの（FAIL にする条件）は変えない
